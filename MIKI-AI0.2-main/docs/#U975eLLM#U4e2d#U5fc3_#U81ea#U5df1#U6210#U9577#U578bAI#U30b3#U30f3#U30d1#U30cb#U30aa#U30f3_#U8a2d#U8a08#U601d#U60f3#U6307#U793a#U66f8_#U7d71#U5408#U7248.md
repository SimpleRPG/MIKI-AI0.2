# 非LLM中心・自己成長型AIコンパニオン 設計思想指示書(統合版)

作成日: 2026-09-11
対象端末: Galaxy S25 / Android / Termux(任意) / 将来的にはAndroidアプリ常駐
利用可能ストレージ目安: 約65GB
統合元: 「GalaxyS25_非LLM記憶対話コード生成システム設計書」「非LLM型_自己成長AIコンパニオン構想」の2文書

---

## 0. この文書の位置付け

本文書は、上記2つの設計書を1つに統合したものである。両文書は同じ方向性(ローカルLLMを中核から外し、通常のプログラムとデータベースで会話・記憶・判断・コード生成を行う)を別の角度から記述していたため、重複を整理し、矛盾なく1つの設計思想として読めるようにした。

**背景となる問題意識:** Termux上でローカルLLM(Vulkan実行)を使う従来方式では、プロンプトが一定量を超えるとDevice Lostや長大な遅延(3B/4Bモデルで1回答に25〜60秒以上)が発生し、KVキャッシュを維持してもこの問題は根本的には解決しなかった。この経験から、「LLMに全記憶を毎回読ませて確率的に文章を生成する」方式を中核から外し、決定論的でテスト可能な非LLM処理を中心に据える方針へ転換する。

---

## 1. 目的

Galaxy S25(および将来的なAndroidアプリ常駐)だけで、次を満たす個人専用AIを構築する。

- 自然な日本語で会話し、過去の会話・訂正・案件・個人ルールを長期保持する
- 「あれ」「前の方」「どっち」などの省略・指示表現を会話状態から解決する
- 情報の真偽・現実・創作・仮定・意見・推測を混同せず管理する
- 知らないことを自分で検出し、調査し、次回から再利用できる知識へ変換する
- 自然言語の依頼(特にVBA/Excel関連)を構造化し、既存コード部品を組み合わせてコードを生成する
- 未知の処理は調査・試行・検証を経て新しい部品として登録する
- 過去の成功・失敗例を再利用して判断を改善する
- 端末内では解決に時間がかかりすぎる未知問題だけをクラウドAIへ依頼する
- ローカルLLMを必須にしない。長大なプロンプト・KVキャッシュ増加・Vulkan Device Lostへの依存を避ける
- 最終的にはAndroidアプリとして常駐し、テキスト・音声のAIコンパニオンとして動作する

目標は汎用LLMの完全な模倣ではない。継続的に利用する分野(個人の会話スタイル、VBA/Excel業務、Galaxy S25特有の制約、過去案件)において、固定サイズの小型LLMより正確・再現性が高く・使うほど成長する専用AIを目指す。

## 2. 基本方針

### 2.1 中核とする技術

- SQLite + 全文検索(FTS5)
- 日本語形態素解析(SudachiPy/SudachiDict等) + 個人辞書
- 会話状態管理・対話行為判定・意味役割解析
- 主張(claim)・証拠(evidence)管理データベース
- ケースベース推論・ルールエンジン
- 部品(コンポーネント)レジストリ + DSLによるコード生成
- 静的検査・実行テスト・Gitまたは独自バージョン管理
- 重み付き意思決定(状況別ユーザー優先順位)
- 計画探索(要求型コンパイラ・能力依存グラフ・制約ソルバー)

### 2.2 補助として使う技術

- ネット検索(公式資料・GitHub実装例・複数情報源比較)
- ダウンロード可能な日本語辞書データ(日本語WordNet、JMdict、Wiktionary構造化データ、chiVe等)
- 必要に応じた軽量な分類器・単語ベクトル(NPU向け)

### 2.3 例外的にのみ使うもの

- **ローカル生成LLM:** 当面必須にしない。非LLM構成で明確に不足が判明した場合のみ、交換可能なProviderとして再検討する。通常経路の必須要素にはしない。
- **クラウドAI:** 常設の頭脳ではなく、端末内で解決が難しい未知問題を「既知の部品」へ変換するための臨時開発担当として、限定的にのみ使う。

### 2.4 非LLM構成を選ぶ理由(利点)

- 通常時のRAM/GPU使用量が小さく、Vulkan Device Lostの影響を受けない
- 長大なプロンプトやKVキャッシュ維持が不要
- 同じ入力に対して同じ結果を返しやすい(再現性)
- 判断理由を追跡しやすく、正式知識・部品の登録条件を厳密管理できる
- ネットが切れても既存の記憶と部品を利用できる
- ストレージを知識庫・部品庫に集中して使える

重くなり得るのは「未知問題で候補を大量列挙し、探索とテストを繰り返す場合」のみであり、その場合だけクラウドAIへ回す。

### 2.5 3BクラスLLMが1回答60秒かかる場合の比較優位

3B LLMがその60秒を「今回の文章生成」だけに使うのに対し、非LLM型は同じ60秒で「今回の回答・根拠収集・検証・次回用知識の保存・新部品候補の作成」まで同時に進められる。既知の問題は即答し、未知の問題だけ調査する設計であれば、同種の問題は2回目以降、知識・規則・部品の再利用により高速化する。

## 3. 対話処理パイプライン(全体像)

```
ユーザー入力
↓
文字正規化・形態素解析(Sudachi等)
↓
会話状態から参照先候補を取得(現在の話題・比較対象・直近実体・未解決事項)
↓
個人辞書・WordNet・Wiktionary・JMdict等の検索
↓
対話行為判定(質問/依頼/訂正/確認/拒否/話題転換 等)・意味役割抽出
↓
記憶(主張DB)・過去事例(ケースDB)・部品レジストリを検索
↓
一意に解釈できるか判定
├─ できる → 既存知識・ルール・部品で処理 → 比較・採点・コード生成・回答内容IR作成
└─ できない → ネット検索 → 主張・条件・根拠抽出 → 既存知識と矛盾検査
              → 端末内で候補探索 → (長大なら)クラウドAI
              → 候補をGalaxy S25で検証 → 成功・失敗・訂正を保存
              → 実績十分ならルール/部品へ昇格
↓
回答内容IR(結論・理由・条件・例外・確実性・対象・次の行動・詳細度・会話モード)の確定
↓
回答骨格・文型・語彙・助詞・活用・語尾の選択(性格設定に応じた表層生成)
↓
意味保持検査(条件・否定・確実性・世界スコープが欠落していないか)
↓
最終回答
```

**重要な設計原則:** 「回答内容(何を言うか)」と「表層表現(どう言うか)」を分離する。性格・口調は表層生成ポリシーであり、事実・数値・成立条件・禁止事項・安全判断・検証結果・出典・確実性など、確定した内容そのものを変更してはならない。

## 4. 会話状態管理・参照解決

### 4.1 保持する状態

`current_session` / `active_topic` / `subtopic` / `current_goal` / `current_comparison` / `recent_entities` / `pending_questions` / `latest_correction` / `last_decision` / `answer_depth` / `interaction_mode`

### 4.2 対話行為の分類

`QUESTION` `REQUEST` `CORRECTION` `CONFIRMATION` `REJECTION` `TOPIC_SHIFT` `CONTINUATION` `FEEDBACK` `CASUAL_CHAT` `REQUEST_RECOMMENDATION` `REQUEST_EXPLANATION` `REQUEST_ARTIFACT`

### 4.3 指示語・省略表現の解決

例:「前に話していたあれ、結局どっちが良さそう？」

- 「前に話していた」→ 直近の継続トピック
- 「あれ」→ 会話状態の`active_topic`
- 「どっち」→ `current_comparison`の候補A/B
- 「良さそう」→ 推奨案を求める意図

候補採点の要素: 直前出現(加点)、現在話題(加点)、未解決事項(加点)、比較対象と候補数の一致(加点)、話題転換後の古い候補(減点)、別案件(大幅減点)、SUPERSEDED(除外)。点数は固定値として崇拝せず、実会話の訂正率から調整する。

**規則:** 候補が一意に絞れるなら自動解決する。複数候補が残っても、どれを選んでも結果が同じなら処理を継続する。**結果が分岐する場合、または誤選択が非可逆・高コストな場合、あるいはユーザーしか決められない価値判断の場合だけ確認する。** 全ての曖昧性に聞き返さない。

### 4.4 単語単体での誤判定を避ける

「長い」「固い」「変」等の単語が含まれただけでフィードバックと判定しない。発言全体・文構造・対話行為・直前回答との関係・否定・引用・仮定・例示・変更要求の有無から判定する。状態を段階化する: `MENTIONED → POSSIBLE_FEEDBACK → DIRECT_FEEDBACK → ADJUSTMENT_REQUEST → CONFIRMED_PREFERENCE`。一度の指摘で全体人格を変更せず、適用範囲(今回のみ/現在の会話のみ/特定話題のみ/特定作業のみ/全体設定)を分けて扱う。

## 5. 性格・自然言語生成

### 5.1 性格は多軸で管理する

単一の形容詞ではなく、複数軸に分解する: 丁寧さ / 親しみやすさ / 直接性 / 形式性 / 回答量 / 技術用語の使用度 / 自発提案の度合い / 慎重さ / 質問頻度 / ユーモアの有無。

設定例:
```
POLITENESS=CASUAL_POLITE
WARMTH=MEDIUM_HIGH
DIRECTNESS=HIGH
FORMALITY=MEDIUM_LOW
VERBOSITY=ADAPTIVE
CONCLUSION_FIRST=TRUE
ASK_ONLY_WHEN_BLOCKING=TRUE
HUMOR=OFF
```

場面別に口調を変える: 通常会話 / 技術調査 / 正式納品 / エラー報告 / 障害復旧 / 短文モード / 詳細説明モード。

### 5.2 回答内容IRと骨格の分離

完成回答を大量に保存するのではなく、部品を分離して組み合わせる: 回答骨格 / 意味別の文型 / 語彙候補 / 接続表現 / 文末表現 / 活用規則 / 助詞選択規則 / 性格設定 / 回答長設定 / 重複除去 / 意味保持検査。

骨格の例:
- **推薦:** 結論 → 主な理由 → 欠点 → 推奨が変わる条件
- **訂正:** 訂正内容の認識 → 古い前提の無効化 → 影響範囲 → 修正後の結論
- **不明:** 現在分かること → 分からないこと → 不足している証拠 → 次の調査手段
- **作業完了:** 実際に完了した内容 → 成果物 → 検証結果 → 未確認事項

同じ意味に複数の表現候補を用意し、回答長・場面・直近で使った語尾・性格設定により選択することで、定型文の反復を抑える。**事実部分はテンプレート変更で意味が変わらないよう固定する。**

## 6. 記憶・知識管理:「事実DB」ではなく「主張DB」

### 6.1 基本原則

ネットや会話から得た文章を、いきなり事実として保存しない。最初は「誰かが述べた主張」として保存する。**保存されていることと真実であることを分離する。**

### 6.2 主張(claim)の分類

**世界の区分:** `REAL`(現実) `FICTION`(創作) `HYPOTHETICAL`(仮定・思考実験) `UNKNOWN_CONTEXT`(不明)

**情報の性質:** `OBSERVATION` `FACT_CLAIM` `OPINION` `HYPOTHESIS` `PREDICTION` `INSTRUCTION` `QUOTE` `FICTIONAL_STATEMENT` `JOKE_OR_IRONY` `CORRECTION`

**検証状態:** `UNVERIFIED` `SUPPORTED` `DEVICE_VERIFIED` `CONTRADICTED` `DISPUTED` `FALSE` `SUPERSEDED` `CONTEXT_ONLY` `UNRESOLVED`

主張データの例:
```json
{
  "claim_id": "CLM-000001",
  "statement": "特定条件で長い入力時にDevice Lostが発生した",
  "world": "REAL",
  "kind": "OBSERVATION",
  "status": "UNVERIFIED",
  "scope": {"device": "Galaxy S25", "environment": "Termux", "backend": "Vulkan"},
  "source": "user_observation"
}
```

「この作品では月に都市がある」は現実では事実ではないが作品世界では正しい可能性がある。単純なtrue/falseではなく、**どの世界・どの条件で成り立つかを保存する。**

### 6.3 情報保存の最小構成

Webページ本文を丸ごと保存せず、保存単位を「ページ」から「知識・主張」へ変える。長期保存するのは抽出した主張・成立条件・情報の種類・検証状態・出典URL・必要な根拠断片のみ。取得したページ本文・コードブロック・検索結果一覧は原則一時保存とし、正式部品作成後は削除可能とする。

### 6.4 情報の品質管理

- **条件を落とさない:** 「Galaxy S25ではDevice Lostが起きる」ではなく「Galaxy S25上のTermuxで、Vulkanを使用し、特定モデルと長い入力条件でDevice Lostが観測された」のように、端末・OS・ランタイム・バックエンド・モデル・設定・入力長・日時を可能な範囲で保存する。
- **推測を事実化しない:** 「たぶんメモリ不足」は`HYPOTHESIS`のまま保存し、実機ログや複数根拠が得られるまで`FACT`へ昇格させない。
- **訂正は上書きでなく状態変更:** 誤情報は削除せず`SUPERSEDED`または`FALSE`に変更し、新しい主張との関係を保存する。
- **矛盾検出:** 主語・述語・対象・肯定否定・端末・バージョン・設定・成立条件・観測日時を比較し、条件が同じで正反対なら強い矛盾とする。条件が違えば別スコープの情報として共存させる。
- **「分からない」を正式結果にする:** `INSUFFICIENT_EVIDENCE` `AMBIGUOUS` `CONFLICTING_SOURCES` `UNSUPPORTED_ENVIRONMENT` `REQUIRES_DEVICE_TEST`。無理に断定しないことがシステムの信頼性を高める。

### 6.5 開世界管理(検索で見つからない ≠ 存在しない)

`FOUND_SUPPORTED` / `NOT_FOUND_IN_SEARCH_SCOPE` / `NONEXISTENCE_SUPPORTED` / `SEARCH_INCOMPLETE` / `SOURCE_UNAVAILABLE` を区別し、検索範囲・検索クエリ・検索対象・検索日時・結果件数・停止理由を保存する。

### 6.6 出典の実質的独立性

複数URLが同じ一次情報を転載している場合、独立した複数根拠として数えない。`ORIGIN_SOURCE_ID` `DERIVED_FROM` `INDEPENDENCE_CLUSTER_ID` 等で追跡し、**信頼度を上げるのはURL数ではなく独立根拠数とする。**

### 6.7 自己生成情報による自己証明の禁止

同じ生成経路が作った主張・根拠・テスト・期待結果・評価だけで正式昇格させない。状態は `SELF_SUPPORTED → INDEPENDENTLY_SUPPORTED / EXECUTION_CONFIRMED / USER_CONFIRMED` の順で扱い、正式昇格には決定論的期待値・独立評価・別実装比較・実行結果・ユーザー明示確認のいずれかを要求する。

### 6.8 知識の成熟度

`DISCOVERED → DEFINED → CONNECTED → APPLIED → REPRODUCED → TRANSFERRED → MATURE`(または`RESTRICTED`=限定条件のみ有効)。取得直後に正式採用しない。転載サイトが複数あっても同じ一次資料なら根拠を積み増ししない。賛成資料だけでなく反対証拠も探す。

### 6.9 概念地図(知識グラフ)

単語一覧ではなく、概念同士を意味付きの関係(「利用する」「必要とする」「原因候補」「一種である」等)で結ぶ。関係には状態(観測済み/辞書由来/資料で支持/仮説/反証あり/ユーザー確認済み/実機検証済み/再検証必要)を持たせ、**概念関係は元の主張・根拠へ必ずリンクし、なぜ接続したか追跡可能にする。**

## 7. 知らないことを自分で調べる仕組み

### 7.1 基本ループ

```
未知・曖昧な発言
↓ 既知部分と未知部分を分離 → 複数の解釈候補を作成
↓ 会話状態・辞書・過去事例・概念地図を検索 → 不足部分だけ外部調査
↓ 候補ごとの結果差を比較
├─ 結果が同じ → 処理継続
└─ 結果が大きく分かれユーザーしか決められない → 確認
↓ 正しい解釈・反例・成立条件を保存
```

知識ギャップの例: 理解できなかった語/意味候補が複数残った表現/回答できなかった質問/根拠不足の判断/矛盾する知識/古くなった技術情報/失敗率の高い部品/毎回クラウドAIが必要になる能力。

調査価値の評価要素: 出現頻度/現在案件への影響/他案件への転用性/誤り防止効果/クラウド依存削減/検証可能性/調査時間/通信量/容量/実験コスト。

### 7.2 調査手段(課題に応じて切り替える)

- **読む:** 会話、確定記憶、個人辞書、対象ファイル、公式資料、API、サンプル、ソース/テストコード、Issue、リリースノート、Web資料、過去納品物、ログ
- **見る/観測する:** スクリーンショット、エラーダイアログ、UI要素、操作履歴、処理時間、メモリ使用量
- **試す:** 合成データ、差分実験、A/B比較、静的検査、コンパイル、実機試験、回帰試験、反例テスト
- **聞く:** 最小情報量で候補を減らす確認質問、自然なユーザー訂正、必要時のクラウドAI
- **追跡する:** 公式更新、API変更、新しいIssue、後日の利用結果、予測と実績の差

課題別の優先手段の例: 未知語→辞書・用例・会話履歴／技術仕様→公式資料／実装方法→公式サンプル・ソース・テスト／不具合→Issue・変更履歴・再現実験／性能→対象端末でのベンチマーク。

### 7.3 自動的に賢くなる仕組み

- **能力不足の自動診断:** 回答不能、検索回数の多さ、応答時間、ユーザー訂正、確認質問の多さ、クラウドAI利用、部品接続失敗、根拠不足、後日の再修正、予測と実績の差、から弱点を検出する。
- **自己試験:** 新知識に対し「何の一種か/目的/入出力/必要条件/使えない条件/類似概念との違い/反例/現在案件への適用」を自問する。
- **未来質問シミュレーター:** 今日習得した能力から次に聞かれそうな境界条件(見出しなし、空欄、列順変更、大量行、先頭ゼロ等)を先取りして用意する。
- **自動レッドチーム:** 自分が失敗しそうな入力(二重否定、引用内の命令、話題転換、評価語の例示利用、過去結論の訂正/空シート、見出し欠落、保護シート、大量行/古い資料、転載、条件付き主張、反対情報)を意図的に作って試す。
- **予測誤差学習:** 実行前に所要時間・変更件数・想定エラー・必要メモリ・採用解釈を予測し、実績との差が大きい箇所を弱点として学習する。
- **学習戦略自体の評価:** 「VBA APIなら公式資料が有効」「俗語なら実会話用例が有効」「Galaxy固有障害なら実機試験が有効」のように、問題の種類ごとに過去成功した調査経路を選ぶ。

## 8. 判断・意思決定

### 8.1 「良い/悪い」はLLM固有の能力ではない

比較対象・評価項目・重要度・確認済み事実が定義されていれば、重み付き採点で判断できる。**事実(観測)と価値判断(優先順位)を分けて保存し、この2つを組み合わせて結論を出す。**

### 8.2 状況別ユーザー優先順位

ユーザーの優先順位を単一の固定値にせず、作業状況(プロファイル)ごとに保持する。

プロファイル例: `casual_chat` `technical_research` `code_design` `code_delivery` `background_learning` `troubleshooting` `data_migration` `emergency_recovery`

優先規則: 1. 最新の明示指示 → 2. 現在案件の確定方針 → 3. 現在作業種別のプロファイル → 4. 過去の同種判断 → 5. 一般既定値。異なる状況の好みを無条件に一般化しない。

### 8.3 反事実テスト

現在の結論に対し、条件を変えた場合(「速度最優先ならどうなるか」「環境が改善したらどうなるか」)を再評価し、無条件の結論ではなく条件付きの結論を作る。

### 8.4 判断結果の遅延評価と後悔学習

即時成功だけで判断せず、`IMMEDIATE / SESSION_END / NEXT_USE / SHORT_TERM / LONG_TERM`の各時点で再評価する。`DECISION_ID` `EXPECTED_OUTCOMES` `ACTUAL_OUTCOMES` `USER_CORRECTIONS` `REWORK_COUNT` `FINAL_UTILITY`等を保存する。失敗理由は`DECISION_ERROR / INFORMATION_GAP / ENVIRONMENT_DRIFT / PREFERENCE_CHANGE / IMPLEMENTATION_ERROR / COMPOSITION_ERROR / TEST_GAP`に分類し、**結果が悪かっただけで当時の判断ロジック全体を誤りとしない。** 原因区分に応じて検索・評価軸・部品・テスト・環境条件のどこを直すか決める。

### 8.5 削減知能(機能追加抑制)

機能や部品を増やすこと自体を賢さとみなさない。既存能力で解決できるなら新規部品を作らない。判定区分: `IMPLEMENT / COMPOSE_EXISTING / MERGE / DOCUMENT_ONLY / WAIT_FOR_EVIDENCE / REJECT_COMPLEXITY / NO_CHANGE`。

## 9. 部品(コンポーネント)レジストリとコード生成

### 9.1 物理保存形式:TXT部品を正本、SQLiteを索引とする

各部品は最低4つの領域(仕様/実装/テスト定義/検証結果)を持つ。小規模部品は次の4ファイルで開始できる。

```
components/text.normalize_spaces/
├─ component.txt      … 仕様・契約・適用条件
├─ implementation.txt … 実装コードの正本
├─ tests.txt          … 試験条件の定義
└─ validation.txt      … 実際の試験結果と正式利用可否
```

外部情報を参考にした部品や複数バージョンを持つ部品では、以下2領域を追加する。
```
├─ sources.txt  … 出典・根拠断片・ライセンス
└─ history.txt  … 変更履歴(追記型、削除禁止)
```
大規模部品では`implementation/` `tests/` `runs/`のようにディレクトリへ分割してよい。**重要なのはファイル数の固定ではなく、仕様・実装・試験定義・検証結果・出典・変更履歴・個別実行記録という役割を混在させないことである。**

### 9.2 component.txtの主要項目

`COMPONENT_ID`(固定・改良版でも不変) `VERSION` `STATUS` `PURPOSE` `INPUTS` `OUTPUTS` `PRECONDITIONS` `POSTCONDITIONS` `SIDE_EFFECTS` `DEPENDENCIES` `SUPPORTED_ENVIRONMENTS` `ENTRY_POINT` `FAILURE_BEHAVIOR` `SECURITY_CLASS`(`READ_ONLY/LOCAL_WRITE/NETWORK/PROCESS_EXECUTION/PRIVILEGED`) `IDEMPOTENT` `DETERMINISTIC`

### 9.3 状態遷移

`COLLECTED → CANDIDATE → ANALYZED → (CLOUD_TESTED) → DEVICE_TESTED → VERIFIED`、または `DEPRECATED / SUPERSEDED / REJECTED`。**状態を飛ばしてVERIFIEDへ昇格させない。CLOUD_TESTEDはDEVICE_TESTEDの代わりにならない(Galaxy S25実機での確認が必須)。**

### 9.4 重複判定・新規作成前の判定

`REUSE`(既存をそのまま利用) `COMPOSE`(組み合わせ) `EXTEND`(後方互換拡張) `NEW`(本当に新規) `DUPLICATE`(重複のため不登録) `REJECT`(安全性・品質上の理由で却下)。重複検出は完全一致ハッシュ→正規化ハッシュ→仕様(目的/入出力/条件/依存)比較→AST構造比較の順で行う。

### 9.5 テスト区分

`NORMAL` `BOUNDARY` `EMPTY` `INVALID` `MISSING_DEPENDENCY` `PERMISSION` `TIMEOUT` `INTERRUPTION` `LARGE_INPUT` `DUPLICATE` `REGRESSION`(過去に失敗した条件の再現)。

### 9.6 検証原則

検証したコードと登録するコードのハッシュを一致させる。検証後にコードを変更したら全検証をやり直す。一部テスト未実施を`PASSED`にしない。クラウド環境での試験だけで`DEVICE_TESTED`にしない。不合格理由を削除しない。

### 9.7 部品検索・選択の優先順位

検索順: COMPONENT_ID完全一致→ENTRY_POINT完全一致→タグ一致→PURPOSEキーワード一致→入出力型一致→構成可能性→正規化ハッシュ→過去の類似事例→意味類似度。
同一能力の複数候補がある場合の優先順: VERIFIED→DEVICE_TESTED→現在環境と完全一致→成功率が高い→依存が少ない→副作用が少ない→新しい対応バージョン→処理時間が短い。

### 9.8 部品構成時の確認事項

前段の出力と後段の入力の接続可能性、型変換の要否、前提条件、副作用の競合、ロールバック経路、タイムアウトの連鎖、循環依存、重複実行、全体テストの存在。**一度しか使わない構成はCASE_ONLYとし、複数回再利用されたら正式な複合部品へ昇格する。**

### 9.9 VBAコード生成の実例

自然言語要求を直接コードへ変換せず、要求コンパイラと検証済み部品を介する。

例: 「元データの仕入先コードと品目コードを抜き出して、重複を除いて新しいシートへ出して。仕入先コードの先頭ゼロは残して。」

```
内部要求:
- 入力元: 元データ / 対象見出し: 仕入先コード、品目コード
- 処理: 見出し検索→配列読込→重複除去→新規シート出力
- 制約: 先頭ゼロ維持 / 禁止: 固定列番号依存
```

Android上で可能な検査: VBAテキスト解析、Sub/Function列挙、ブロック整合検査、GoTo/ラベル検出、Option Explicit確認、Publicインターフェース比較、未宣言変数候補、SHA-256。
Android単体では困難: 実際のExcel VBEでのコンパイル・対象ブックでのイベント動作・Windows API実行→**これらはPC上のExcel環境へ検証依頼する。**

ネットで得られるもの(VBA言語仕様、Excelオブジェクトモデル、一般アルゴリズム、既知のエラーと対策)と、ネットでは得られないもの(対象ブックの実際の見出し・データ開始行・既存数式・業務固有の正解・ユーザーの期待)を区別し、**完成マクロは「公式資料の一般知識+対象ブックの解析+既存コードの解析+業務ルール+過去の訂正+検証済み部品+Excel実機試験」の組み合わせで作る。**

## 10. VBAI(旧ローカルLLM中核)の責務分解

従来ローカルLLMが一括して行っていた処理を、検証可能な複数能力に分解し、それぞれに最適な非LLM部品を割り当てる。目標は単一の代替エンジンで置き換えることではない。

| 旧責務(LLM) | 非LLM代替 |
|---|---|
| 自由文からの意図推測 | 形態素解析+対話行為パターン+会話状態(+任意で軽量分類器) |
| 指示語・省略表現の解決 | 会話状態(active_topic等)+候補採点+結果分岐シミュレーション |
| 記憶選択 | SQLite FTS+語義ID+成立条件+根拠強度+利用実績(SUPERSEDED等は必ず除外) |
| 比較・推薦 | 評価軸+状況別重み+過去実績+反事実評価 |
| 計画作成 | 要求型+能力依存グラフ+Skill IR+探索+制約充足 |
| コード候補生成 | 部品TXT検索+REUSE/COMPOSE/EXTEND+DSLテンプレート+AST変換 |
| コード検証 | 構文解析+型検査+依存検査+テスト実行+ハッシュ照合+実機検証 |
| 説明文生成 | 説明内容IR+多解像度テンプレート+未確認事項の強制表示 |
| 自己改善 | 実行結果+ユーザー訂正+失敗シグネチャ+A/B比較+遅延結果評価(モデルの内省文は根拠にしない) |

基本原則: ローカル生成LLMを通常経路の必須要素にしない。検索・比較・計画・合成・検証を一つの自由生成へ任せない。クラウドAIの回答は候補であり正式知識・正式部品ではない。端末内で検証できないものをVERIFIEDにしない。不明を推測で埋めず未確認状態を正式に保持する。ローカルLLMを後から追加する場合も交換可能なProviderとして扱う。

### 10.1 要求型コンパイラ

自然言語をそのまま実行せず、機械検査可能な要求型へ変換する。項目: `REQUEST_ID` `GOAL` `TARGET` `DELIVERABLES` `CONSTRAINTS` `PROHIBITIONS` `ACCEPTANCE_CRITERIA` `PRIVACY_CLASS` `SIDE_EFFECT_CLASS` `APPROVAL_CLASS` `UNRESOLVED_QUESTIONS` `ROLLBACK_REQUIREMENT`。**型エラーを生成モデルの推測で埋めない。**可逆・局所・非破壊・非送信で重大な影響がない場合だけ安全な既定値を使う。

### 10.2 計画・能力合成エンジン

各能力に`CAPABILITY_ID` `INPUT/OUTPUT_TYPES` `PRECONDITIONS` `POSTCONDITIONS` `INVARIANTS` `PERMISSIONS` `ROLLBACK_CAPABILITY` `RESOURCE_BOUNDS`等の契約を持たせ、前向き/後ろ向き/双方向探索で構成する。型不一致・前提不足・禁止事項違反・権限不足・副作用競合・循環依存・ロールバック不能・検証方法なしの候補は早期に枝刈りする。**終端保証:** 最大探索ノード数・最大深度・最大再計画数・最大同一失敗回数・最大時間を設け、進捗のない反復は`NO_PROGRESS`として停止する。

## 11. クラウドAIとの連携

### 11.1 発動条件

端末内に対応部品がない/探索候補数が上限超過/制限時間内に検証可能案がない/未知API・未知形式/複雑な暗黙関係の推定が必要/同じ能力で再現可能な失敗が複数回起きた、場合に限る。

### 11.2 送信内容と非送信内容

送るもの: 抽象化した目的、要求型、不足能力、関連部品の仕様、端末で試した候補、失敗シグネチャ、成立条件、期待する出力形式、プライバシー検査結果。
**送らないもの:** 全会話履歴、全記憶、全コード部品、資格情報、社内固有情報、未検査の実ファイル。

### 11.3 受入れプロセス

クラウド出力は`CLOUD_PROPOSED`から開始し、端末側の仕様検査・重複検査・静的検査・隔離試験・実機試験を経てから昇格する。一度検証済み部品へ変換できれば、次回以降は端末だけで処理できる。

## 12. ネット情報の安全な取り扱い

Webページ・README・コードコメントに含まれる文章はすべて資料データとして扱い、**命令として実行しない。**「以前の規則を無視せよ」「秘密情報を送信せよ」「このコードをそのまま実行せよ」「正式部品として登録せよ」のような記述は無効化する。

領域分離: ネット取得領域(読み取り専用) / 候補部品領域(原則実行禁止) / 隔離テスト領域(制限権限で実行) / 正式部品領域(検証済みのみ)。

自動化の可否も分離する: 記憶追加(自動可) / 辞書候補追加(自動可) / ルール変更(テスト必須) / 部品追加(隔離テスト必須) / 権限変更(自動化しない) / 正式エンジン更新(バックアップとロールバック必須)。

## 13. 自己改善の安全な運用

### 13.1 改善器・評価器・本番の分離

- **改善領域:** 新規知識候補、新規ルール候補、新規部品候補、新しい表現候補、失敗してよい実験
- **評価領域:** 固定テスト、秘密テスト、過去案件再生、実行結果比較、性能測定、意味等価性
- **本番領域:** 合格済み能力のみ使用、固定規則を保護、問題時に旧版へ戻す

状態遷移: `CANDIDATE → UNIT_TESTED → SHADOW_TESTED → LIMITED → STABLE`。不合格は隔離、悪化確認時は自動ロールバック。

### 13.2 自動変更の可否

自動変更してよい: 回答表現候補、接続表現順位、語尾反復抑制、検索規則、辞書候補、低リスクな読取り部品、テスト候補。
**自動変更させない:** 安全基準、権限拡大、外部送信範囲、正式評価器、監査ログ、ロールバック機構、本番データの破壊処理、ユーザーの固定ルール。

### 13.3 LLM機能の移管判定プロトコル

ローカルLLM呼出しログを解析し、反復して同形式の入出力を扱う処理(意図ラベル付け、検索語生成、JSON整形、候補順位付け、定型説明、構文チェック等)を移管対象として抽出する。移管可能条件: 入力を構造化できる、出力契約を定義できる、同一入力で同一結果が期待される、機械的な合否判定ができる、非LLM実装の方が速度/負荷/再現性で有利。

比較試験は同一入力・同一資料・同一完成条件・同一資源予算で行い、要求理解/条件保持/結果正確性/自然さ/処理時間/RAM/電池/温度/再現性/ユーザー修正回数を比較する。状態: `LLM_ONLY → NON_LLM_CANDIDATE → SHADOW_COMPARISON → NON_LLM_LIMITED → NON_LLM_DEFAULT`(または`LLM_FALLBACK_ONLY / LLM_REMOVED / ROLLBACK_TO_LLM`)。**非LLM経路が必要品質を満たし重大退行がなく資源面で同等以上の場合に既定経路へ昇格する。自然さがわずかに低下しても、コード完全性や安全性が上がる場合はそちらを優先してよい。**

### 13.4 意味差分と条件脱落防止

要約・検索・説明・部品一般化・クラウド受け渡しの各所で重要条件(SUBJECT/ACTION/OBJECT/CONDITIONS/ENVIRONMENT/NEGATION/EXCEPTIONS/TIME_SCOPE/CERTAINTY/SOURCE)が消えていないかを検査する。重要条件が消えた場合、短縮版・抽象化版を正式入力に使わず、元情報を復元して再検証する。

### 13.5 部品の下流影響評価

単体試験の成功率だけでなく、下流成功率・再作業率・失敗伝播率・ユーザー訂正率を部品選択に反映する。単体成功率が高くても下流失敗が多い部品は優先順位を下げる。

### 13.6 非LLM中核の賢さを測る指標

会話(参照解決成功率・不要な聞き返し率・条件保持率)/記憶(関連主張取得率・SUPERSEDED混入率)/判断(推奨後の採用率・再作業率)/部品(REUSE率・下流成功率・二回目以降の処理短縮率)/クラウド依存度(`LOCAL_ONLY`〜`LIVE_CLOUD_REQUIRED`、目標は既知能力についてLIVE_CLOUD_REQUIREDを減らすこと。未知問題を無理にローカル完結させることは目標にしない)。

## 14. ハードウェア・資源の使い分け

### 14.1 CPU / NPU / GPUの役割

- **CPU(非LLM中核):** Sudachi、辞書検索、SQLite/FTS5、会話状態、対話行為規則、概念グラフ探索、要求構造化、VBA解析、部品構成、回答組立、SHA-256
- **NPU:** 意味ベクトル、発言分類、曖昧候補の順位付け、音声認識の一部、画像分類、軽量ニューラル分類器
- **GPU:** NPU非対応のニューラルモデル、画像処理、大規模並列計算、アバター描画

フォールバック順: NPU→(非対応/遅い)→GPU→(不安定/遅い)→CPU。ただし辞書・DB・VBA解析はCPU固定でよい。処理ごとに実機で速度・発熱・電力・安定性を実測して選択する。

### 14.2 Termux vs Androidアプリ

技術的にはPython(Chaquopy等)をAndroidアプリへ内蔵でき、Termuxは必須ではない。開発方針: 1. Pythonで会話中核を作る → 2. アプリへ内蔵 → 3. 実機計測 → 4. 遅い処理だけKotlin/Rust/C++へ移す → 5. ニューラル補助だけNPU/GPUへ移す。Termuxは即時変更・DB調査・緊急保守・試作のための任意環境として残せる。

### 14.3 応答速度の目標値(実測値ではない)

テキスト: 単純既知返答0.1〜0.5秒/記憶検索0.2〜1秒/複雑な比較0.5〜2秒/Web検索は数秒以上/本格調査は数十秒以上。
音声: 呼びかけへの画面反応はほぼ即時/既知回答開始は発話終了後1〜3秒程度。
体感速度を上げる工夫: 呼びかけ直後のアバター反応、結論文から先に読む、検索を直近記憶→頻出知識→長期記憶→Webの順に段階化、重い調査のバックグラウンド化。

### 14.4 ストレージ設計(65GB目安)

区分の目安: 記憶DB・会話原文/辞書類/抽出知識・根拠/コード部品・仕様・テスト/全文検索索引/分類器・ベクトル/候補部品・隔離試験領域/Git履歴・監査ログ/一時ファイル/**常時空き10〜15GB維持。**

空き容量による動作変更: 15GB以上=通常運転/10〜15GB=大容量取得を抑制/5〜10GB=キャッシュと失敗成果物を削除/5GB未満=収集と部品生成を停止。

**容量を満杯にすることは賢さではない。** 保存価値が高いもの(確認済み表現、訂正、成立条件付き知識、再利用成功した部品、失敗の反例、検証ログ)と低いもの(重複回答、未検証Web要約、同一情報の転載、成功不明の部品、全フレーム動画)を区別し、検索範囲をHOT/WARM/COLD/DORMANT/QUARANTINEDに分けて毎回全件検索しないようにする。

## 15. マルチモーダル(画像・音声)と常駐化の優先順位

画像理解(OCR、QR/バーコード、UI検出、エラーダイアログ読取)・動画理解は追加可能だが、AIコンパニオン常駐に必須ではない。優先順位: 1. 会話と記憶 → 2. 音声 → 3. 性格とアバター → 4. 通知 → 5. 必要時だけ画像理解 → 6. 動画理解。画像・動画は原本を永続保存せず、解析結果・タイムスタンプ・重要な証拠画像だけを残す。

常駐時の動作階層: 常時(軽量ウェイクワード・会話状態・通知・簡単なアバター状態) / 呼びかけ時だけ(音声認識・記憶検索・意味解析・回答生成) / 指示時だけ(OCR・画像分類・カメラ) / 充電・アイドル時だけ(Web調査・知識整理・索引更新・部品テスト・自己試験)。

アバター状態: `IDLE` `LISTENING` `THINKING` `SPEAKING` `NOTIFYING` `ERROR` `SLEEPING`。コンパニオンらしさは動画理解より、呼びかけへの即応・過去の会話を覚えていること・話題と口調の継続性で決まる。

---

## 16. 小型LLM(0.5B/1.5B等)との関係

非LLMでも初見表現の分解・言い換え理解・実務文の即興組立・未知話題の調査継続は相当実装できる。ただし小型LLMは学習済みパターンから初見でも素早く候補を出せる点、自由な言い換え・雑談の流暢さで有利。非LLM型は未知を検索・検証して次回から確実な知識に変える点、長期記憶・業務ルール・検証・再現性で有利。

分野別の見込み: 完全初見の自由会話は小型LLMが有利になりやすい/一度調査済みの話題は非LLMが追いつける/繰り返し扱う個人用途は非LLMが上回る可能性/VBA等の既知業務は検証済み部品型が有利/完全未知の高度問題はクラウドAIが有利。

**最も現実的な構成:** 非LLM中核 + 必要時だけ小型分類・埋め込みモデル + 本当に難しい不足部分だけクラウドAI。小型モデルへ全会話・全知識を渡さず、構造化済み候補数件だけを渡して順位付けや曖昧性解消に使う。

---

## 17. この方式の限界(正直な評価)

- 完全な自由対話には大量の辞書・規則・事例が必要で、初見の比喩や皮肉を誤解する可能性がある
- 未知のコード問題では探索時間が長くなり得る
- 誤ったネット情報を取り込む可能性がある
- 知識・ルールが増えるほど重複・矛盾・古い情報の管理が必要になる
- テンプレート回答はLLMより表現が単調になりやすい
- 権限変更や正式エンジン更新は自動化しても慎重に扱う必要がある

一方で次の点では強い: 記憶の正確な保存/訂正履歴/条件付き知識/決定理由の追跡/既知問題の高速処理/再現性/端末内完結/Vulkan非依存/既存部品の再利用/同じ失敗の回避。

## 18. 実装ロードマップ(統合版)

両設計書のロードマップを1本化すると、概ね次の順序になる。

1. **記憶基盤:** SQLite、会話原文・状態、主張DB、訂正履歴、出典
2. **日本語解析:** SudachiPy/SudachiDict、個人辞書、日本語WordNet、Wiktionary、JMdict
3. **会話状態・参照解決:** active_topic/current_comparison/recent_entities/pending_questions、対話行為判定、省略参照の候補解決
4. **判断エンジン:** 評価軸、状況別ユーザー優先順位、重み付き採点、判断理由の保存、反事実テスト
5. **部品基盤:** 部品カタログ(component/implementation/tests/validation.txt)、コードハッシュ、重複判定、依存関係、バージョン管理
6. **コード生成:** 要求型コンパイラ、内部DSL、部品構成(REUSE/COMPOSE/EXTEND)、静的検査、隔離テスト
7. **自律調査:** 知識ギャップ検出、調査価値評価、公式資料・Web検索、反対証拠検索、転載元統合
8. **VBA支援:** VBA構文モデル、Excel基本部品、データ処理部品、TXT納品
9. **VBAIからの責務移管:** ローカルLLM呼出しの棚卸し、非LLM候補化、シャドー比較、限定移管、既定化
10. **クラウド限定連携:** 抽象化、送信監査、候補受入れ、実機検証、部品昇格
11. **自己改善:** ケースベース推論、成功率記録、遅延評価/後悔学習、下流影響グラフ、削減知能、未来質問シミュレーター、自動レッドチーム

13. **ハードウェア最適化:** NPU/GPUでの意味埋め込み・音声・画像認識の実測、遅い中核のRust/Kotlin移植、CPU/NPU/GPU自動フォールバック
14. **PC連携:** Excelでの実コンパイル・対象ブック回帰試験・VBE適用・バックアップ/ロールバック

## 19. 完成条件

### 19.1 通常会話
現在話題を保持できる。省略参照を候補化できる。候補が一意なら自動解決できる。重要な分岐だけ聞き返せる。訂正後に古い条件を再利用しない。

### 19.2 知識利用
主張と事実を区別できる。現実・創作・仮定を混ぜない。成立条件を保持する。出典と独立根拠を追跡する。検索で見つからないことを不存在と断定しない。

### 19.3 判断
比較対象と評価軸を明示できる。状況別ユーザー優先順位を適用できる。推奨理由と結論変更条件を説明できる。後日の実結果で評価規則を更新できる。

### 19.4 コードと部品
既存部品を優先検索できる。重複部品を抑止できる。型・条件・副作用を満たす部品だけ合成できる。静的検査とテストを通過できる。検証済みコードと納品コードのハッシュが一致する。

### 19.5 クラウド依存
通常会話と既知部品利用はクラウドなしで動作する。未知問題だけを抽象化して依頼できる。クラウド回答を無検証で正式利用しない。クラウド由来能力を次回から端末部品として再利用できる。

### 19.6 資源
ローカルLLM常駐なしで通常動作する。VulkanとKVキャッシュへ中核が依存しない。探索・テスト・索引再構築に上限と中断再開がある。ストレージの容量警戒水準を守る。

## 20. 最終方針

VBAIのローカルLLM部分は、単一の代替エンジンではなく、**会話状態・辞書・主張DB・ケース記憶・要求型・能力依存グラフ・部品TXT・探索・ソルバー・テンプレート・静的検査・実行テストへ責務分解して置き換える。**

既知の会話、既知の判断、既知の部品構成、検証可能なコード生成は端末内の非LLM処理を標準とする。端末だけでは探索時間が長大になる未知問題、既存部品にない新規アルゴリズム、複雑な暗黙関係の統合だけクラウドAIへ限定的に依頼する。クラウドAIは回答代行ではなく、新しい未知能力を検証可能な部品TXT・試験・反例へ変換する臨時開発担当とする。

**システムの賢さは、機能数・保存件数・生成文章量では測らない。** 測るべきは次の連鎖が継続的に改善しているかである。

```
未知を検出する → 何が分からないか分類する → 最適な調査手段を選ぶ
→ 根拠と反証を集める → 知識を条件付きで保存する → 実問題へ適用する
→ 成功と失敗を測る → 別案件へ転用する → 検証済み能力として定着する
```

- 同じ失敗を繰り返さない
- 二回目以降が速くなる
- 不要な新規部品を作らない
- 条件を落とさない
- 根拠の独立性を見分ける
- 誤った自己証明を拒否する
- 後日の結果から判断規則を修正する
- 必要なときだけクラウドを使う
- 正式知識と正式部品を実機証拠で支える

理想は無制限に自己書換えするAIではない。**「勝手に学習候補を作り、勝手に試験し、証明できた改善だけ安全に採用するAI」である。** これらが継続的に改善した場合に、非LLM中核が実際に賢くなったと認定する。

## 21. 2026-09-20 実装整合: 会話解析を共通Component機構へ統一

### 21.1 日本語解析を独立した管理系統にしない

日本語解析は独立分類でも、独立オーケストレータでもない。Sudachi、Intl.Segmenter、決定論的Dictionary/N-gram等は、会話で利用可能な通常の解析Componentとして扱う。

禁止する構造:

```text
通常会話 → 日本語専用オーケストレータ → 日本語解析
```

採用する構造:

```text
CORE
↓
conversation
↓
共通Conversation Component Pipeline
↓
Component Registry
↓
解析Componentを取得・構成
↓
解析Componentを実行
↓
Component合成結果
↓
既存のClaim/推論/表層Componentと同じ流れで処理
↓
AnswerContentIR
↓
CORE
↓
UI
```

### 21.2 Componentは言語ではなく契約で扱う

解析Componentは `COMPONENT_ID`、I/O型、前提条件、事後条件、依存関係、環境、決定性、安全性、検証状態を持つ通常Componentとする。

例:

```text
conversation.analysis.sudachi
conversation.analysis.intl_segmenter
conversation.analysis.dictionary_ngram
```

これらは「日本語だから特別」なのではなく、「入力を解析Fragmentへ変換するComponent」である。

将来別言語・別解析方式を追加する場合も、同じRegistry/Composition契約へ登録する。

### 21.3 解析Componentの検証状態

解析Componentが `ANALYZED` の場合でも、決定論的・READ_ONLY・ランタイム許可された解析処理として利用できる。ただし `VERIFIED` とはみなさない。`VERIFIED` への昇格は既存の検証規則に従う。

「実行できること」と「正式検証済みであること」を混同しない。

### 21.4 共通Composition機構

会話解析も `ComponentCompositionService` の計画契約を利用する。

```text
Component Registry
↓
runtime component set
↓
I/O・依存・環境・安全条件をCompositionで検査
↓
CompositionPlan
↓
各Component実装を実行
↓
統合結果
```

Claim × Claim × 推論テンプレート × 表層Componentの合成と、解析Componentの合成は、別オーケストレータを持たず、同じComponent Registry / Compositionの契約で扱う。

### 21.5 17分類 + COREの維持

この共通化によって分類数を増やさない。日本語解析Componentは `conversation` 内部の実装Componentであり、19番目の分類や独立した管理入口を追加しない。

### 21.6 最終不変条件

```text
UI → CORE → 17分類内の必要ドメイン → Component Registry / Composition
→ AnswerContentIR → CORE Result → UI
```

通常会話から日本語解析実装を直接呼び出すことは禁止し、共通Conversation Component Pipelineだけを入口とする。
