# MIKI-AI 18分類 設計・実装基準書

## 文書の目的と正本

この文書は、MIKI-AIの現行アーキテクチャ、責務境界、実装判断、受入条件を定義するLiving Specificationである。

正本の確認は次の三者を相互監査して行う。

- この文書に記載された現在の設計
- GitHub mainに存在する現行コード
- 機械検証で確認された実動作・成果物

この文書だけを実装完了の証拠にはしない。
過去の作業指示書、版別実装レポート、移行履歴、修正ログ、旧設計思想文書は現在の設計の正本にしない。
作業履歴はGit履歴、CI Artifact、監査JSON等で追跡する。

## 基本原則

### 18分類

MIKI-AIは、COREと17の専門分類から成る18分類構造を使用する。

1. CORE
2. autonomy
3. capability
4. conversation
5. data
6. execution
7. experience
8. improvement
9. learning
10. memory
11. promotion
12. research
13. safety
14. selfAwareness
15. selfDevelopment
16. strategy
17. unknown
18. verification

COREも分類の一つとしてコード上に存在するが、実行上は18分類全体の中央統括を担当する。
17専門分類は、それぞれの責務に従って専門処理を担当する。

### COREが次の処理を選ぶ

MIKI-AIは、18分類を固定順序で一周する構造ではない。

現在のBlackboard、目的、Evidence、未解決要件、制約、実行結果をCOREが再評価し、その時点で必要な分類だけを選択する。

したがって、

- 全18分類を毎回呼ばない
- 分類同士を固定チェーンにしない
- 次の分類を前の分類が独断で決定しない
- COREを迂回して業務処理を直結させない

ことを基本とする。

全分類を一括確認する処理は、起動監査・整合性監査・手動診断などに限定する。

## CORE

COREは、MIKI-AIの入口、判断、再評価、終了を統括する。

### COREの責務

COREは次を管理する。

- UI、イベント、自律トリガー、外部指示からの正規Task Ingress
- Task ID、Run ID、Request ID、correlation ID、causation ID
- Blackboardの生成、読取り、更新、永続化
- 現在状態から必要な専門分類の選択
- Domain Commandの生成・配送
- Domain Resultの回収・正規化
- Evidence、Claim、未解決要件、エラー、再試行情報の統合
- 実行環境・資源制約の反映
- 結果回収後のBlackboard更新
- 次の処理が必要かどうかの再評価
- 継続、別分類への切替、保存、検証、停止、完了の決定
- pause、resume、cancel、timeout、cycle上限
- 完了条件とfail-closed

COREは専門分類の内部データを直接書き換えない。
専門処理は分類の公開入口へDomain Commandとして依頼する。

### COREの基本ループ

正規の業務処理は次の考え方で動く。

UI / Event / Autonomous Trigger / External Directive
→ Core Task Ingress
→ Core Orchestrator
→ Blackboard
→ COREが必要な分類を選択
→ Domain Command
→ Domain Result + Evidence + unresolvedRequirements
→ Blackboard更新
→ COREが再評価
→ 次の分類 / 保存 / 検証 / 停止 / 完了

ここで「次の分類」は固定された順番ではなく、その時点のBlackboardからCOREが決定する。

## 17専門分類の責務

### autonomy
自律実行、定期実行、バックグラウンド処理、実行予算を担当する。

### capability
利用可能能力、能力不足、部品選択、Capability Gapを担当する。

### conversation
会話入力、意図、照応、否定、訂正、数値・版数、回答候補の合成を担当する。

### data
構造化データ、Schema、テストデータ、決定論モデル情報を担当する。

### execution
計画された処理、検査Runner、実行要求、実行結果を担当する。

### experience
過去事例、今回結果、成功・失敗・修正の経験化を担当する。

### improvement
改善要求、課題選定、候補ライフサイクル、改善Queueを担当する。

### learning
検証済み結果からの学習、信頼度更新、再利用成績を担当する。

### memory
記憶Repository、永続化、検索適格性、隔離・削除遮断を担当する。

### promotion
Validation済み候補の昇格判定、レビュー待ち、定着状態を担当する。

### research
ローカル資料、Web、GitHub、外部AI調査、Evidence取得を担当する。

### safety
秘密情報、禁止操作、端末資源、危険処理、ロールバック可能性を担当する。

### selfAwareness
自己構成、未確認範囲、制約、不足、接続状態を担当する。

### selfDevelopment
対象コード理解、隔離Candidate生成、部品・テンプレート候補を担当する。

### strategy
Blackboardの状態から計画案、優先度、代替案を作る。
最終的な配送先はCOREが決定する。

### unknown
未知分類、Knowledge Gap、再利用可能な過去解決、未解決状態を担当する。

### verification
Evidence、Claim、反証、型、回帰、一般化、永続化、端末検査を担当する。

## 分類間連携

分類間連携は、固定された直結チェーンではなく、COREを中心としたCommand / Result方式を基本とする。

- Eventは発生した事実を表す。
- Commandは一つの分類への実行要求を表す。
- Resultは観測結果、Evidence、未解決要件、エラーを表す。
- BlackboardはTaskの共有状態を保持する。
- COREはResultを受けて状態を再評価する。
- 次の分類はCOREが決定する。

分類が別分類の内部実装を直接操作することは原則として避ける。
既存の直接呼出しは、発見しただけで即削除せず、責務・契約・副作用・Blackboard帰還方法を確認してから整理する。

## Research

Research分類の正規オーケストレーターはResearchServiceとする。

### ResearchService

ResearchServiceはResearch全体を統合する。

- Knowledge Gapとの接続
- Research Plan / Query Strategy
- Research経路選択
- 複数検索Round
- 検索結果取得
- 結果ページ読取り
- Evidence / Claim登録
- Verification連携
- Knowledge Gapの解決状態
- continuation状態
- Research Outcome

### Web検索層

UnifiedWebResearchServiceはResearchの第二正本ではない。
Web検索技術へのFacadeとして、検索実行、結果ページ取得、設定、統計、低レベルWeb操作を担当する。

AutonomousSearchServiceはProvider探索と結果統合を担当する低レベル実装であり、通常のResearchオーケストレーションを担当しない。

正規Research経路は、

CORE
→ Research分類
→ ResearchService
→ UnifiedWebResearchService
→ AutonomousSearchService
→ Provider

とする。

### Research結果とCORE再評価

Researchの検索結果は、そのまま最終的な真実にはしない。

Researchから返されたResult、Evidence、Claim、Verification結果、unresolvedRequirements、continuation状態をBlackboardへ反映し、COREが次の処理を再評価する。

次のResearch Roundが必要なら、COREがResearch分類を再選択する。
Research内部の安全上限を、探索全体の固定回数制限とは解釈しない。

検索結果はEvidence候補であり、既存のVerification境界を通過した結果だけがKnowledge利用可能状態へ進む。

### Researchの直接呼出し監査

UI、Unknown、Memory、Capability、Autonomy、Background処理などがResearch業務を要求する場合、原則としてCORE Task Ingressから入り、COREがResearch分類を選択する。

既存の直接Research / Web検索呼出しは、次のいずれかに分類してから整理する。

- CORE経路へ統合すべき業務Research
- Research内部からの正当な利用
- Web技術への低レベル利用
- 診断・検証専用利用
- 互換入口
- 設計上未定義の経路

結果契約や副作用を確認せずに削除・置換しない。

### Research実行境界

COREによる認証・受付と、COREによる業務実行は別物として扱う。

UI Gatewayや専門分類がCORE Task Ingressを呼んだ後、その同じ処理の中でResearchServiceやWeb検索実装を直接実行してはならない。
CORE Task Ingressへの送信だけを行い、実際のResearch実行はCOREがResearch分類へDomain Commandとして配送する。

Unknown分類は未知状態の分類、検索必要性の判定、Knowledge Gap生成などを担当できる。
ただしResearch実行そのものはResearch分類の責務とし、UnknownからResearchService.executeSearch等を直接呼び出さない。

Research UI Gatewayは設定・表示・受付の入口として機能できる。
ただし「COREでauthorizeした後にGateway自身がResearchを実行する」構造はCORE経路とはみなさない。
Research実行要求はCORE Taskとして渡し、Domain ResultをCOREから受け取る。

ResearchService.executeSearch等の既存直接APIは、Research内部、低レベルWeb層、互換入口、診断経路を除き、業務実行入口として外部分類から直接利用しない。
既存直接呼出しを整理するときは、結果契約、Evidence、Claim、continuation、エラー、Blackboard帰還を確認してから移行する。

### 会話からUnknown/ResearchへのCORE経路

Chat UIはUnknown DomainやResearch Domainを直接実行しない。

会話から未知解決が必要な場合は、CORE Task IngressへUSER_REQUESTとして投入する。
COREがBlackboardを基準にUnknownを選択し、Unknown ResultにResearch要求があればCOREが再評価してResearch Domain Commandを配送する。

UIはCORE Taskの完了結果を受け取り、Domain内部サービスの直接実行結果を会話処理の入口として使用しない。

### UnknownからResearchへの要求契約

Unknownが検索の必要性を判定した場合、Unknown自身はResearchを実行しない。

Unknown Domain Resultには、少なくとも次を返す。

- status: RESEARCH_REQUIRED
- researchQuestion: COREがResearchへ渡す検索要求
- unresolvedRequirements: Research実行が必要であることを示す未解決要件

COREはこのResultをBlackboardへ記録し、再評価時にresearchQuestionをResearch Domain Commandのqueryへ変換する。

Research Domain CommandはCOREからResearchへ配送する。
Research結果は再びCOREのBlackboardへ戻し、COREが次のUnknown、Verification、Learning、Conversation等の必要分類を再評価する。

Unknownの「検索が必要」という判定と、Researchの「検索を実行する」という処理を同一処理として扱わない。

## 自己改善

自己改善の本番コード自動適用は行わない。
自律処理の安全な終点は、レビュー待ち累積ZIPの作成までとする。

基本経路は、

課題自動発見
→ 自動発見Run
→ 自己改善Ingress
→ 永続Queue
→ CORE / Blackboard / 必要分類
→ 対象ファイルをEvidenceで特定
→ 現行Snapshot固定
→ 隔離Candidate Workspace
→ Candidate SHA固定
→ STATIC / TYPECHECK / REGRESSION / COUNTEREXAMPLE
  / GENERALIZATION / PERSISTENCE / DEVICE
→ Shadow Evaluation
→ 単一Promotion Gate
→ レビュー待ち台帳
→ 累積レビューZIP
→ 外部AI・利用者による確認

自動発見Runと外部AI作業指示Runは、別Run、別Task、別Workspaceとして管理する。
安全パイプラインだけを共通利用する。

自己改善で不足が発生した場合は、Knowledge Gap、Capability Gap、Validation Script不足、実行環境不足などとして必要資産を増やす。
ただし物理的資源不足や安全違反を無視して強行しない。

GitHubへのpushは通常機能として残すが、自己改善ループから本番コードを自動pushしない。

### 自己改善の実装責務分離

ImprovementIntakeRouterServiceはRunの正規化・重複抑制・系譜を担当する。
SelfImprovementIngressServiceは正規Ingress、AutonomousSelfImprovementLoopServiceはQueue、Task、attempt、resource/evidence wait、pause/resume、復旧を担当する。
AutonomousIssueDiscoveryServiceはIssue発見、CandidateCodeGenerationServiceはCandidate生成、IsolatedCandidateWorkspaceServiceはBaseline/Candidate分離、CandidateValidationRunnerServiceとCandidateValidationEvidenceServiceは検証、ShadowEvaluationServiceはShadow評価、SinglePromotionGateServiceは唯一のPromotion判定、CumulativeRevalidationServiceは累積Candidateの再検証、ReviewZipExportServiceはレビュー成果物化、ExternalDirectiveIntakeServiceは外部指示の正規化を担当する。

これらの責務を一つの自己改善Controllerへ統合しない。
Loopは専門判断を持たず、Candidate生成はPromotion判断を持たず、Review ZIP生成は採用判断を持たない。

### 自己改善RunとCORE Task

RunとCORE Taskは同一IDとして扱わない。
Runは改善要求のライフサイクル、TaskはCOREのオーケストレーション単位とする。
runId、taskId、ChangeSetID、sourceId、workspaceId、operationInstanceId等で系譜を接続する。

Adaptive Route Plannerの業務OperationにはoperationInstanceIdとdedupeKeyを持たせる。
同一Operationの誤重複実行は防ぐが、新しい入力・Revision・Attemptが必要な場合は新しいOperation Instanceとして再実行できる。

### 自己改善の完了判定

自己改善Taskでは固定された18分類の全通過を完了条件にしない。
CorePlanRevisionServiceのrequiredOperationsを基準にCoreCompletionGateServiceがPlan、必須Operation、失敗、pending、Domain Error、Reply lineage、persistence receipt、Evidence qualityを確認する。

Candidate生成とReview Package生成は、処理結果が返っただけでは完了としない。
必要なpersistence receiptとlineageが確認できることを完了条件に含める。

### 自己改善の開始源

自己改善はUIだけを入口としない。
AUTONOMOUS_DISCOVERY、EXTERNAL_DIRECTIVE、USER_REQUEST、EXECUTION_FAILURE、REVALIDATIONをRunTypeとして区別する。
実行失敗、検証上の矛盾・未解決、自己改善要求Event等からも正規Ingressへ接続できる。

### 外部指示の境界

ExternalDirectiveIntakeServiceは外部指示を直接実行しない。
directiveId、sourceHash、objective、targetFiles、requirements、prohibitions、invariants、validationRequirements、deliveryRequirements、relatedIssueIdsを保持してから改善Runへ渡す。

外部指示はCOREの判断を置き換えない。
COREがBlackboardとEvidenceを再評価し、必要なResearch、Unknown、Verification、SelfDevelopment等を選択する。

### Candidateからレビューまでの状態境界

Candidate生成成功、Validation成功、Shadow Evaluation成功、Promotion Gate通過、Review ZIP生成、本番採用、本番適用は別状態である。

ReviewZipExportServiceはBaseline/Candidate manifest、hash、Validation、Shadow、Issue、Directive、系譜、未解決事項を保持し、ZIP自体も検証する。
累積PackageではpackageSeriesId、packageRevision、candidateRevisionを保持する。

### 本番反映境界

SinglePromotionGateServiceのallowedはCandidateが検証条件を満たしたことを示すだけで、本番書込み権限を意味しない。
本番反映はレビュー結果、明示的承認、対象SHA、現在Baselineとの一致を確認する別境界とする。
自己改善Loop、Candidate生成、Review ZIP生成から本番コードを直接変更・pushしない。

### 自己改善の現在実装境界

自己改善は、本番コードを直接変更する処理ではなく、改善要求をCOREへ渡し、必要な18分類をCOREが選択し、Candidateを隔離して検証し、レビュー可能な成果物まで到達させる自律処理として扱う。

SelfImprovementIngressServiceは入口を正規化し、ChangeSetID等の系譜情報を付与してAutonomousSelfImprovementLoopServiceへ渡す。

AutonomousSelfImprovementLoopServiceは永続Queue、Task、attempt、pause、resume、resource wait、evidence wait、retry、failure recoveryを管理する。専門的な改善判断をこのLoopへ集約しない。

Queueへ入った自己改善TaskはCoreTaskIngressServiceを経由してCOREへ渡す。COREはBlackboardを基準に必要な分類を選択する。自己改善専用の固定順序を作らない。

AutonomousIssueDiscoveryServiceは、実行失敗、Knowledge Gap、Capability Gap、停滞Task、Domain Disconnect、Claim矛盾、Improvement Debt等から改善候補を発見する。発見したIssueは即コード変更せず、自己改善要求としてCOREへ渡す。

コード変更が必要になった場合はIsolatedCandidateWorkspaceServiceでBaselineとCandidateを分離する。CandidateにはworkspaceId、issueId、runId、writeGuard、Baseline hash、Candidate hash、対象ファイル、Evidenceを紐付ける。

CandidateValidationRunnerService等による検証は、単なるファイル生成確認ではなく、static、typecheck、regression、counterexample、generalization、persistence、device、Evidence整合性等を個別のEvidenceとして残す。ComplexityCostGateも候補評価の一部とする。

ShadowEvaluation後の採用可能性はSinglePromotionGateServiceに集約する。Candidate hash、Validation Evidence、Shadow結果を確認し、別経路から採用可能状態へ進めない。

レビュー成果物はReviewZipExportServiceを正規の成果物化経路とする。複数Candidateを累積する場合はCumulativeRevalidationServiceで同一ファイルの競合と累積状態を検査する。

外部AIや利用者からの作業指示はExternalDirectiveIntakeServiceでDirectiveとして正規化する。指示本文をそのまま実行命令とせず、objective、target files、requirements、prohibitions、invariants、validation requirements、delivery requirements、source hash等を保持する。

自己改善の完了状態は「コードを書いた」「Candidateを作った」「Promotion Gateを通った」「ZIPを作った」のどれか一つではない。検証済みCandidate、系譜、hash、Evidence、レビュー成果物が揃い、レビュー待ちとして固定された時点を自律改善サイクルの安全な終点とする。

本番コードへの自動適用および自己改善ループからの本番pushは行わない。採用、拒否、修正、追加調査はレビュー後の別段階としてCOREへ戻せる。

自己改善の自律性とは、本番コードを勝手に書き換えることではなく、発見、要求化、COREによる分類選択、調査、Candidate生成、検証、再計画、待機、成果物化、レビュー引渡しまでを人間の逐次操作なしで進められることを意味する。

## Evidenceと完了条件

次だけでは完了と判定しない。

- ファイルを作成した
- exportした
- UI文言を変更した
- 固定値でtrue / success / passedを返した
- AIが自己申告した
- ユーザーが一度肯定した
- エラーダイアログが表示されなかった

完了には、少なくとも次の4段階の証拠を必要とする。

EXISTENCE
→ WIRING
→ BEHAVIOR
→ ARTIFACT

安全側ではPARTIALから開始する。
taskId、correlationId、artifactHash、verification Evidence、検証環境、必要な検査結果が揃った場合だけ完了へ進める。

## ユーザー反応

ユーザー反応は重要なEvidenceだが、単独で最終真実にはしない。

- 一回の肯定でVERIFIEDへ昇格しない。
- 一回の否定で全回答・全部品を破棄しない。
- 良かった部分、誤った部分、訂正された部分を分離する。
- ユーザーの訂正も、既存Claim、辞書、公式情報、実行結果等と照合する。
- 未知語や矛盾があればUNKNOWNまたはCONFLICTEDとして追加調査へ戻す。

## Memory

アプリから見た記憶の正本は単一Memory Repository契約とする。

- AndroidはSQLiteをBackendにする。
- WebはIndexedDBをBackendにする。
- JSON全件配列は移行・互換・バックアップ用途に限定する。
- 更新はレコード単位とし、FTSも差分更新する。
- retrieval、usage、execution success、validation success、ユーザー反応を別指標として扱う。
- quarantine、discard candidate、inactive、expired、superseded、pending revalidationは、回答、自己改善、クラウド送信、exportから遮断する。

## 会話と言語

日本語解析は役割の異なる決定論的部品を組み合わせる。

Sudachi Native
+ Intl.Segmenter
+ 決定論的辞書
+ N-gram

通常会話では検証済み部品を制限時間内で組み合わせる。
未研究の組合せはバックグラウンド研究で候補化し、意味保持、反証、複数観測を経て昇格させる。

## 外部知識と外部AI

既存Claim、Memory、Web検索、公式資料、実行試験、外部AIの情報源を区別する。

外部AI調査は関連Knowledge Gapを小規模バンドルにまとめ、次の経路を選択可能にする。

- 自動API
- 手動コピー
- 質問TXT
- 返信TXT取込み

外部AIの回答はCLOUD_AI Evidenceとして保存し、直ちに検証済み知識へ昇格させない。

## ローカルLLM

旧GGUF、llama.cpp、WebLLM等のローカル生成ランタイムは、現在のMIKI-AIの通常経路として使用しない。

通常処理は決定論的Non-LLM部品を使用し、自由生成が必要な場合だけ明示された外部AI経路を使用する。

ローカルLLM再導入禁止の監査規則と退役試験は保持してよい。
旧実行コード、旧設定UI、旧モデル読込み、旧案内文、旧互換層は、参照がなくなり安全に退役できることを確認した上で削除する。

## UI

スマートフォンを第一対象とする。

- 主要操作は44px相当以上
- 入力文字は16px以上
- 1列配置を基本とする
- 詳細情報は折り畳む
- Queue受付と処理完了を区別する
- 現在分類、待機理由、Evidence不足、再試行、レビュー待ち件数を確認できる
- 自己改善の方向と実行間隔を設定できる
- Safe Areaとキーボード表示を考慮する
- 横幅依存の巨大な図や表を主要説明に使用しない

UIは表示専用状態までCOREへ集中させない。
永続状態、業務状態、改善状態、外部作用を伴う操作はCORE経由を原則とする。

## 重複と複雑性

同じ責務のController、Coordinator、Router、Gate、Repository、保存キー、イベントを増やさない。

新規サービスを作る前に既存サービスを検索し、少なくとも次を比較する。

- 責務
- 入出力
- 副作用
- 保存先
- 呼出元
- ライフサイクル
- 既存の公開契約

機能差がなければ既存の正本へ統合する。
互換入口が必要な場合も、独自の業務ロジックを持たせず正本へ委譲する。

複雑性コストとして、新規ファイル、Public API、保存キー、イベント、依存辺、変更行数を確認する。

## 変更判断

設計と実装の不一致は、次の4種類に分類する。

1. 設計が正しく、コードが誤っている
2. 実装が進展し、設計が古くなっている
3. 設計と実装の双方に問題がある
4. 単純な実装バグである

判断を飛ばしてコードだけを変更しない。

設計が正しい場合はコードを設計へ合わせる。
実装の進展で設計が古くなった場合は、先にこの文書を更新してからコードを変更する。
双方に問題がある場合は、設計を整理してからコードを変更する。

## 実装・検証・GitHubの流れ

変更は次の順序で確認する。

現行GitHub main確認
→ 設計確認
→ 不一致分類
→ 必要なら設計更新
→ 実装
→ 型・import検査
→ 挙動検査
→ 成果物検査
→ GitHub mainへ反映
→ mainを再取得して確認
→ 設計との再照合

GitHub mainに存在しない変更を、存在すると仮定して次の変更へ進まない。

## 必須監査項目

18分類全体に変更を加える場合、または分類境界に関係する変更では、少なくとも次を確認する。

### 構造

- 18分類の定義が一つである
- 未分類サービスがない
- 同一責務の重複実装が増えていない
- COREの責務と専門分類の責務が逆転していない

### 経路

- UI・イベント・自律トリガー・外部指示が必要な業務処理でCOREを迂回していない
- CORE Task Ingressへの認証・受付だけで、業務実行をCORE経由と誤認していない
- UI GatewayがCORE受付後に専門サービスを直接実行していない
- UnknownがResearch実行を直接所有していない
- Research実行はResearch Domain Commandから開始される
- Domain CommandがCOREから配送される
- Domain ResultがBlackboardへ戻る
- COREがResultを再評価して次の処理を決定する

### Research

- ResearchServiceがResearchの正規オーケストレーターである
- UnifiedWebResearchServiceが第二Research正本になっていない
- AutonomousSearchServiceが低レベルWeb層として維持されている
- 直接検索呼出しを責務ごとに監査している
- UI Gatewayからの直接Research実行がない
- Unknownからの直接Research実行がない
- CORE認証後の直接Research実行をCORE経路として扱っていない
- Research結果がCOREの再評価へ戻る
- Research検索結果だけでKnowledgeを確定していない
- Research関連の型・関数・結果収集が意図せず重複していない

### 自己改善

- 本番コードの自動適用を行わない
- Candidateとbaselineを識別できる
- Candidate SHAとEvidence SHAを照合できる
- Promotion Gateが単一の判定境界として機能する
- レビュー待ち成果物を累積ZIPとして再現できる
- 自動pushが自己改善の完了条件になっていない

### 安全・検証

- 相対import断線がない
- 静的import循環を確認する
- 旧ローカル生成経路が残っていない
- 固定成功値がない
- 重要経路に空catchがない
- 記憶の隔離・削除遮断が全経路で維持されている
- ZIPが破損していない
- ZIP内TXTと実体が一致している

## Living Specificationとしての維持

この文書は作業履歴ではなく、現在有効な設計・制約・受入条件だけを保持する。

個別の実装作業、P番号、版番号、修正ログを逐次追加しない。

設計変更時は、現行コードと機械検証を調査し、設計と実装の差を分類する。
変更後は必ずコードと機械検証を再確認し、その結果をこの文書と照合する。

設計・コード・機械検証の三者に矛盾が残っている状態を、実装完了とは扱わない。

## Research探索十分性の追加基準

Researchは「検索APIを呼べたこと」や「一定回数検索したこと」だけで探索完了と判定しない。

探索十分性は、検索量ではなくEvidence Coverageを中心に判断する。

少なくとも次をResearchの進捗として扱う。

- 必要ClaimまたはKnowledge Gapの未解決要件
- 検索観点のCoverage
- 独立した情報源の数と独立性
- 一次情報・公式情報の取得状況
- 反証・制限情報の探索状況
- 現在の実行環境への適用可能性
- 実際の結果ページ本文を読めたか
- Evidence品質
- Claim間の矛盾
- 前回探索からの新規情報量
- 未解決Requirements
- 次の探索で得られる情報価値

検索回数、URL数、ページ数、時間予算は安全上の上限であり、それ自体を「十分探索した」という意味にしない。

Researchは必要に応じて複数の検索観点を使用し、結果が不足していればQuery Revision、別観点、公式情報、反証、現在環境確認などへ展開できる。

1回のResearch呼出しで安全な実行上限を設けても、論理的な探索全体はCOREの再評価によって次のCycleへ継続できる。

Researchが検索を十分に行ったがVerificationが不足している場合と、ResearchそのもののCoverageが不足している場合を区別する。
前者ではVerification等をCOREが選択し、後者ではResearchを再投入できるようにする。

「結果が見つからなかった」と「対象が存在しない」を同一視しない。
CONFIRMED_ABSENCEを使用する場合は、対象に応じた探索Coverage、一次/公式情報、反証探索、時間・環境条件、未解決要件を満たしたことをEvidenceとして残す。

Research Query PlanはCOREの18分類思想と矛盾する固定分類リストを正本として持たない。
Research内のQuery Planningは探索観点を計画する責務であり、次にどの18分類を実行するかを決定する権限はCOREにある。

Researchの安全な終端は「検索した」ではなく、
必要なEvidence Coverageを確認し、Verification境界を通過するか、未解決理由と次に必要な処理をCOREへ返した状態とする。

## Research完了判定とCORE完了条件

Research結果が存在することだけを、Research完了またはTask完了の根拠にしない。

Researchの完了状態は、Research結果の存在に加えて、探索十分性または明示された終端条件を満たしていることを必要とする。

- continuationAvailable=true のResearch結果は未完了として扱い、COREは追加探索を再評価する。
- outcome=INSUFFICIENT_SEARCH はCoverage不足として扱い、COREがResearchを再投入できる状態を維持する。
- outcome=INSUFFICIENT_VERIFICATION はResearch結果の存在だけで完了とせず、COREがVerification等の必要な分類を選択する。
- outcome=NOT_FOUND_AFTER_COVERAGE は、対象に必要なCoverage条件を満たしたことがEvidenceとして確認できる場合に限り、探索終端として扱える。
- resolved=true または同等の十分性終端条件を満たさないResearch結果だけでは、Research依存Taskを完了させない。
- COREのTask完了判定は、Research結果の有無ではなく、Researchの状態、Evidence、Verification、未解決要件、continuation状態をBlackboardから再評価して決定する。

これにより「検索結果が返った」ことと「必要な探索が完了した」ことを明確に分離する。
