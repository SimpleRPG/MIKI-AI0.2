# MIKI-AI 18分類 設計・実装基準書

## 文書の目的と正本

この文書は、MIKI-AIの現行アーキテクチャ、責務境界、実装判断、受入条件を定義するLiving Specificationである。

正本の確認は次の三者を相互監査して行う。

- この文書に記載された現在の設計
- GitHub mainに存在する現行コード
- 機械検証で確認された実動作・成果物

この文書だけを実装完了の証拠にはしない。
過去の作業指示書、版別実装レポート、移行履歴、修正ログ、旧設計思想文書は現在の設計の正本にしない。
作業履歴はGit履歴、CI Artifact、監査JSON等で追跡する。

## 基本原則

### 18分類

MIKI-AIは、COREと17の専門分類から成る18分類構造を使用する。

1. CORE
2. autonomy
3. capability
4. conversation
5. data
6. execution
7. experience
8. improvement
9. learning
10. memory
11. promotion
12. research
13. safety
14. selfAwareness
15. selfDevelopment
16. strategy
17. unknown
18. verification

COREも分類の一つとしてコード上に存在するが、実行上は18分類全体の中央統括を担当する。
17専門分類は、それぞれの責務に従って専門処理を担当する。

### 18分類を一つの脳として機能させる

18分類は、18個の独立した機能群を並べたものではない。
COREと17専門分類を合わせた18分類全体を、MIKI-AIという一つの脳として扱う。

一つの脳として機能するため、各分類は自分の処理だけを完了させて終わるのではなく、Taskの目的と現在状態を共有する。

- COREは全体の目的、状態、制約、Evidence、Claim、未解決要件、実行結果を統合する。
- 各専門分類は、自分の専門知識・判断・処理能力を使って、現在のTaskに必要な情報や結果をCOREへ返す。
- COREは返された結果をBlackboardへ統合し、現在の全体状態を再評価する。
- 再評価によって次に必要な分類だけを選択する。
- 選択された分類は、直前の分類から独立した別処理として動くのではなく、同じTaskの目的を引き継いで処理する。
- 処理結果は再びCOREへ戻り、18分類全体の状態として統合される。
- 必要な分類が変わった場合も、Taskの目的、系譜、Evidence、Claim、未解決要件を維持したまま別分類へ接続する。

したがって、18分類の基本単位は「分類単体」ではなく、

`目的 → CORE → 必要な専門分類 → 結果 → CORE再評価 → 必要な専門分類 → 結果 → … → 完了`

という一つの認知・実行ループである。

これは固定された一本道ではない。
同じTaskの中でResearchからUnknownへ戻ることも、ResearchからVerificationへ進むことも、ExecutionやSafetyを挟むこともできる。
その時点で必要な分類をCOREが選択し、結果を一つのBlackboard状態へ統合する。

各分類は「自分の判断だけでTaskを完了させる」のではなく、COREへ返すResultによって一つの脳の状態更新に参加する。

### 一つの脳としての情報統合

18分類が一つの脳として機能するため、Taskに関する正規状態を分散した別々の状態として独立管理しない。

Taskの目的、Task ID、Run ID、correlation、Evidence、Claim、未解決要件、制約、Domain Result、Operation Instance、検証状態など、複数分類が参照する情報はCOREのBlackboardを中心に系譜を維持する。

専門分類が生成した情報は、その分類だけの「答え」として閉じず、必要なものをDomain Result、Evidence、Claim、Event等としてCOREへ返す。

COREはそれを受けて、

- まだ何が分かっていないか
- 何が検証されているか
- 何が矛盾しているか
- 何を次に調べる必要があるか
- どの分類の能力が必要か
- 追加処理が必要か
- 完了条件を満たしたか

を再評価する。

このため、18分類の「知能」は各分類の内部に分断されたものではなく、COREによる状態統合と専門分類による処理能力の循環によって成立する。

### 一つの脳としての責務境界

一つの脳であることは、全分類が同じ処理をすることを意味しない。

各分類は専門責務を維持する。

COREは全体判断と接続を担当し、専門分類はそれぞれの専門能力を担当する。
COREへ専門処理をコピーせず、専門分類へCOREの全体判断をコピーしない。

同じTaskについて複数分類が関係する場合も、同じEvidence、Claim、状態遷移を各分類で独立して複製しない。
必要な分類は既存のCanonical Owner、Canonical Entry、Command、Result、Event、Blackboardを通じて接続する。

これにより、

- 18分類がバラバラに動く
- 同じ判断を複数分類が行う
- 同じ検索やVerificationを複数経路が実行する
- 一つの状態を複数サービスが別々に管理する
- CORE経路と直接経路が同時に同じ処理を行う

という構造を避ける。

### 一つの脳としての開始と終了

18分類全体の業務処理は、原則としてCOREを入口とし、COREの再評価を経由して必要な分類を動かす。

外部から見ると一つのTaskとして開始し、一つの系譜を維持しながら複数分類の処理を必要に応じて行い、最終的にCOREが完了・停止・保留・失敗等の状態を確定する。

専門分類単体の成功は、18分類全体のTask完了を意味しない。

逆に、ある分類が未解決を返しても、それだけで全体失敗とはしない。
COREがその未解決状態をBlackboardへ統合し、別の分類、追加処理、Research、Verification、Execution、Unknown等が必要かを再評価する。

この循環こそが、COREと17専門分類からなる18分類を一つの脳として機能させる基本構造である。

### COREが次の処理を選ぶ

MIKI-AIは、18分類を固定順序で一周する構造ではない。

現在のBlackboard、目的、Evidence、未解決要件、制約、実行結果をCOREが再評価し、その時点で必要な分類だけを選択する。

したがって、

- 全18分類を毎回呼ばない
- 分類同士を固定チェーンにしない
- 次の分類を前の分類が独断で決定しない
- COREを迂回して業務処理を直結させない

ことを基本とする。

全分類を一括確認する処理は、起動監査・整合性監査・手動診断などに限定する。

## CORE

COREは、MIKI-AIの入口、判断、再評価、終了を統括する。

### COREの責務

COREは次を管理する。

- UI、イベント、自律トリガー、外部指示からの正規Task Ingress
- Task ID、Run ID、Request ID、correlation ID、causation ID
- Blackboardの生成、読取り、更新、永続化
- 現在状態から必要な専門分類の選択
- Domain Commandの生成・配送
- Domain Resultの回収・正規化
- Evidence、Claim、未解決要件、エラー、再試行情報の統合
- 実行環境・資源制約の反映
- 結果回収後のBlackboard更新
- 次の処理が必要かどうかの再評価
- 継続、別分類への切替、保存、検証、停止、完了の決定
- pause、resume、cancel、timeout、cycle上限
- 完了条件とfail-closed

COREは専門分類の内部データを直接書き換えない。
専門処理は分類の公開入口へDomain Commandとして依頼する。

### COREの基本ループ

正規の業務処理は次の考え方で動く。

UI / Event / Autonomous Trigger / External Directive
→ Core Task Ingress
→ Core Orchestrator
→ Blackboard
→ COREが必要な分類を選択
→ Domain Command
→ Domain Result + Evidence + unresolvedRequirements
→ Blackboard更新
→ COREが再評価
→ 次の分類 / 保存 / 検証 / 停止 / 完了

ここで「次の分類」は固定された順番ではなく、その時点のBlackboardからCOREが決定する。

## 17専門分類の責務

### autonomy
自律実行、定期実行、バックグラウンド処理、実行予算を担当する。

### capability
利用可能能力、能力不足、部品選択、Capability Gapを担当する。

### conversation
会話入力、意図、照応、否定、訂正、数値・版数、回答候補の合成を担当する。

### data
構造化データ、Schema、テストデータ、決定論モデル情報を担当する。

### execution
計画された処理、検査Runner、実行要求、実行結果を担当する。

### experience
過去事例、今回結果、成功・失敗・修正の経験化を担当する。

### improvement
改善要求、課題選定、候補ライフサイクル、改善Queueを担当する。

### learning
検証済み結果からの学習、信頼度更新、再利用成績を担当する。

### memory
記憶Repository、永続化、検索適格性、隔離・削除遮断を担当する。

### promotion
Validation済み候補の昇格判定、レビュー待ち、定着状態を担当する。

### research
ローカル資料、Web、GitHub、外部AI調査、Evidence取得を担当する。

### safety
秘密情報、禁止操作、端末資源、危険処理、ロールバック可能性を担当する。

### selfAwareness
自己構成、未確認範囲、制約、不足、接続状態を担当する。

### selfDevelopment
対象コード理解、隔離Candidate生成、部品・テンプレート候補を担当する。

### strategy
Blackboardの状態から計画案、優先度、代替案を作る。
最終的な配送先はCOREが決定する。

### unknown
未知分類、Knowledge Gap、再利用可能な過去解決、未解決状態を担当する。

### verification
Evidence、Claim、反証、型、回帰、一般化、永続化、端末検査を担当する。

## 分類間連携

分類間連携は、固定された直結チェーンではなく、COREを中心としたCommand / Result方式を基本とする。

- Eventは発生した事実を表す。
- Commandは一つの分類への実行要求を表す。
- Resultは観測結果、Evidence、未解決要件、エラーを表す。
- BlackboardはTaskの共有状態を保持する。
- COREはResultを受けて状態を再評価する。
- 次の分類はCOREが決定する。

分類が別分類の内部実装を直接操作することは原則として避ける。
既存の直接呼出しは、発見しただけで即削除せず、責務・契約・副作用・Blackboard帰還方法を確認してから整理する。

## 正規責務・接続・重複実装防止基準

MIKI-AIの機能追加・修正では、既存機能を再実装する前に、その責務の正規Ownerと正規Entryを確認する。

### Canonical Owner

各機能には、その機能の正規実装・状態管理・判断責務を担当するCanonical Ownerを一つだけ定める。

同じ判断、検索、検証、永続状態変更、成果物生成を複数のサービスへ独立実装してはならない。

既存サービスがCanonical Ownerである場合、新しいサービスは同じ責務を実装せず、Canonical Ownerへ委譲する。

### Canonical Entry

各業務処理には正規Entryを定める。

UI、Event、Autonomous Trigger、External Directive等の異なる入口が存在しても、同じ業務処理を開始する場合は、可能な限り共通の正規Entryへ集約する。

COREが正規Entryである業務処理について、UI Gatewayや専門分類がCOREを通過した後に同じ業務処理を直接実行してはならない。

### Adapter / Facade

AdapterまたはFacadeは既存Canonical Ownerへの接続を担当する。

Adapter / FacadeにCanonical Ownerと同じ判断ロジック、検索ロジック、Verificationロジック、永続状態変更ロジックを追加しない。

技術差を吸収する必要がある場合も、業務上の正規判断はCanonical Ownerへ委譲する。

### Event Subscriber

Event SubscriberはEventを受け取って必要な再評価・通知・連携を行う。

Event SubscriberがEvent発行元と同じ副作用を独立して再実装してはならない。

特に、Eventによって既に実行された処理をSubscriber側でもう一度直接実行して二重変更する構造を作らない。

永続状態を変更する必要がある場合は、その状態のCanonical Ownerが提供する正規APIへ委譲する。

### COREと専門分類

COREは専門分類の選択、Command配送、Result回収、Blackboard更新、再評価を担当する。

COREに専門分類内部の業務ロジックをコピーしない。

専門分類は自身の責務を担当し、別分類の責務を内部へ取り込まない。

「COREから呼ぶ処理」と「専門分類内部で行う処理」を同じサービスへ二重実装しない。

### 正規責務台帳

重要な業務処理について、次の対応関係を正規基準とする。

| 責務 | Canonical Owner | Canonical Entry | 禁止する重複 |
|---|---|---|---|
| Task受付・統括 | CORE / CoreTaskIngressService | Core Task Ingress | UIやDomainによる独自Orchestration |
| Domain選択・再評価 | CORE / AdaptiveRoutePlanner | CORE再評価 | Domain側の固定次処理選択 |
| Researchオーケストレーション | ResearchService | CORE → Research Command | UI/Unknown等の独自Research実行 |
| Web技術実行 | UnifiedWebResearchService / AutonomousSearchService | ResearchServiceからの委譲 | 別サービスでの第二Web検索基盤 |
| Claim Verification | VerifierService / Verification Domain | CORE → VERIFY_RESEARCH_CLAIMS | Research等への独立Verification実装 |
| Verification通知 | ClaimVerificationEventService | VerifierからのEvent発行 | 別Event経路の重複 |
| Knowledge Gap永続状態 | Knowledge Gap所有サービス | Unknown Knowledge Integration等から正規APIへ委譲 | Research/CORE/Verifierによる直接状態管理 |
| Candidate検証 | CandidateValidationRunnerService等 | 自己改善検証経路 | Candidate生成側への独自検証実装 |
| Promotion判定 | SinglePromotionGateService | 単一Promotion Gate | 複数箇所の独立採用判定 |
| Review ZIP生成 | ReviewZipExportService | レビュー成果物化経路 | 各Candidate生成処理での独自ZIP生成 |
| 外部指示正規化 | ExternalDirectiveIntakeService | External Directive Ingress | 外部指示の各所での独自解釈・直接実行 |

この表は新しい実装を作るための一覧ではなく、既存機能を再利用するための責務境界を示す。

### 新規実装前の必須確認

新しいService、Coordinator、Gateway、Router、Event Subscriber等を追加する前に、少なくとも次を確認する。

1. 同じ目的の既存Serviceが存在しないか
2. その既存ServiceがCanonical Ownerではないか
3. 正規Entryが既に存在しないか
4. 既存のCommand / Result / Event / Blackboard経路を再利用できないか
5. 同じEvidence、Claim、Knowledge Gap、Candidate、状態を別管理しないか
6. 新しいEventを追加することで既存Event処理が二重実行されないか
7. 新しい直接呼出しによってCORE経路を迂回しないか
8. 既存の互換入口を削除する場合、その呼出し元と副作用を確認したか

### 重複が発見された場合の統合原則

同じ責務が複数箇所に存在する場合、新しい実装を追加して解決しない。

まずCanonical Ownerを決定し、既存処理を次のいずれかへ整理する。

- Canonical Ownerへの委譲
- Canonical Entryへの接続
- Adapter / Facadeとしての薄い互換層
- Event / Resultを利用した正規連携
- 不要になった旧実装の安全な削除

削除前には呼出し元、戻り値、Evidence、Claim、永続状態、副作用、Error、Retry、Blackboard帰還を確認する。

### 接続の正本

同じ機能について、直接呼出しとCORE Command、または直接副作用とEvent Subscriberを並行して正規経路として扱わない。

複数の技術的入口が必要な場合でも、最終的な業務処理は一つのCanonical Ownerへ収束させる。

これにより、MIKI-AI自身が将来コードを調査・改善するときも、「既に存在する機能を別名のServiceとして再実装する」「既存Eventへさらに別Eventを接続する」「CORE経路と直接経路を二重に動かす」ことを避ける。

### 二重実装と二重接続の受入条件

新しい実装は、既存のCanonical Ownerと同じ責務を独立して持たないこと。

新しい接続は、既存の正規Event、Command、Result、Blackboard経路と同じ副作用を二重に発生させないこと。

既存機能を利用する場合は、原則として新しいロジックを書くのではなく、既存Canonical OwnerまたはCanonical Entryへ接続する。

正規Owner、正規Entry、接続先、禁止される重複が確認できない状態では、実装を開始せず、先に既存コードを調査して設計を確定する。

## Research

Research分類の正規オーケストレーターはResearchServiceとする。

### ResearchService

ResearchServiceはResearch全体を統合する。

- Knowledge Gapとの接続
- Research Plan / Query Strategy
- Research経路選択
- 複数検索Round
- 検索結果取得
- 結果ページ読取り
- Evidence / Claim登録
- Verification連携
- Knowledge Gapの解決状態
- continuation状態
- Research Outcome

### Web検索層

UnifiedWebResearchServiceはResearchの第二正本ではない。
Web検索技術へのFacadeとして、検索実行、結果ページ取得、設定、統計、低レベルWeb操作を担当する。

AutonomousSearchServiceはProvider探索と結果統合を担当する低レベル実装であり、通常のResearchオーケストレーションを担当しない。

正規Research経路は、

CORE
→ Research分類
→ ResearchService
→ UnifiedWebResearchService
→ AutonomousSearchService
→ Provider

とする。

### Research結果とCORE再評価

Researchの検索結果は、そのまま最終的な真実にはしない。

Researchから返されたResult、Evidence、Claim、Verification結果、unresolvedRequirements、continuation状態をBlackboardへ反映し、COREが次の処理を再評価する。

次のResearch Roundが必要なら、COREがResearch分類を再選択する。
Research内部の安全上限を、探索全体の固定回数制限とは解釈しない。

検索結果はEvidence候補であり、既存のVerification境界を通過した結果だけがKnowledge利用可能状態へ進む。

### Research終端状態と探索十分性

Researchの終端状態は「検索結果が返った」ことだけでは決定しない。

- `EVIDENCE_FOUND` は、必要なResearch ClaimがVerificationを通過し、Knowledge Gapを解決できた状態を表す。
- `INSUFFICIENT_SEARCH` は、現在の探索では必要条件を満たせず、追加探索またはCOREによる別処理が必要な状態を表す。
- `INSUFFICIENT_VERIFICATION` は、探索Coverageが一定条件を満たしても、Claimの検証が完了していない状態を表す。
- `NOT_FOUND_AFTER_COVERAGE` は、要求された探索CoverageをEvidenceとして確認したうえで、なお必要なClaimを解決できなかった場合だけ許可する。
- `NO_RESULT`、`SOURCE_UNAVAILABLE`、`NO_NEW_EVIDENCE`、`LOW_INFORMATION_GAIN`等は、探索結果が得られなかったことや探索継続余地が小さいことを意味するだけで、存在しないことの証明にはならない。

Research Outcomeの優先順位は固定する。`EVIDENCE_FOUND`、`INSUFFICIENT_SEARCH`、`INSUFFICIENT_VERIFICATION`、`NOT_FOUND_AFTER_COVERAGE`の順で状態を確定し、上位の状態を下位の状態へ変換してはならない。特にCoverageを満たしていてもVerification不足なら`NOT_FOUND_AFTER_COVERAGE`にはしない。

`NOT_FOUND_AFTER_COVERAGE`を返すためのCoverageは、検索回数ではなくWeb Research Policyの状態で判定する。独立情報源、一次・公式情報、反証探索、矛盾の有無など、要求された条件をEvidenceとして確認する。

`Web Research Policy`の`targetMode=AUTO`は固定件数へ変換して探索十分性を判定しない。AUTOでは、Research目的、Knowledge Gap、要求されるClaim、現在のEvidence、独立情報源、一次・公式情報、反証探索、矛盾、環境適用性などを基に、現在のResearch状態に必要なCoverage条件を決定する。固定の検索回数や固定の情報源数だけでAUTOの十分性を確定してはならない。

`NO_NEW_EVIDENCE`および`LOW_INFORMATION_GAIN`は、探索による新規情報の増加が確認できないことを示す状態であり、Claimが存在しないことの証明ではない。これらの状態を理由として`NOT_FOUND_AFTER_COVERAGE`へ自動変換してはならない。`NOT_FOUND_AFTER_COVERAGE`は、別途定義されたCoverage条件がEvidenceとして成立している場合に限って使用する。

Search budget、pass数、HTTP timeout、candidate URL数などは安全上限であり、これらを使い切ったこと自体を探索十分性とはみなさない。

Research Resultには、`resolved`、`outcome`、`verification`、`continuationAvailable`、`continuationReason`、`nextQuery`等を保持し、COREはこれらをBlackboard上で再評価する。

COREの完了判定でもResearch Resultの存在だけを完了条件にしない。`resolved=true`、または要求CoverageがEvidenceとして成立した`NOT_FOUND_AFTER_COVERAGE`以外はResearch依存Taskの完了根拠にしてはならない。

### Researchの直接呼出し監査

UI、Unknown、Memory、Capability、Autonomy、Background処理などがResearch業務を要求する場合、原則としてCORE Task Ingressから入り、COREがResearch分類を選択する。

既存の直接Research / Web検索呼出しは、次のいずれかに分類してから整理する。

- CORE経路へ統合すべき業務Research
- Research内部からの正当な利用
- Web技術への低レベル利用
- 診断・検証専用利用
- 互換入口
- 設計上未定義の経路

結果契約や副作用を確認せずに削除・置換しない。

### Research実行境界

COREによる認証・受付と、COREによる業務実行は別物として扱う。

UI Gatewayや専門分類がCORE Task Ingressを呼んだ後、その同じ処理の中でResearchServiceやWeb検索実装を直接実行してはならない。
CORE Task Ingressへの送信だけを行い、実際のResearch実行はCOREがResearch分類へDomain Commandとして配送する。

Unknown分類は未知状態の分類、検索必要性の判定、Knowledge Gap生成などを担当できる。
ただしResearch実行そのものはResearch分類の責務とし、UnknownからResearchService.executeSearch等を直接呼び出さない。

Research UI Gatewayは設定・表示・受付の入口として機能できる。
ただし「COREでauthorizeした後にGateway自身がResearchを実行する」構造はCORE経路とはみなさない。
Research実行要求はCORE Taskとして渡し、Domain ResultをCOREから受け取る。

ResearchService.executeSearch等の既存直接APIは、Research内部、低レベルWeb層、互換入口、診断経路を除き、業務実行入口として外部分類から直接利用しない。
既存直接呼出しを整理するときは、結果契約、Evidence、Claim、continuation、エラー、Blackboard帰還を確認してから移行する。

### 会話からUnknown/ResearchへのCORE経路

Chat UIはUnknown DomainやResearch Domainを直接実行しない。

会話から未知解決が必要な場合は、CORE Task IngressへUSER_REQUESTとして投入する。
COREがBlackboardを基準にUnknownを選択し、Unknown ResultにResearch要求があればCOREが再評価してResearch Domain Commandを配送する。

UIはCORE Taskの完了結果を受け取り、Domain内部サービスの直接実行結果を会話処理の入口として使用しない。

### UnknownからResearchへの要求契約

Unknownが検索の必要性を判定した場合、Unknown自身はResearchを実行しない。

Unknown Domain Resultには、少なくとも次を返す。

- status: RESEARCH_REQUIRED
- researchQuestion: COREがResearchへ渡す検索要求
- unresolvedRequirements: Research実行が必要であることを示す未解決要件

COREはこのResultをBlackboardへ記録し、再評価時にresearchQuestionをResearch Domain Commandのqueryへ変換する。

Research Domain CommandはCOREからResearchへ配送する。
Research結果は再びCOREのBlackboardへ戻し、COREが次のUnknown、Verification、Learning、Conversation等の必要分類を再評価する。

Unknownの「検索が必要」という判定と、Researchの「検索を実行する」という処理を同一処理として扱わない。

### Research探索十分性の追加基準Research探索十分性の追加基準

Researchは「検索APIを呼べたこと」や「一定回数検索したこと」だけで探索完了と判定しない。

探索十分性は、検索量ではなくEvidence Coverageを中心に判断する。

少なくとも次をResearchの進捗として扱う。

- 必要ClaimまたはKnowledge Gapの未解決要件
- 検索観点のCoverage
- 独立した情報源の数と独立性
- 一次情報・公式情報の取得状況
- 反証・制限情報の探索状況
- 現在の実行環境への適用可能性
- 実際の結果ページ本文を読めたか
- Evidence品質
- Claim間の矛盾
- 前回探索からの新規情報量
- 未解決Requirements
- 次の探索で得られる情報価値

検索回数、URL数、ページ数、時間予算は安全上の上限であり、それ自体を「十分探索した」という意味にしない。

Researchは必要に応じて複数の検索観点を使用し、結果が不足していればQuery Revision、別観点、公式情報、反証、現在環境確認などへ展開できる。

1回のResearch呼出しで安全な実行上限を設けても、論理的な探索全体はCOREの再評価によって次のCycleへ継続できる。

Researchが検索を十分に行ったがVerificationが不足している場合と、ResearchそのもののCoverageが不足している場合を区別する。
前者ではVerification等をCOREが選択し、後者ではResearchを再投入できるようにする。

「結果が見つからなかった」と「対象が存在しない」を同一視しない。
CONFIRMED_ABSENCEを使用する場合は、対象に応じた探索Coverage、一次/公式情報、反証探索、時間・環境条件、未解決要件を満たしたことをEvidenceとして残す。

Research Query PlanはCOREの18分類思想と矛盾する固定分類リストを正本として持たない。
Research内のQuery Planningは探索観点を計画する責務であり、次にどの18分類を実行するかを決定する権限はCOREにある。

Researchの安全な終端は「検索した」ではなく、
必要なEvidence Coverageを確認し、Verification境界を通過するか、未解決理由と次に必要な処理をCOREへ返した状態とする。

### Research完了判定とCORE完了条件Research完了判定とCORE完了条件

Research結果が存在することだけを、Research完了またはTask完了の根拠にしない。

Researchの完了状態は、Research結果の存在に加えて、探索十分性または明示された終端条件を満たしていることを必要とする。

- continuationAvailable=true のResearch結果は未完了として扱い、COREは追加探索を再評価する。
- outcome=INSUFFICIENT_SEARCH はCoverage不足として扱い、COREがResearchを再投入できる状態を維持する。
- outcome=INSUFFICIENT_VERIFICATION はResearch結果の存在だけで完了とせず、COREがVerification等の必要な分類を選択する。
- outcome=NOT_FOUND_AFTER_COVERAGE は、対象に必要なCoverage条件を満たしたことがEvidenceとして確認できる場合に限り、探索終端として扱える。
- resolved=true または同等の十分性終端条件を満たさないResearch結果だけでは、Research依存Taskを完了させない。
- COREのTask完了判定は、Research結果の有無ではなく、Researchの状態、Evidence、Verification、未解決要件、continuation状態をBlackboardから再評価して決定する。

これにより「検索結果が返った」ことと「必要な探索が完了した」ことを明確に分離する。

## Verification

ResearchがEvidence Coverageを満たしているが、Required Research ClaimのVerificationが未完了の場合、ResearchはINSUFFICIENT_VERIFICATIONを返し、COREがVerification Domainを選択する。

Verification DomainはResearchServiceを直接呼び出さない。Verificationは指定されたClaimを検証し、ClaimごとのVerificationResult、検証済みかどうか、反証・未解決状態、対象Claim IDs、必要に応じてKnowledge Gapとの関連情報をDomain ResultとしてCOREへ返す。

COREはVerification ResultをBlackboardへ収集し、Research Resultと同一のTask・Correlation・Claim IDsを用いて再評価する。Verificationが必要ClaimをすべてSUPPORTEDまたはDEVICE_VERIFIEDとして確認した場合、COREはそのResearch依存を解決済みとして扱い、同じINSUFFICIENT_VERIFICATIONのResearch Resultだけを根拠にVerificationを再実行しない。

Verificationが未解決または反証を返した場合は、COREがその状態を新しいEvidence・未解決要件として扱い、Research継続、別のVerification、Unknown、Execution、その他の必要な分類を再選択する。「Verificationを一度実行した」こと自体は完了条件ではない。

ResearchとVerificationの間では、Research Coverage不足、Claim検証不足、Claim検証済み、Claim反証、Claim未解決を別状態として保持する。

Knowledge Gapの永続状態を変更する責務はKnowledge Gapの所有境界に置く。COREは専門サービスの内部状態を直接書き換えず、必要な状態更新は既存のDomain Command、Result、Event等の正規経路を使用する。一方、COREのBlackboardには検証済みClaimとResearch依存の解決関係を保持し、永続Knowledge Gap状態と一時的なTask解決状態を混同しない。

Verification Resultには対象Claim IDs、各ClaimのVerification Outcome、全Required Claimが検証済みか、未解決・反証の有無、Research/Knowledge Gapとの関連識別子、Evidence IDsを保持できる契約を用いる。Verifierが実際に評価したEvidenceとの系譜をCOREへ返せることを原則とする。

### Verification結果とKnowledge Gap所有境界

VerificationによるClaim状態の確定と、Knowledge Gapの永続状態更新は同一責務として扱わない。

VerifierはClaimのEvidenceを評価し、Verification Outcomeを確定する。Claim状態がSUPPORTED、DEVICE_VERIFIED、CONTRADICTED等へ変化した場合、その結果はVerification Eventとして後続のKnowledge連携へ通知できる契約を持つ。

Verification Eventを受け取るUnknown側の連携サービスは、対象Unknown、関連Claim、Evidence、Knowledge Gapの関係を再評価する。関連する必要ClaimがすべてSUPPORTEDまたはDEVICE_VERIFIEDとなった場合に限り、Knowledge Gap所有サービスの正規APIを通じてKnowledge GapをRESOLVEDへ進める。

したがって、COREやVerification DomainがKnowledge GapService.markResolved()を直接呼び出して永続状態を変更しない。また、Research結果だけでKnowledge Gapを永続的に解決済みにしない。

正規の責務境界は、

Verification
→ Verification Result / Verification Event
→ Unknown Knowledge Integration
→ Knowledge Gap所有サービス
→ Knowledge Gap状態更新

とする。

VerificationがCONTRADICTEDまたはUNRESOLVEDの場合はKnowledge Gapを解決済みにせず、その結果をCOREのBlackboardへ戻す。COREはEvidence、Claim、未解決要件、既存Research結果を再評価し、Research継続、Unknown、別Verification、Execution等の必要な分類を選択する。

Verification ResultをDomain Command経由で返す場合も、claimIds、各ClaimのOutcome、promoted状態、Evidence IDs、Research/Knowledge Gapとの関連識別子を保持し、Verification Eventによる永続状態連携とCOREによるTask状態の再評価を混同しない。

この境界により、Claimの検証、Unknownの解決状態、Knowledge Gapの永続状態、CORE Taskの完了状態を分離しながら、Research → Verification → CORE再評価 → 必要Domainという18分類の循環を維持する。

### Verification EventとCORE再評価の接続

Verification Resultは、COREのBlackboardへ返すDomain Resultと、Claim状態変更を他分類へ伝えるVerification Eventを、それぞれの目的に応じて扱う。

VerifierがClaimの検証結果によってClaim状態を変更した場合、対応するClaimVerificationEventを正規Event経路へ発行する。Eventには少なくともClaim ID、Verification Outcome、promoted状態、検証時刻等を含め、購読側が対象Claimの最新状態を再取得できるようにする。

Unknown側のVerification Event購読処理は、Eventを受けてUnknownとEvidenceの関係を再評価し、関連Claimが必要条件を満たした場合だけKnowledge Gap所有サービスの正規APIによって永続Knowledge Gapを解決する。

COREが受け取るVerification Domain ResultとVerification Eventによる永続状態更新は同一状態として扱わない。

- Domain Resultは現在のTask、Run、Correlation、Claimに対するCOREの再評価材料
- Verification EventはClaim状態変更を関連Domainへ伝える事実通知
- Unknown Knowledge IntegrationはEventを基にUnknownとKnowledge Gapを再評価
- Knowledge Gap所有サービスが永続Knowledge Gap状態を変更
- CORE BlackboardはTask上のResearch依存解決状態を保持

Eventを発行したことだけをCORE Task完了の証拠にしない。また、CORE Taskが完了したことだけを永続Knowledge Gap解決の証拠にしない。

### Verification再実行の制御

同一Task、同一Research Claim集合、同一Evidence状態に対して、同じVerification Commandを無条件に繰り返してはならない。

ResearchがINSUFFICIENT_VERIFICATIONを返した場合、COREはVerificationを選択できる。
その後のVerification Resultが必要ClaimをすべてSUPPORTEDまたはDEVICE_VERIFIEDとした場合、Research依存を解決済みとして扱い、同じVerificationを再実行しない。

Verification ResultにUNRESOLVEDまたはCONTRADICTEDが含まれる場合、COREはその結果をBlackboardへ記録し、同じClaim集合・同じEvidence状態に対する同一Verificationを自動反復しない。

その場合の次経路は固定しない。COREは最新のEvidence、Claim状態、未解決要件、Research continuation、反証、環境条件、実行可能性等を再評価し、必要に応じてResearch、Unknown、別のVerification、Execution、その他の分類を選択する。

新しいEvidence、Claim変更、Verification条件変更、Research continuation、実行結果などによって検証条件が変化した場合は、新しいOperation Instanceとして再検証できる。

この制御により、Verification不足を理由に同じVerificationだけを無限に繰り返す経路を作らず、COREが結果を材料として次の処理を選択する。

### Verification Eventの発行責務と正規契約

ClaimVerificationEventServiceはVerification結果を他分類へ通知する共通Event経路として扱う。Event購読機構だけを存在させ、VerifierがEventを発行しない状態を正規構成とはしない。

VerifierがClaimの検証結果を確定し、Claim状態を変更した場合は、そのVerification結果に対応するClaimVerificationEventを正規Event経路へ発行する。

Verification Eventの正規情報として、少なくとも以下を保持する。

- claimId
- outcome
- promoted
- verifiedAt

ここでoutcomeはVerificationResultのSUPPORTED、DEVICE_VERIFIED、CONTRADICTED、UNRESOLVED等の結果を表す。Claim Database上のstatusとVerification Outcomeは意味が異なるため、Event受信側が両者を暗黙に同一視しない。

Eventは永続状態そのものではなく、Claim状態変更を関連分類へ伝える通知である。Event購読側は必要に応じてClaim、Evidence、Unknown、Knowledge Gapの現在状態を正規サービスから再取得して判断する。

VerifierのDomain ResultとVerification Eventは同じVerification結果を異なる目的へ伝えるための二つの経路であり、Event発行だけをCORE Task完了の証拠にしたり、Domain ResultだけでKnowledge Gap永続状態を直接変更したりしない。

### Verification Operation Instanceの再実行条件

同一Task、同一Research Claim集合、同一Evidence状態、同一Verification条件のVerification Operation Instanceを、COREが無条件に再実行してはならない。

Verification ResultがSUPPORTEDまたはDEVICE_VERIFIEDの場合は、そのClaim集合についてVerification依存を解決済みとして扱い、同一条件のVerificationを再実行しない。

Verification ResultがUNRESOLVEDまたはCONTRADICTEDの場合も、結果を受け取っただけで同一Verificationを再実行しない。COREは最新のBlackboard状態を再評価し、Research、Unknown、Execution、別条件のVerification等から必要な次処理を選択する。

同一Claimを再Verificationできるのは、少なくとも次のいずれかによって検証条件が変化した場合とする。

- 新しいEvidenceが追加された
- Evidenceの状態が変化した
- Claim状態または反証関係が変化した
- Research continuationによって新しい調査結果が得られた
- Verification条件、freshness条件、環境条件等が変更された
- Executionによる新しい検証Evidenceが生成された

再Verificationを行う場合は、新しいOperation InstanceとしてCORE Blackboard上で識別し、過去のVerification Resultと混同しない。

この識別により、COREは「Verificationが未完了だから再Verificationする」という固定条件ではなく、「前回Verificationから何が変化したため再Verificationが必要なのか」をEvidenceと状態差分から判断する。

### Verification EventとUnknown Integrationの二重処理防止

Verification Eventを受信したUnknown Knowledge IntegrationとCORE Blackboardは、それぞれ異なる責務を持つ。

Unknown Knowledge IntegrationはUnknown、Claim、Evidence、Knowledge Gapの永続的な関係を再評価する。
COREはTask、Run、Correlation、Research依存、未解決要件を再評価する。

同じEventを理由として両者がKnowledge Gapを直接解決してはならない。Knowledge Gapの永続状態変更はKnowledge Gap所有サービスの正規APIに限定する。

また、Verification Eventの購読順序や非同期処理順序を、COREの最終的なDomain選択根拠にしない。COREの再評価はBlackboardに保存された最新のResult、Evidence、Claim状態、未解決要件を正本として行う。

この制御により、Verification不足を理由に同じVerificationだけを無限に繰り返す経路を作らず、COREが結果を材料として次の処理を選択する。

### ResearchからKnowledge解決までの責務境界

ResearchはEvidenceとClaimを生成・収集し、VerificationはClaimの検証を担当する。
VerificationがClaimをSUPPORTEDまたはDEVICE_VERIFIEDへ進めた場合、その状態変更はVerification Eventによって関連するUnknown Knowledge Integrationへ通知できる。

Unknown Knowledge Integrationは関連Claim全体の状態を確認し、必要なClaimがすべて検証済みである場合にKnowledge Gap所有サービスへ状態更新を依頼する。

したがって、ResearchService、Verification Domain、CORE、Unknown Knowledge Integration、Knowledge GapServiceのいずれも、別分類の永続状態を直接横取りして更新しない。

正規の概念経路は、

Research
→ Evidence / Claim
→ Verification
→ Verification Result + Verification Event
→ CORE再評価 / Unknown Knowledge Integration
→ Knowledge Gap所有サービス

とする。

この経路では、検索成功、Verification成功、Unknown解決、Knowledge Gap解決、CORE Task完了をそれぞれ独立した状態として保持する。どれか一つの成功だけを他の状態の成功として自動的に扱わない。

この境界により、Research → Verification → CORE再評価は一方向の固定手順ではなく、COREがVerification結果を材料として次の必要Domainを選択する18分類の循環として成立する。
## 自己改善

自己改善の本番コード自動適用は行わない。
自律処理の安全な終点は、レビュー待ち累積ZIPの作成までとする。

基本経路は、

課題自動発見
→ 自動発見Run
→ 自己改善Ingress
→ 永続Queue
→ CORE / Blackboard / 必要分類
→ 対象ファイルをEvidenceで特定
→ 現行Snapshot固定
→ 隔離Candidate Workspace
→ Candidate SHA固定
→ STATIC / TYPECHECK / REGRESSION / COUNTEREXAMPLE
  / GENERALIZATION / PERSISTENCE / DEVICE
→ Shadow Evaluation
→ 単一Promotion Gate
→ レビュー待ち台帳
→ 累積レビューZIP
→ 外部AI・利用者による確認

自動発見Runと外部AI作業指示Runは、別Run、別Task、別Workspaceとして管理する。
安全パイプラインだけを共通利用する。

自己改善で不足が発生した場合は、Knowledge Gap、Capability Gap、Validation Script不足、実行環境不足などとして必要資産を増やす。
ただし物理的資源不足や安全違反を無視して強行しない。

GitHubへのpushは通常機能として残すが、自己改善ループから本番コードを自動pushしない。

### 自己改善の実装責務分離

ImprovementIntakeRouterServiceはRunの正規化・重複抑制・系譜を担当する。
SelfImprovementIngressServiceは正規Ingress、AutonomousSelfImprovementLoopServiceはQueue、Task、attempt、resource/evidence wait、pause/resume、復旧を担当する。
AutonomousIssueDiscoveryServiceはIssue発見、CandidateCodeGenerationServiceはCandidate生成、IsolatedCandidateWorkspaceServiceはBaseline/Candidate分離、CandidateValidationRunnerServiceとCandidateValidationEvidenceServiceは検証、ShadowEvaluationServiceはShadow評価、SinglePromotionGateServiceは唯一のPromotion判定、CumulativeRevalidationServiceは累積Candidateの再検証、ReviewZipExportServiceはレビュー成果物化、ExternalDirectiveIntakeServiceは外部指示の正規化を担当する。

これらの責務を一つの自己改善Controllerへ統合しない。
Loopは専門判断を持たず、Candidate生成はPromotion判断を持たず、Review ZIP生成は採用判断を持たない。

### 自己改善RunとCORE Task

RunとCORE Taskは同一IDとして扱わない。
Runは改善要求のライフサイクル、TaskはCOREのオーケストレーション単位とする。
runId、taskId、ChangeSetID、sourceId、workspaceId、operationInstanceId等で系譜を接続する。

Adaptive Route Plannerの業務OperationにはoperationInstanceIdとdedupeKeyを持たせる。
同一Operationの誤重複実行は防ぐが、新しい入力・Revision・Attemptが必要な場合は新しいOperation Instanceとして再実行できる。

### 自己改善の完了判定

自己改善Taskでは固定された18分類の全通過を完了条件にしない。
CorePlanRevisionServiceのrequiredOperationsを基準にCoreCompletionGateServiceがPlan、必須Operation、失敗、pending、Domain Error、Reply lineage、persistence receipt、Evidence qualityを確認する。

Candidate生成とReview Package生成は、処理結果が返っただけでは完了としない。
必要なpersistence receiptとlineageが確認できることを完了条件に含める。

### 自己改善の開始源

自己改善はUIだけを入口としない。
AUTONOMOUS_DISCOVERY、EXTERNAL_DIRECTIVE、USER_REQUEST、EXECUTION_FAILURE、REVALIDATIONをRunTypeとして区別する。
実行失敗、検証上の矛盾・未解決、自己改善要求Event等からも正規Ingressへ接続できる。

### 外部指示の境界

ExternalDirectiveIntakeServiceは外部指示を直接実行しない。
directiveId、sourceHash、objective、targetFiles、requirements、prohibitions、invariants、validationRequirements、deliveryRequirements、relatedIssueIdsを保持してから改善Runへ渡す。

外部指示はCOREの判断を置き換えない。
COREがBlackboardとEvidenceを再評価し、必要なResearch、Unknown、Verification、SelfDevelopment等を選択する。

### Candidateからレビューまでの状態境界

Candidate生成成功、Validation成功、Shadow Evaluation成功、Promotion Gate通過、Review ZIP生成、本番採用、本番適用は別状態である。

ReviewZipExportServiceはBaseline/Candidate manifest、hash、Validation、Shadow、Issue、Directive、系譜、未解決事項を保持し、ZIP自体も検証する。
累積PackageではpackageSeriesId、packageRevision、candidateRevisionを保持する。

### 本番反映境界

SinglePromotionGateServiceのallowedはCandidateが検証条件を満たしたことを示すだけで、本番書込み権限を意味しない。
本番反映はレビュー結果、明示的承認、対象SHA、現在Baselineとの一致を確認する別境界とする。
自己改善Loop、Candidate生成、Review ZIP生成から本番コードを直接変更・pushしない。

### 自己改善の現在実装境界

自己改善は、本番コードを直接変更する処理ではなく、改善要求をCOREへ渡し、必要な18分類をCOREが選択し、Candidateを隔離して検証し、レビュー可能な成果物まで到達させる自律処理として扱う。

SelfImprovementIngressServiceは入口を正規化し、ChangeSetID等の系譜情報を付与してAutonomousSelfImprovementLoopServiceへ渡す。

AutonomousSelfImprovementLoopServiceは永続Queue、Task、attempt、pause、resume、resource wait、evidence wait、retry、failure recoveryを管理する。専門的な改善判断をこのLoopへ集約しない。

Queueへ入った自己改善TaskはCoreTaskIngressServiceを経由してCOREへ渡す。COREはBlackboardを基準に必要な分類を選択する。自己改善専用の固定順序を作らない。

AutonomousIssueDiscoveryServiceは、実行失敗、Knowledge Gap、Capability Gap、停滞Task、Domain Disconnect、Claim矛盾、Improvement Debt等から改善候補を発見する。発見したIssueは即コード変更せず、自己改善要求としてCOREへ渡す。

コード変更が必要になった場合はIsolatedCandidateWorkspaceServiceでBaselineとCandidateを分離する。CandidateにはworkspaceId、issueId、runId、writeGuard、Baseline hash、Candidate hash、対象ファイル、Evidenceを紐付ける。

CandidateValidationRunnerService等による検証は、単なるファイル生成確認ではなく、static、typecheck、regression、counterexample、generalization、persistence、device、Evidence整合性等を個別のEvidenceとして残す。ComplexityCostGateも候補評価の一部とする。

ShadowEvaluation後の採用可能性はSinglePromotionGateServiceに集約する。Candidate hash、Validation Evidence、Shadow結果を確認し、別経路から採用可能状態へ進めない。

レビュー成果物はReviewZipExportServiceを正規の成果物化経路とする。複数Candidateを累積する場合はCumulativeRevalidationServiceで同一ファイルの競合と累積状態を検査する。

外部AIや利用者からの作業指示はExternalDirectiveIntakeServiceでDirectiveとして正規化する。指示本文をそのまま実行命令とせず、objective、target files、requirements、prohibitions、invariants、validation requirements、delivery requirements、source hash等を保持する。

自己改善の完了状態は「コードを書いた」「Candidateを作った」「Promotion Gateを通った」「ZIPを作った」のどれか一つではない。検証済みCandidate、系譜、hash、Evidence、レビュー成果物が揃い、レビュー待ちとして固定された時点を自律改善サイクルの安全な終点とする。

本番コードへの自動適用および自己改善ループからの本番pushは行わない。採用、拒否、修正、追加調査はレビュー後の別段階としてCOREへ戻せる。

自己改善の自律性とは、本番コードを勝手に書き換えることではなく、発見、要求化、COREによる分類選択、調査、Candidate生成、検証、再計画、待機、成果物化、レビュー引渡しまでを人間の逐次操作なしで進められることを意味する。

## Evidenceと完了条件

次だけでは完了と判定しない。

- ファイルを作成した
- exportした
- UI文言を変更した
- 固定値でtrue / success / passedを返した
- AIが自己申告した
- ユーザーが一度肯定した
- エラーダイアログが表示されなかった

完了には、少なくとも次の4段階の証拠を必要とする。

EXISTENCE
→ WIRING
→ BEHAVIOR
→ ARTIFACT

安全側ではPARTIALから開始する。
taskId、correlationId、artifactHash、verification Evidence、検証環境、必要な検査結果が揃った場合だけ完了へ進める。

## ユーザー反応

- 良かった部分、誤った部分、訂正された部分を分離する。

## 変更判断

設計と実装の不一致は、次の4種類に分類する。

1. 設計が正しく、コードが誤っている
2. 実装が進展し、設計が古くなっている
3. 設計と実装の双方に問題がある
4. 単純な実装バグである

判断を飛ばしてコードだけを変更しない。

設計が正しい場合はコードを設計へ合わせる。
実装の進展で設計が古くなった場合は、先にこの文書を更新してからコードを変更する。
双方に問題がある場合は、設計を整理してからコードを変更する。

## 自己改善経路の実装監査補足

自己改善UIの「指示からレビューZIPまで」の操作は、単一の関数呼出しだけで完了したとみなしてはならない。COREが複数Cycleを必要とする場合、COREの再計画・分類実行・結果回収・再評価を継続できる状態であることを確認し、UIは実行中・待機中・レビュー待ち・失敗を区別して表示する。

Review Packageが`EXTERNAL_REVIEW_PENDING`である間、Candidateを人間の明示的な採用Decisionなしに本番コードへ適用してはならない。`APPROVE_REVIEWED_CANDIDATE`による適用は、対象Package、Candidate Manifest SHA、Workspace、必要なPersistence Receiptが一致し、かつ対象External Reviewに紐づく人間の明示的な採用Decision（`ACCEPT`）が記録されていることを条件とする。適用が正常完了した後、Review Packageを`ACCEPTED`へ遷移させる。\n\nPromotion適用のトランザクション境界は明示的に分離する。`ACCEPT`は適用完了を意味せず、Review Packageは`EXTERNAL_REVIEW_PENDING`のまま適用処理へ進む。Self Code SpaceへのCandidate反映、Candidate Commit Transactionの確定、Review Packageの`ACCEPTED`遷移は同一の成功条件として扱い、途中で失敗した場合に変更済みSelf Code Spaceだけが残る状態を正常完了として扱わない。`candidateCommitTransactionService`のTransaction記録だけではSelf Code Spaceへの実変更完了を証明しない。`ACCEPTED`は対象Candidateの実適用、Transaction、Persistence Receipt、Manifest/Revision整合性がすべて確認された後だけ設定する。GitHubへのPUSHはさらに別の明示的な境界とし、自己改善Loopから自動実行しない。

外部指示から開始した自己改善では、directiveId、sourceHash、要求・禁止事項・不変条件・検証条件・納品条件・関連IssueをCORE Task、Improvement Run、Candidate、Validation、Review Packageの系譜で追跡可能にする。途中の分類結果や再計画によってDirectiveの識別情報を失ってはならない。

## Living Specificationとしての維持

この文書は作業履歴ではなく、現在有効な設計・制約・受入条件だけを保持する。

個別の実装作業、P番号、版番号、修正ログを逐次追加しない。

設計変更時は、現行コードと機械検証を調査し、設計と実装の差を分類する。
変更後は必ずコードと機械検証を再確認し、その結果をこの文書と照合する。

設計・コード・機械検証の三者に矛盾が残っている状態を、実装完了とは扱わない。


## 自己改善指示書からレビューZIPまでの完了経路

自己改善は、指示書を受け取ったことや候補コードを生成したことだけでは完了としない。指示内容をCOREが受け取り、必要な専門分類を動的に選択し、結果をCOREへ戻しながら必要な処理を継続し、最終的に人間が確認できるレビューZIPを生成するまでを一連の自己改善経路として扱う。

### 指示書の受け取り

指示書は実行コマンド列として直接実行せず、自己改善の目的と制約を持つ入力情報としてCOREへ渡す。

指示書から、可能な限り以下を保持する。

- directiveId
- directiveHash
- objective
- target
- requirements
- prohibitions
- invariants
- validationRequirements
- deliveryRequirements
- relatedIssueIds

指示書の識別情報と内容は、自己改善処理の追跡対象として保持する。

### COREによる自己改善処理

COREは指示内容、現在の状態、既存コード、証拠、不足要件、制約、直前の分類結果を確認し、次に必要な分類を判断する。

18分類を固定順序で実行してはならない。必要な分類だけを選択し、分類から返された結果をCOREが再評価して、次の処理を決定する。

必要な情報、能力、検証条件が不足している場合は、無理に候補生成や完了へ進めず、COREが追加調査、追加検証、再計画、待機または失敗として扱う。

### コード変更候補と検証

コード変更候補を生成しただけでは自己改善成功とはしない。

候補について、目的、対象、要求、禁止事項、不変条件、検証条件との整合性を確認し、必要なテスト・検証・証拠を取得する。

検証に必要な条件が満たされていない場合、成功として扱わない。

### レビュー成果物

検証を通過した変更候補は、レビューに必要な情報を含むReview Packageとしてまとめる。

Review Packageには、少なくとも変更対象、変更内容、検証結果、関連する証拠、未解決事項、指示書との対応関係を追跡できる情報を保持する。

Review PackageからレビューZIPを生成し、ZIPの内容と整合性を検証する。

### 人間による確認

レビューZIPの生成は、本番コードへの自動適用を意味しない。

自己改善処理はレビューZIPを人間へ渡せる状態で停止し、人間による確認・承認を経ずに本番コードへ直接適用したり、自己判断でGitへPUSHしたりしてはならない。

レビューで修正が必要になった場合は、その結果をCOREへ戻し、COREが再計画して必要な分類を再選択する。

### 完了条件

自己改善の完了とは、少なくとも以下が追跡可能な状態をいう。

1. 指示書の識別情報が保持されている
2. CORE Taskと自己改善処理の対応関係が保持されている
3. COREが必要な分類を動的に選択している
4. 分類の結果がCOREへ戻されている
5. 変更候補が生成されている
6. 必要な検証結果と証拠が記録されている
7. Review Packageが生成されている
8. レビューZIPが生成されている
9. ZIPの内容と整合性が確認されている
10. 人間による確認待ちとして扱われている
11. 本番への自動適用が行われていない


## Galaxy S25専用UI受入基準

UI変更はGalaxy S25実機での利用を基準に判定する。

- 主要画面で意図しない横方向の画面はみ出しがない
- Header、本文、固定操作、下部ナビゲーションが連続して潰れた表示にならない
- 長い文字列によって隣接する操作要素が押し潰されない
- キーボード表示中も入力欄と送信・確定等の主要操作を利用できる
- Safe Area内に主要操作を配置する

CODE ComponentをCandidate化し、既存ComponentRegistryへ接続する。

そのため、単なるCatalog存在だけではmaterializationされず、
実際のConstruction要求に必要な部品だけが遅延接続される。

再監査後も解決できない不足だけを既存Construction Gap
→ Unknown / Research経路へ返す。

`buildConstructionGraph()` 自体には生成・登録副作用を追加しない。
Graphは既にmaterializeされたRegistry接続済みCODE Componentだけを
実行可能なConstruction Componentとして扱う。

`storeCandidates()`、Research更新、Verification更新、
Lifecycle更新、Usage更新はBuilt-in Catalogを
Persistent Storageへ丸ごと書き戻さない。

新しいCatalog管理Service、第二のGenerator、
第二のConstruction Graph、19番目の分類は追加しない。
