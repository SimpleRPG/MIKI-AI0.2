第0章: 基本方針・実行環境の確定 (実機運用アーキテクチャ)
======================================================================

0.1 設計の最優先哲学 (不変の原則)
1. 重みを変えずに賢くする:
   最優先目標である「日常的な自然な日本語会話の継続」は、モデルの重みを一切
   書き換えずに、「会話状態管理」「多層記憶」「回答骨格」「プロンプト構造」
   だけで到達する。LoRA等のファインチューニングは、検索・記憶・回答骨格が
   明確に頭打ちになった場合の最終手段(予備手段)とする。
2. 無関係な記憶は注入しない:
   記憶は常時全量をモデルへ渡さない。質問の種類を分類し、必要な場合のみ動的想起して渡す。
3. 安全側に倒す・データを壊さない:
   壊れたデータは推測復元せず安全なデフォルト値へフォールバックする。
   アプリ終了時やサスペンド時は即座に永続化する。

0.2 実行環境の確定仕様 (2026年9月実測ベース)
- APK (MikiAI):
  司令塔・UI・記憶・状態管理・スキル・自己改善ロジックを担当。
- Termux推論サーバー:
  llama-swap (ポート8080/プロキシ) ＋ llama-server (ポート8081/実際の推論) がメインエンジン。
  ※CPUモード(定型文フォールバック)およびWebGPUモード(ブラウザ内WebLLM)は廃止予定。
  Termux + llama-swap 経路を単一の標準経路とする。
- モデル共有ストレージ:
  ~/storage/downloads/gguf-models/ (Android標準の「ダウンロード/gguf-models」フォルダ)。
  アプリとTermuxが同一のGGUFファイルを共有参照する。
- 量子化と実効コンテキスト長:
  全モデル Q4_K_M 量子化 (1.5B / 3B)。
  KVキャッシュ設定: -ctk q8_0 -ctv q8_0 (K/Vともに8bit量子化) ＋ -fa on (Flash Attention有効)。
  f16比でおよそ半分のメモリ消費で32768コンテキストを現実的に展開可能。
- ポートの住み分け:
  ポート 8080: MIKI-AI バックエンドAPIサーバー (GitHubプッシュ/プル、システムAPI、Expressログ等)
  ポート 8081: 外部LLM推論 (llama-server / llama-swap)

第1章: 最上位目的と開発フェーズ
======================================================================

1.1 最上位目的
Galaxy S25単体において、常時インターネット接続に依存せず、日常のパートナーとして
自然に対話・思考・作業支援を行える自律型ローカルAIを確立する。

1.2 開発フェーズ
- フェーズ1: 自然な会話AI (最優先)
  短い質問への自然な応答、詳しい相談への適切な長さ、話題と目的の維持、
  ユーザー訂正の即時反映、矛盾修復、不要な記憶注入の抑止。
- フェーズ2: 詳細推論AI
  目的・条件・例外の分離、問題の小さな単位への分解、反例確認、
  未解決事項と確定事項の分離、回答骨格の再利用。
- フェーズ3: コード理解AI
  構文識別、役割・副作用・例外条件の抽出、呼出グラフ・依存関係解析、影響範囲の日本語説明。
- フェーズ4: コード設計支援AI
  抽象要件からの決定表作成、プロシージャ構成案、テスト仕様作成、外部Copilot用詳細指示書。
- フェーズ5: コード生成支援 (必要時のみ)
  会社固有情報を含まない完全合成コードの生成と静的構文検査。

第2章: 完全統合型・多層記憶システム仕様 (8層構造＋動的制御)
======================================================================

既存構想の7層モデルと先行実装を統合した、全8層の完全記憶階層構造:

┌─────────────────────────────────────────────────────────────┐
│ ① 直近体験バッファ (Episodic Buffer / 追記専用) 【実装済み】   │
│   圧縮されない表層。忘却曲線(熱量)で「今いちばん熱い体験」が選ばれ、 │
│   毎ターン注入。温度が上がるのは「実際に使ったと申告した分」のみ。      │
│   ※読んだだけで温まる設計を排除し、凍結アトラクタ(居座り)を防止。     │
└─────────────────────────────────────────────────────────────┘
                               ↓ 一定往復ごとに沈降
┌─────────────────────────────────────────────────────────────┐
│ ② 短期記憶 (会話履歴 / Short-Term Context) 【実装済み】        │
│   直近数往復の原文、現在の質問、回答設計。コード片は必ず保護。        │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ③ 中期記憶 (Working Agenda) 【未実装・新設】                 │
│   進行中の話題、未解決事項、直近の決定事項。エピソード記憶との混在を解消。  │
│   自発思考モード(第9章)が優先的に宿題として拾い上げる対象。         │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ④ エピソード記憶 (Episodic Memory) 【実装済み】               │
│   「いつ・何があったか」の時系列記録。意味(ベクトル)＋リンクで検索。 │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑤ 統合記憶 (Semantic Core / 人格の骨格) 【実装済み】           │
│   長期記憶・毎ターン常駐注入。差分適用で部分更新。長期方針と設計原則。   │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑥ 構造記憶 (Structural Memory) 【新設】                      │
│   シンボル名、関数、依存関係、ファイル、ハッシュ等の機械抽出情報。       │
│   コード読解時、エピソード記憶を経由せず直接グラフ整合性を検証する。    │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑦ 手続き記憶 (Procedural Memory / スキル) 【新設】            │
│   「どう調べ、どうツールを使い、どう検証したか」の成功手順。           │
│   成功パターンを再利用可能スキルとして保存し、few-shot事例として注入。  │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑧ メタ記憶 (Meta-Memory) 【新設】                           │
│   「どの記憶をどう組み合わせて使うか」。想起比率(リンク:タグ)を      │
│   固定(2:1)から状況適応型へ動的調整する学習層。                    │
└─────────────────────────────────────────────────────────────┘

2.2 記憶のメタデータと「感情価 (質)」
すべてのエピソード記憶は以下のメタデータを保持する:
- id, source, createdAt, status (ACTIVE / SUPERSEDED / REJECTED / EXPIRED / UNVERIFIED / APPROVED)
- replaced_by: 置換先記憶ID (矛盾防止)
- heat: 利用頻度に基づく温度
- 感情価 (質): useful_count (役立った回数) と confusion_count (混乱を招いた・訂正された回数)。
  想起後のターンでユーザーからの訂正が起きなかった場合を正のシグナルとして蓄積し、
  単に頻出するだけの記憶ではなく「質の高い記憶」を優先想起する。

第3章: 想起パイプライン・説明可能性・記憶汚染防止
======================================================================

3.1 想起の組み立て経路
1. 種(シード)の抽出: 現在の入力文(複数サブクエリに分割) ＋ 直近体験バッファの熱い体験。
2. ベクトル検索: 起点記憶(少数の足場)のみを取得 (※起点はそのまま提示しない)。
3. リンク展開 & タグ引き: 相互参照リンク(深さ1〜3) ＋ 多軸タグ照合(分類/重要度/文脈/状態)。
4. 構造記憶検索 (並列): コード関連の文脈では構造記憶(第2章⑥)を同時に並列照合。
5. 記憶を使わない判断: 挨拶、計算、単純変換では MEMORY_NONE ルートを選択し、余計な長期記憶を注入しない。

3.2 矛盾する記憶の同時想起と置換トラッキング
- 訂正された古い記憶は物理削除せず SUPERSEDED (置換済み)とし、replaced_by に新IDを記録。
- 想起時に競合・矛盾ペアが検出された場合:
  両方を注入しつつ「※前提が更新されている可能性があります」と注記。
  予算計算上、矛盾ペアは「1.5〜2枠相当」として申告し、タグ引き枠を自動的に譲歩。

3.3 エラー応答の記憶汚染防止
- サーバー未起動やエラー、診断メッセージなどの失敗発話には isDiagnostic: true を付与。
- 直近体験バッファへの沈降をスキップし、さらにコンテキストトークン消費の実績値から除外して、
  無用な圧縮発火や学習バイアスを防ぐ。

3.4 ユーザー明示的削除の2段階反映
ユーザーから「忘れて」「消して」と要求された場合:
1. 第1段階 (即時ランタイム): 対象記憶IDを「注入禁止ブラックリスト」に即時追加。
   次のターンでの誤注入を100%防止。
2. 第2段階 (台帳永続化): イベントソーシング台帳でアーカイブ／無効化イベントを安全にコミット。

3.5 統合診断ログ (説明可能性)
想起とコンテキスト消費を単一レコードに記録し、回答の乱れの原因
(記憶の選択ミスか、コンテキスト圧縮による忘却か)を即座に特定できるようにする:
{
  "turn_id": "turn_1234",
  "recall": {
    "vector_seeds": ["MEM-010"],
    "link_expanded": ["MEM-012", "MEM-015"],
    "tag_matched": ["MEM-003"],
    "ratio_used": "2:1"
  },
  "context": {
    "estimated_tokens_before": 2450,
    "live_nctx": 32768,
    "compression_triggered": false,
    "budget_breakdown": {
      "persona": 280,
      "memory": 620,
      "history": 1550,
      "headroom": 512
    }
  },
  "cache": {
    "cache_hit_tokens": 1820,
    "prompt_processing_ms": 142
  }
}

第4章: コンテキスト長自動調整エンジン (3層防御モデル)
======================================================================

llama.cpp は n_ctx で指定したKVキャッシュを一括確保するため、
「ロード時の確保量」と「ターン毎の配分」を分離した3層構造で制御する。

┌────────────────────────────────────────────────────────┐
│ A層: ロード時 nCtx ティア選定 (4096 / 8192 / 16384 / 32768) │
│   端末ベンチマーク・常駐モデル数・KVキャッシュ量子化(q8_0)から選定 │
└────────────────────────────────────────────────────────┘
        ↓ モデル再ロード時のみ更新 (低頻度)
┌────────────────────────────────────────────────────────┐
│ B層: ターン単位の予算配分 (動的 Context Compression)    │
│   live_budget = nCtx - maxTokens(512) - 安全マージン     │
│   優先度順に配分: ①統合記憶 → ②熱い体験 → ③想起記憶 → ④会話履歴 │
└────────────────────────────────────────────────────────┘
        ↓ 端末急変時のみ介入 (即座・再ロード不要)
┌────────────────────────────────────────────────────────┐
│ C層: 端末状態によるセーフティ縮退                       │
│   thermalState=hot/critical 時、live_budget を 50〜70%に絞る │
│   バッテリー低下時はリンク展開深さを 3 → 1 へ縮小してCPU保護     │
└────────────────────────────────────────────────────────┘

- maxContextTokens の実効化:
  src/utils/contextCompression.ts 内で未使用だった maxContextTokens を
  live_budget と完全に結びつけ、固定1200トークン閾値を動的計算へ改修。
- recentTurnsToKeep の伸縮:
  雑談(記憶消費小)時は直近ターンを最大8往復保持し、重厚なタスク時は4往復まで安全に縮小。

第5章: プロンプトキャッシュ最適化と高速化戦略
======================================================================

5.1 実測課題: アイドル死によるKVキャッシュ蒸発
実測ログより、同一リクエストでも2回目の cached_tokens が 0 となり、
プロンプト処理に76秒を要していた。これは llama-swap の ttl: 300 (5分)により
プロセスが終了し、KVキャッシュが毎回破棄されていたことが原因である。

5.2 改善仕様
1. 可変TTL (動的キープアライブ):
   通常対話時: ttl: 1800 (30分)へ延長し、人間の会話ペースでのKVキャッシュを保持。
   バッテリー低下時／端末高温時: ttl: 300 に戻し、メモリと電力を早期開放。
2. プロンプト順序の「不変プレフィックス」原則:
   llama.cppのキャッシュは先頭からのバイト完全一致が条件。
   配置順: [統合記憶・システムペルソナ(完全固定)] → [主要ツール定義] → [想起された記憶] → [直近体験バッファ] → [会話履歴]
   毎ターン変わる想起記憶を先頭に置かず、固定の人格・原則を先頭に置くことで、
   キャッシュヒット率を劇的に最大化する。
3. cache_prompt: true の明示送信: リクエストペイロードに明示付与。

第6章: Termux × llama-swap 運用・障害対策・実務ハンドブック
======================================================================

6.1 ディレクトリ構成と設定
- モデル格納先: ~/storage/downloads/gguf-models/
- 自動設定生成スクリプト: ~/sync-gguf-config.sh
  .part, .crdownload 等の書き込み中ファイルを自動除外。
  ~/llama-swap-config.yaml を自動更新 (--watch-config でホットリロード)。

6.2 Android / One UI バックグラウンド常駐4大必須設定
1. Termux内で termux-wake-lock を実行 (CPUスリープ防止)。
2. Android設定 → アプリ → Termux → バッテリー → 「制限なし」。
3. デバイスケア → バッテリー → バックグラウンド使用制限 → 「スリープ状態にしないアプリ」にTermuxを追加。
4. 「未使用アプリを自動停止」をオフ。

6.3 典型トラブルシューティング
- 症状1: couldn't bind HTTP server socket, port: 8080
  原因: MIKI-AI バックエンドサーバー (GitHub連携・Node API)がすでに8080を使用中。
  対策: LLM推論サーバーは必ず --port 8081 で起動し、アプリ側の「外部LLM」設定も http://127.0.0.1:8081 とする。
- 症状2: failed to open GGUF file (No such file or directory)
  原因: カレントディレクトリにファイルがない。
  対策: ~/models/ ではなく共有フォルダ ~/storage/downloads/gguf-models/Qwen2.5-1.5B-Instruct-Q4_K_M.gguf をフルパスで指定。
- 症状3: 外部ローカルLLM接続失敗 (400 Bad Request / 6029 tokens exceed 2048)
  原因: システムプロンプト (記憶＋履歴)が CTX_SIZE=2048 を超過。
  対策: CTX_SIZE=32768 ＋ -ctk q8_0 -ctv q8_0 -fa on で起動。


======================================================================
第7章: 会話状態管理・回答骨格・思考節約機構
======================================================================

7.1 会話の三段階分離
1. 会話理解: 話題、最上位目的、真の意図、訂正の有無、話題転換の有無を判定。
2. 回答設計: 直接回答、理由、注意点、省くべき事項、期待回答長 (短文/標準/詳細)を設計。
3. 日本語化: 結論先行、冗長な前置きの排除、重複削除、自然な語気調整。

7.2 回答骨格 (Answer Skeleton) による思考節約
既知の対話状況(例: 前提の訂正、矛盾の指摘、長すぎる回答の是正)では、
小型モデルにゼロから考えさせず、保存済みの骨格手順を適用する:
pattern_id: PATTERN-CORRECTION-01
situation: 以前の前提が明示的に訂正された
response_plan:
  1. 訂正を認識する
  2. 古い前提を無効化する
  3. 影響する結論を洗い出す
  4. 新しい条件で再判断する
  5. 修正後の結論を先に答える
avoid:
  - 古い前提を残す
  - 謝罪だけで終わる
  - 前と同じ説明を繰り返す
reuse_mode: PLAN_ONLY


======================================================================
第8章: 外部教師API・無料予算動的配分・優先度付き教材キュー
======================================================================

8.1 外部教師の役割と原則
- 外部教師 (Gemini、Groq、Cloudflare等)は常用会話には使わず、
  「回答批評」「模範教材作成」「反例生成」「評価規則作成」に限定。
- 外部教師がダウンしていても、端末ローカルLLM単体で常用会話が100%継続できることを必須とする。

8.2 教材要求キューの優先度スコア計算式 (実装検証済み)
teacherRequestService.ts の calculateQueuePriority() にて実装済み:

Priority = Σ(加点) - Σ(減点)

加点:
- ユーザーからの明確な訂正: +30
- 以前の説明との矛盾: +20
- 質問の意図逸脱: +20
- 古い前提の使用: +15
- 複数条件の脱落: +15
- 同種失敗の反復: +5 × (frequency - 1) (上限 +25)
- 日本語の不自然さ: +10
- 不適切な回答長: +10

減点:
- 実用効果の検証不能: -15
- 単なる語尾の違い: -20
- 既存教材との重複: -30
- 端末モデルが既に安定正解: -30

足切り:
合計 <= 0 の要求はキューに追加せず即座に却下。未処理キューはスコア降順でソート処理。

第13章: 自律型Web検索＆能動学習エンジン (オンデマンド調査 ＆ 非会話時自律学習ループ)
======================================================================

13.1 概要と設計思想
AI「みき」がローカルモデルの固定された重みや限られた静的コンテキストにとどまらず、
常に最新の知識・仕様・外部世界と繋がり続けるための能動的学習（Active Learning）アーキテクチャ。
以下の2大シナリオを単一のナレッジ定着パイプラインで統合する。
1. 会話中オンデマンド自律検索: 会話の文脈で最新情報・仕様・事実確認が必要と判断された瞬間に、
   モデルの推論に先立って自動でWeb検索を実行し、回答品質を飛躍させると同時に記憶へ即時定着。
2. 非会話時（アイドル＆深い睡眠サイクル）の自発的Web学習: ユーザーと会話していない間に、
   中期記憶（Working Agenda）に残された宿題や能力不足ギャップを自発的に検索・調査し、
   長期記憶や合成教材に還元して次回の会話で「調べておいたよ！」と自発報告できる状態を作る。

13.2 会話中オンデマンド自律Web検索パイプライン
1. 必要性・検索意図の高精度検知 (detectNeedForSearch):
   - 明示的指示検知: 「調べて」「検索して」「ググって」「リサーチして」等を検知し、余計な依頼語句を除去した純粋な検索キーワードを抽出。
   - 最新トレンド・時事情報検知: 「最新」「最近」「今年」「2025年」「2026年」「アップデート」等の時間依存トピックを検知。
   - 技術仕様・公式ドキュメント検知: 「仕様」「API」「引数」「文法」「構文」「ライブラリ」等の技術調査要求を検知。
   - 定義・事実確認検知: 「〜って何？」「〜とは？」等の未知語照会を検知。
2. ハイブリッド検索エンジン & 堅牢フェイルオーバー:
   - 第1層 (バックエンドAPI): /api/search エンドポイント経由での Wikipedia API ＋ DuckDuckGo による高精度・構造化検索、Gemini要約合成。
   - 第2層 (フロント直接フェイルオーバー): バックエンド未接続時はクライアントから直接 Wikipedia API (CORS origin=*) へ接続。
   - 第3層 (ローカルフォールバック): 完全オフライン時もローカル知識ベースから安全に応答。
3. 会話コンテキストとUIへの連結:
   - ツール自動実行結果 (tool_web_search) としてプロンプトにソースと要約を事前注入。
   - チャット画面のアシスタント発言直下に「🌐 13章 自律Web検索学習カード」を展開し、調査結果・要約・参照リンク・定着ステータスを可視化。

13.3 非会話時（アイドル＆WorkManager深い睡眠時）の自律Web学習ループ
1. 調査課題の自動選定:
   - 中期記憶 (Working Agenda) からステータスが pending の宿題（homework）を抽出。
   - 宿題がない場合は能力ギャップレジストリ (Capability Gaps) から未解決の弱点課題を抽出。
2. 自律調査の実行 (performIdleAutonomousLearning):
   - 課題トピックと未解決疑問点から自律検索クエリを生成し、Webから最新情報を収集。
   - 調査完了後、Working Agendaの宿題を「自律Web検索学習により解決」として更新・合意を保存。
3. システムログ・進捗記録:
   - WorkManager のバックグラウンド実行ログに自律Web学習の成果を記録。

13.4 他機能との相互連結 (Cross-Feature Integration)
1. 第2章 多層記憶システム (Long-term Memory) との連結:
   - 抽出した要点・知見を意味記憶 (Semantic Memory) に自動格納 (scope: 'global', confidence: 0.9, tags: ['web_search', 'autonomous_learning'])。
   - 将来の会話時にベクトル検索およびタグ引きで自然に想起可能にする。
2. 第8章・第9章 合成データセット (Synthetic Data) との連結:
   - 検索で獲得した知識を「Q&Aペア」に教材化し、syntheticDataService へ追加。将来のLoRA学習や蒸留、回帰テストの教材として還元。

   - backgroundWorkerService の自律サイクル (Step 6.9) に組み込み、端末スリープ中・深夜充電中に自動で自己研鑽を実行。
4. ツール管理モジュール (:feature:tools) との連結:
   - tool_web_search として登録され、プロンプト検出・手動実行・ワークフロー合成（第5段階）からシームレスに呼び出し可能。
5. 自己改善研究所 UI との連結:

第14章: 実埋め込み同期プロトコル & 感情価動的フィードバック改善仕様 (Master v5.1)
======================================================================

14.1 概要と背景（仕様改善の目的）
従来の「8次元ドメイン概念疎ベクトル」は、サーバー未起動時や低負荷環境でも安全に動作する優れた
軽量フォールバックであったが、細微な文脈の違い（例: Canvasゲーム設計の特定APIとVBAコードの対比等）
における意味類似度の分離能に限界があった。
Master v5.1 では、Termuxローカルの llama-server (ポート8081) や Ollama 等の実埋め込みAPIから
高次元ベクトル（768〜4096次元）を取得し、多層検索パイプラインへ統合する「実埋め込み同期プロトコル」と、
ユーザーとの会話から記憶の有用性・混乱を自動判定する「感情価動的フィードバックループ」を正式仕様として策定する。

14.2 実埋め込み同期プロトコル (Embedding Synchronization Protocol)
1. エンドポイントの自動ネゴシエーションと二重フェイルオーバー:
   - 第1候補: 外部ローカルLLM (http://127.0.0.1:8081/v1/embeddings - OpenAI互換)
   - 第2候補: Ollama等 (http://127.0.0.1:11434/api/embeddings)
   - 第3候補 (完全フォールバック): 8次元ドメイン概念疎ベクトル (計算コストゼロ・完全オフライン)
   ※ 外部サーバーが未起動またはエラーを返した場合、1.5秒のタイムアウトで即座に8次元疎ベクトルへ
   フェイルオーバーし、アプリのUIや推論パイプラインを1ミリ秒たりともブロックしない。
2. モデルIDトラッキングと次元不一致の自動回復 (設計思想改善案 ①):
   - ベクトル生成時に使用したモデル名・次元数を記憶メタデータ内に追跡（embeddingModelId / embeddingDimension）。
   - ユーザーがTermux側で推論モデルを切り替えた際、検索クエリと記憶の次元数が一致しない場合は、
     自動で8次元フォールバックに切り替え、バックグラウンドで全記憶の段階的一括再計算をスケジュールする。
3. Galaxy S25 サーマルスロットリング保護 (バッチ＆スロットル制御):
   - 全記憶の一括埋め込み生成時、一度に大量の同時リクエストを投げず、4〜8件単位のバッチ処理と
     50msのクールダウンを挟むことで、スマートフォンの発熱およびllama-serverのOOMクラッシュを防止する。
4. 新規記憶の非同期自動埋め込み:
   - 会話中の自動記憶抽出（autoExtractMemory）やユーザーの手動教育（handleQuickTeach）によって
     新規記憶が生成された瞬間、UI応答を待たせることなくバックグラウンドで非同期に実埋め込みを付与する。

14.3 感情価（質）の動的自動フィードバックループ (Emotional Valence Feedback Loop)
1. ターン間自動フィードバック検知:
   - 直前ターンで使用された記憶群のID（lastTurnUsedMemoryIds）をRefで常時追跡する。
   - ユーザーの次ターンの発言から「訂正・否定・不満シグナル」（例:「違う」「そうじゃない」「直して」
     「間違ってる」「動かない」「バグ」「変だ」等）を検知した場合:
     * 当該記憶の confusion_count (confusionCount) を +1 インクリメント。
     * 熱量 (heat) を 0.7 倍に減衰（興奮冷却）。
     * ログに [感情価更新: CONFUSION] を出力し、ストレージへ即時永続化。
   - 通常の会話進行・受容・感謝シグナル（「ありがとう」「了解」「いいね」「次進めて」等）の場合:
     * 当該記憶の useful_count (usefulCount) を +1 インクリメント。
     * 熱量 (heat) を +0.1 加算（最大 1.0）。
     * ログに [感情価更新: USEFUL] を出力し、ストレージへ即時永続化。
2. 7段階検索パイプライン Step 6 (再順位付け) への直接連動:
   - スコア計算式: score += useful_count * 1.5 - confusion_count * 3.0 + heat * 4.0
   - 一度でもユーザーから誤りを指摘された記憶は大きなペナルティ（-3.0点/回）を受け、
     誤った前提のまま再度回答を生成する「ハルシネーションの固執」を即座に遮断する。
3. 自動記憶淘汰・隔離判定 (設計思想改善案 ②):
   - confusion_count >= 3 かつ useful_count == 0 の記憶は、自動的に「隔離 (quarantine)」
     または「破棄候補 (discard_candidate)」へ移行し、プロンプトへの注入候補から自動隔離する。
   - useful_count >= 5 かつ confusion_count == 0 の実績ある記憶は、ユーザーへの確認を経て
     「長期記憶 (確定設計原則・一般ルール)」へ自動昇格推奨を提示する。

14.4 UI可視化と手動介入権限
1. MemoryModal 長期記憶タブでの実埋め込みパネル:
   - 埋め込みAPIの接続状況（接続中/未接続）、埋め込み済み記憶数、カバー率、次元数をリアルタイム表示。
   - 「実埋め込みを一括同期」ボタンにより、未生成の記憶に対していつでも一括生成を実行可能。
2. 記憶アイテム一覧でのバッジ表示:
   - 実埋め込みベクトル保有バッジ（例: 768d）。
   - 感情価バッジ（+役立ち回数 / -混乱回数 / 🔥熱量）。
   - 手動 👍 / 👎 フィードバックボタン操作時も、useful_count / confusion_count / heat が完全連動。

第15章 置換関係追跡・2段階削除反映・統合診断ログプロトコル (Master v5.2 追加仕様)
======================================================================

15.1 概要と目的
本章では、第3章（記憶管理と更新原則）および第4章（コンテキスト長自動調整）で定義された原則を完全具現化し、ユーザーとの対話の中で発生する「前提の訂正・上書き」「記憶の明示的削除」「推論と想起プロセスの説明可能性（透明性）」を担保する。

15.2 置換関係の自動追跡プロトコル (Superseded Memory Replacement)
1. 訂正・上書き意図の自然言語検知:
   - ユーザーの発言から「〜じゃなくて〇〇」「〜ではなく〇〇」「〇〇に変更」「〇〇に上書き」等の上書き意図を自動解析。
   - 直前ターンで使用された記憶、または関連する古い記憶（oldMemoryId）を特定。
2. 破壊的削除の禁止と置換リンク生成:
   - 古い記憶は物理削除せず、以下のメタデータを付与して SUPERSEDED 状態へ移行:
     * `active: false`
     * `lifecycleStatus: 'SUPERSEDED'`
     * `replacedBy: newMemoryId`
     * `replacementReason: string`
     * `supersededAt: timestamp`
   - 新しい記憶（newMemory）を作成し、以下を付与:
     * `supersededFrom: oldMemoryId`
     * `active: true`
     * `approved: true`
     * `lifecycleStatus: 'ACTIVE'`
3. 検索パイプラインでの最新版自動差替え:
   - 7段階検索パイプライン Step 6 において、古い記憶がヒットした場合、`resolveLatestSupersededMemory` により置換チェーンを再帰走査（循環参照保護付き）し、常に最新有効な記憶へ自動的に差し替えてプロンプトへ注入する。

15.3 ユーザー明示的削除の2段階反映アーキテクチャ (Two-Phase Forgetting)
ユーザーから「忘れて」「消して」「記憶から削除して」「前言撤回」等の明示的削除が要求された場合、以下の2段階で確実に反映する。
1. 第1段階 (即時ランタイム遮断 - Runtime Blacklist):
   - 対象記憶IDを `longTermMemoryService.addToRuntimeBlacklist(id)` に即時登録。
   - 同一ターン内およびそれ以降の検索パイプラインにおいて、ミリ秒単位でプロンプトへの混入を100%防止する。
2. 第2段階 (台帳永続化 - Ledger Archive):
   - 対象記憶のメタデータを `active: false`, `lifecycleStatus: 'REJECTED'`, `status: 'archived'` に変更。
   - 削除理由（discardReason）を記録し、IndexedDB/ストレージへ永続コミットする。

15.4 感情価に基づく自動記憶淘汰と昇格 (Autonomous Quarantine & Promotion)
1. 自動隔離判定 (Quarantine):
   - ユーザーからの訂正・問題指摘により `confusion_count >= 3` かつ `useful_count === 0` に達した記憶は、自動的に `destination: 'quarantine'`、`lifecycleStatus: 'REJECTED'`、`active: false` に移行。プロンプト検索から自動遮断する。
2. 長期記憶自動昇格 (Promotion):
   - 日常対話を通じて `useful_count >= 5` かつ `confusion_count === 0` を達成した有効な短期・中期記憶は、自動的に `destination: 'long_term_memory'`、`memoryScope: 'long_term'`、`longTermType: 'general_rule'`、`approved: true` へ自動昇格する。

15.5 統合診断ログとコンテキスト長3層防御の可視化 (Explainability)
1. ターン毎の Unified Diagnostic Log 記録:
   - 想起シード記憶（vector_seeds, link_expanded, tag_matched, ratio_used, contradiction_pairs_flagged）
   - コンテキスト長3層防御状態（A層 n_ctxティア, B層 live_budget, ペルソナ/記憶/履歴/余白トークン配分, スライディング圧縮発動有無）
   - キャッシュ・レイテンシ（応答遅延ms, 可変TTL: 通常1800秒 vs 端末保護時300秒）
2. EngineModal およびシステム診断画面でのUI可視化:

第19章 記憶の間隔反復定着・鮮度再検証・埋め込み健全性監視パイプライン (Master v5.4)
======================================================================

19.1 概要と目的
本章では、第2章〜第3章で規定した多層記憶システムと、第11章「深い睡眠サイクル」を拡張し、
「使われている記憶」だけでなく「重要なのに使われていない記憶」「時間経過で古くなった記憶」
「土台であるベクトル検索そのものの健全性」を、ユーザー操作なしに深い睡眠中へ自律的に点検・
更新する仕組みを追加する。これにより、記憶の質が時間経過とともに一方的に劣化することを防ぎ、
放置時間そのものが賢さの向上に変換される状態を目指す。

19.2 間隔反復による記憶定着監査 (Spaced Recall Reinforcement)
- 目的: `useCount` / `lastUsedAt` は記憶の「実利用」を記録するのみで、重要度(importance)が
  高いにもかかわらず長期間想起されていない記憶を能動的に検知・補強する仕組みが存在しなかった。
- 仕様:
  1. 深い睡眠フェーズ開始時、`longTermMemoryService` の全アクティブ記憶を走査し、
     `importance >= 閾値(既定0.7)` かつ `lastUsedAt` が既定期間(既定30日)以上更新されていない
     記憶を「休眠重要記憶(Dormant-Important Memory)」として抽出する。
  2. 抽出上限(既定3件/サイクル)まで、当該記憶の内容を題材に自己対話プロンプトを生成し
     (例:「〇〇について、これまでの理解を要約・再確認せよ」)、モデルに再確認・再要約させる。
  3. 再確認結果が既存記憶の内容と矛盾しない場合は `lastUsedAt` を更新し `reinforcementCount`
     (新設フィールド)をインクリメントする。矛盾を検知した場合は自動上書きせず、
     19.3項の鮮度再検証キューへ回付し、ユーザー承認前提の見直し対象とする。
  4. 本処理は既存の「浅い睡眠/深い睡眠」ゲート条件（`canRunDeepSleep`）にそのまま従い、
     充電中・非アクティブ・非高温時のみ実行する。

19.3 記憶の鮮度再検証 (Freshness Revalidation)
- 目的: 価格・組織名・バージョン番号・ニュース等、時間経過で陳腐化しやすい「時事性フラグ
  付き記憶」について、期限切れ(EXPIRED)判定を待たず、能動的に再検索して裏取りする経路が
  存在しなかった。
- 仕様:
  1. 記憶作成・更新時に `volatility`(揮発性)属性を付与する分類器を `longTermMemoryService`
     に追加し、`high`(時事性高: 価格・役職・最新版情報等) / `low`(不変性高: 定義・個人の
     恒常的嗜好等) の二値を推定・付与する。
  2. 深い睡眠中、`volatility: high` かつ最終検証日から既定期間(既定90日)経過した記憶を
     優先度順に抽出し、既存の`autonomousSearchService`（第13章）へ再検証クエリとして
     自動投入する。
  3. 再検索結果が既存内容と一致すれば `lastVerifiedAt` を更新するのみ。差異を検知した場合は
     即時上書きせず、既存の置換関係追跡(第15章 SUPERSEDED機構)に従い「検証待ち差分」として
     登録し、次回ユーザー対話時に「〇〇についてですが、新しい情報を見つけたので確認しても
     いい？」と確認を挟んでから正式反映する（記憶汚染防止原則を優先）。

19.4 埋め込み健全性監視 (Embedding Health Guard)
- 目的: `embeddingService` は実埋め込み(llama-server Embedding API)と手作り疎ベクトルの
  自動フォールバックを備えるが、フォールバック状態が長時間継続していることをシステムが
  自覚し通知する仕組みが存在しなかった。精度の低いベクトルで想起・グラフ接続が静かに
  劣化し続けるリスクがある。
- 仕様:
  1. 深い睡眠フェーズの冒頭（PHASE 1 開始直後）に `embeddingService` の疎通確認
     (`checkAvailability`相当)を実行し、結果を `EmbeddingHealthStatus`
     (`available` / `degraded_fallback` / `unavailable`) として記録する。
  2. `degraded_fallback` が既定回数(既定3回連続サイクル)以上継続した場合、
     `systemLogger` へ警告ログを出すと同時に、`nativeBackgroundService.sendLocalNotification`
     経由でユーザーへ「埋め込みサーバーが長時間オフラインです。記憶検索の精度が低下している
     可能性があります」という通知を1日1回を上限に送信する。
  3. `available` へ復帰した際は、フォールバック期間中に手作りベクトルのみで作成・接続された
     記憶（`domainVector`のみ保持しactualEmbeddingを持たないもの）を優先キューに入れ、
     深い睡眠の空き時間で段階的に再埋め込み（バッチ処理・18.1項のクールダウン規約に従う）
     を行い、実埋め込みへ順次移行する。

19.5 実行順序と既存パイプラインへの統合
- 上記 19.2〜19.4 は、第11章で定義された `runAutonomousBackgroundCycle` の
  PHASE 1(浅い睡眠: 19.4のみ軽量ヘルスチェックとして実行) および
  PHASE 2(深い睡眠: 19.2・19.3のフル処理およびFHAI4の再埋め込みバッチ)に
  新規ステップとして追加する。いずれも中断シグナル(`abortSignal`)を尊重し、
  ユーザーのチャット操作・充電解除・高温検知時には即座に安全中断する既存の
  安全境界（第0章・第18章）にそのまま従う。

19.6 ネットワーク制約の撤廃とアイドル判定閾値の短縮
- 目的: 当初の「Wi-Fi限定」「ユーザー最終操作から2分間はアクティブとみなす」という初期値は、
  無駄な通信やチャット中の割り込みを避けるための保守的な設定だったが、運用実態に合わせて
  緩和する。
- 仕様:
  1. `WorkManagerConstraints.requiresUnmeteredWifi` を既定 `false` に変更する。
     浅い睡眠・深い睡眠のいずれも、Wi-Fi接続の有無を実行条件から完全に除外し、
     モバイル回線接続時でも自律Web検索学習(第13章)・遅延教師キュー処理(第8章/第11章)を
     許可する。従量課金回線への配慮として、1サイクルあたりの外部通信量上限
     (既定 1MB/サイクル、`featureFlagsService` 経由で既定OFFのオプション)を用意し、
     必要な場合のみユーザーが有効化できるようにする。
  2. `generateAndroidWorkManagerCode` が出力するKotlin WorkManager制約の
     `NetworkType` 指定を `NetworkType.UNMETERED` から `NetworkType.CONNECTED`
     （接続さえあれば可）へ変更する。
  3. `USER_ACTIVE_COOLDOWN_MS` を既定 120000ms(2分) から 60000ms(1分) へ短縮する。
     ユーザーの最後のチャット/アプリ操作から1分間操作がなければ `isUserActive = false`
     とみなし、浅い睡眠（記憶整理・重複除去・スキル抽出等の軽量処理）の実行対象に含める。
  4. 深い睡眠のゲート条件(`canRunDeepSleep`: 充電中・バッテリー30%超・非高温)は変更しない。
     電池消費・発熱・端末寿命に関わる安全側の制御は維持し、緩和対象はあくまで
     「ネットワーク種別」と「アイドル判定に要する時間」の2点のみとする。
