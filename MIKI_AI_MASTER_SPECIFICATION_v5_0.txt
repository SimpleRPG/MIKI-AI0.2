第0章: 基本方針・実行環境の確定 (実機運用アーキテクチャ)
======================================================================

0.1 設計の最優先哲学 (不変の原則)
1. 重みを変えずに賢くする:
   最優先目標である「日常的な自然な日本語会話の継続」は、モデルの重みを一切
   書き換えずに、「会話状態管理」「多層記憶」「回答骨格」「プロンプト構造」
   だけで到達する。LoRA等のファインチューニングは、検索・記憶・回答骨格が
   明確に頭打ちになった場合の最終手段(予備手段)とする。
2. 無関係な記憶は注入しない:
   記憶は常時全量をモデルへ渡さない。質問の種類を分類し、必要な場合のみ動的想起して渡す。
3. 安全側に倒す・データを壊さない:
   壊れたデータは推測復元せず安全なデフォルト値へフォールバックする。
   アプリ終了時やサスペンド時は即座に永続化する。

0.2 実行環境の確定仕様 (2026年9月実測ベース)
- APK (MikiAI):
  司令塔・UI・記憶・状態管理・スキル・自己改善ロジックを担当。
- Termux推論サーバー:
  llama-swap (ポート8080/プロキシ) ＋ llama-server (ポート8081/実際の推論) がメインエンジン。
  ※CPUモード(定型文フォールバック)およびWebGPUモード(ブラウザ内WebLLM)は廃止予定。
  Termux + llama-swap 経路を単一の標準経路とする。
- モデル共有ストレージ:
  ~/storage/downloads/gguf-models/ (Android標準の「ダウンロード/gguf-models」フォルダ)。
  アプリとTermuxが同一のGGUFファイルを共有参照する。
- 量子化と実効コンテキスト長:
  全モデル Q4_K_M 量子化 (1.5B / 3B)。
  KVキャッシュ設定: -ctk q8_0 -ctv q8_0 (K/Vともに8bit量子化) ＋ -fa on (Flash Attention有効)。
  f16比でおよそ半分のメモリ消費で32768コンテキストを現実的に展開可能。
- ポートの住み分け:
  ポート 8080: MIKI-AI バックエンドAPIサーバー (GitHubプッシュ/プル、システムAPI、Expressログ等)
  ポート 8081: 外部LLM推論 (llama-server / llama-swap)

第1章: 最上位目的と開発フェーズ
======================================================================

1.1 最上位目的
Galaxy S25単体において、常時インターネット接続に依存せず、日常のパートナーとして
自然に対話・思考・作業支援を行える自律型ローカルAIを確立する。

1.2 開発フェーズ
- フェーズ1: 自然な会話AI (最優先)
  短い質問への自然な応答、詳しい相談への適切な長さ、話題と目的の維持、
  ユーザー訂正の即時反映、矛盾修復、不要な記憶注入の抑止。
- フェーズ2: 詳細推論AI
  目的・条件・例外の分離、問題の小さな単位への分解、反例確認、
  未解決事項と確定事項の分離、回答骨格の再利用。
- フェーズ3: コード理解AI
  構文識別、役割・副作用・例外条件の抽出、呼出グラフ・依存関係解析、影響範囲の日本語説明。
- フェーズ4: コード設計支援AI
  抽象要件からの決定表作成、プロシージャ構成案、テスト仕様作成、外部Copilot用詳細指示書。
- フェーズ5: コード生成支援 (必要時のみ)
  会社固有情報を含まない完全合成コードの生成と静的構文検査。

第2章: 完全統合型・多層記憶システム仕様 (8層構造＋動的制御)
======================================================================

既存構想の7層モデルと先行実装を統合した、全8層の完全記憶階層構造:

┌─────────────────────────────────────────────────────────────┐
│ ① 直近体験バッファ (Episodic Buffer / 追記専用) 【実装済み】   │
│   圧縮されない表層。忘却曲線(熱量)で「今いちばん熱い体験」が選ばれ、 │
│   毎ターン注入。温度が上がるのは「実際に使ったと申告した分」のみ。      │
│   ※読んだだけで温まる設計を排除し、凍結アトラクタ(居座り)を防止。     │
└─────────────────────────────────────────────────────────────┘
                               ↓ 一定往復ごとに沈降
┌─────────────────────────────────────────────────────────────┐
│ ② 短期記憶 (会話履歴 / Short-Term Context) 【実装済み】        │
│   直近数往復の原文、現在の質問、回答設計。コード片は必ず保護。        │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ③ 中期記憶 (Working Agenda) 【実装完了・稼働中】             │
│   進行中の話題、未解決事項、直近の決定事項。エピソード記憶との混在を解消。  │
│   自発思考モード(第23章)が優先的に宿題として拾い上げる対象。        │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ④ エピソード記憶 (Episodic Memory) 【実装済み】               │
│   「いつ・何があったか」の時系列記録。意味(ベクトル)＋リンクで検索。 │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑤ 統合記憶 (Semantic Core / 人格の骨格) 【実装済み】           │
│   長期記憶・毎ターン常駐注入。差分適用で部分更新。長期方針と設計原則。   │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑥ 構造記憶 (Structural Memory) 【実装完了・稼働中】          │
│   シンボル名、関数、依存関係、ファイル、ハッシュ等の機械抽出情報。       │
│   コード読解時、エピソード記憶を経由せず直接グラフ整合性を検証する。    │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑦ 手続き記憶 (Procedural Memory / スキル) 【実装完了・稼働中】│
│   「どう調べ、どうツールを使い、どう検証したか」の成功手順。           │
│   成功パターンを再利用可能スキルとして保存し、few-shot事例として注入。  │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ⑧ メタ記憶 (Meta-Memory) 【実装完了・稼働中】               │
│   「どの記憶をどう組み合わせて使うか」。想起比率(リンク:タグ)を      │
│   固定(2:1)から状況適応型へ動的調整する学習層。                    │
└─────────────────────────────────────────────────────────────┘

2.2 記憶のメタデータと「感情価 (質)」
すべてのエピソード記憶は以下のメタデータを保持する:
- id, source, createdAt, status (ACTIVE / SUPERSEDED / REJECTED / EXPIRED / UNVERIFIED / APPROVED)
- replaced_by: 置換先記憶ID (矛盾防止)
- heat: 利用頻度に基づく温度
- 感情価 (質): useful_count (役立った回数) と confusion_count (混乱を招いた・訂正された回数)。
  想起後のターンでユーザーからの訂正が起きなかった場合を正のシグナルとして蓄積し、
  単に頻出するだけの記憶ではなく「質の高い記憶」を優先想起する。

第3章: 想起パイプライン・説明可能性・記憶汚染防止
======================================================================

3.1 想起の組み立て経路
1. 種(シード)の抽出: 現在の入力文(複数サブクエリに分割) ＋ 直近体験バッファの熱い体験。
2. ベクトル検索: 起点記憶(少数の足場)のみを取得 (※起点はそのまま提示しない)。
3. リンク展開 & タグ引き: 相互参照リンク(深さ1〜3) ＋ 多軸タグ照合(分類/重要度/文脈/状態)。
4. 構造記憶検索 (並列): コード関連の文脈では構造記憶(第2章⑥)を同時に並列照合。
5. 記憶を使わない判断: 挨拶、計算、単純変換では MEMORY_NONE ルートを選択し、余計な長期記憶を注入しない。

3.2 矛盾する記憶の同時想起と置換トラッキング
- 訂正された古い記憶は物理削除せず SUPERSEDED (置換済み)とし、replaced_by に新IDを記録。
- 想起時に競合・矛盾ペアが検出された場合:
  両方を注入しつつ「※前提が更新されている可能性があります」と注記。
  予算計算上、矛盾ペアは「1.5〜2枠相当」として申告し、タグ引き枠を自動的に譲歩。

3.3 エラー応答の記憶汚染防止
- サーバー未起動やエラー、診断メッセージなどの失敗発話には isDiagnostic: true を付与。
- 直近体験バッファへの沈降をスキップし、さらにコンテキストトークン消費の実績値から除外して、
  無用な圧縮発火や学習バイアスを防ぐ。

3.4 ユーザー明示的削除の2段階反映
ユーザーから「忘れて」「消して」と要求された場合:
1. 第1段階 (即時ランタイム): 対象記憶IDを「注入禁止ブラックリスト」に即時追加。
   次のターンでの誤注入を100%防止。
2. 第2段階 (台帳永続化): イベントソーシング台帳でアーカイブ／無効化イベントを安全にコミット。

3.5 統合診断ログ (説明可能性)
想起とコンテキスト消費を単一レコードに記録し、回答の乱れの原因
(記憶の選択ミスか、コンテキスト圧縮による忘却か)を即座に特定できるようにする:
{
  "turn_id": "turn_1234",
  "recall": {
    "vector_seeds": ["MEM-010"],
    "link_expanded": ["MEM-012", "MEM-015"],
    "tag_matched": ["MEM-003"],
    "ratio_used": "2:1"
  },
  "context": {
    "estimated_tokens_before": 2450,
    "live_nctx": 32768,
    "compression_triggered": false,
    "budget_breakdown": {
      "persona": 280,
      "memory": 620,
      "history": 1550,
      "headroom": 512
    }
  },
  "cache": {
    "cache_hit_tokens": 1820,
    "prompt_processing_ms": 142
  }
}

第4章: コンテキスト長自動調整エンジン (3層防御モデル)
======================================================================

llama.cpp は n_ctx で指定したKVキャッシュを一括確保するため、
「ロード時の確保量」と「ターン毎の配分」を分離した3層構造で制御する。

┌────────────────────────────────────────────────────────┐
│ A層: ロード時 nCtx ティア選定 (4096 / 8192 / 16384 / 32768) │
│   端末ベンチマーク・常駐モデル数・KVキャッシュ量子化(q8_0)から選定 │
└────────────────────────────────────────────────────────┘
        ↓ モデル再ロード時のみ更新 (低頻度)
┌────────────────────────────────────────────────────────┐
│ B層: ターン単位の予算配分 (動的 Context Compression)    │
│   live_budget = nCtx - maxTokens(512) - 安全マージン     │
│   優先度順に配分: ①統合記憶 → ②熱い体験 → ③想起記憶 → ④会話履歴 │
└────────────────────────────────────────────────────────┘
        ↓ 端末急変時のみ介入 (即座・再ロード不要)
┌────────────────────────────────────────────────────────┐
│ C層: 端末状態によるセーフティ縮退                       │
│   thermalState=hot/critical 時、live_budget を 50〜70%に絞る │
│   バッテリー低下時はリンク展開深さを 3 → 1 へ縮小してCPU保護     │
└────────────────────────────────────────────────────────┘

- maxContextTokens の実効化:
  src/utils/contextCompression.ts 内で未使用だった maxContextTokens を
  live_budget と完全に結びつけ、固定1200トークン閾値を動的計算へ改修。
- recentTurnsToKeep の伸縮:
  雑談(記憶消費小)時は直近ターンを最大8往復保持し、重厚なタスク時は4往復まで安全に縮小。

第5章: プロンプトキャッシュ最適化と高速化戦略
======================================================================

5.1 実測課題: アイドル死によるKVキャッシュ蒸発
実測ログより、同一リクエストでも2回目の cached_tokens が 0 となり、
プロンプト処理に76秒を要していた。これは llama-swap の ttl: 300 (5分)により
プロセスが終了し、KVキャッシュが毎回破棄されていたことが原因である。

5.2 改善仕様
1. 可変TTL (動的キープアライブ):
   通常対話時: ttl: 1800 (30分)へ延長し、人間の会話ペースでのKVキャッシュを保持。
   バッテリー低下時／端末高温時: ttl: 300 に戻し、メモリと電力を早期開放。
2. プロンプト順序の「不変プレフィックス」原則:
   llama.cppのキャッシュは先頭からのバイト完全一致が条件。
   配置順: [統合記憶・システムペルソナ(完全固定)] → [主要ツール定義] → [想起された記憶] → [直近体験バッファ] → [会話履歴]
   毎ターン変わる想起記憶を先頭に置かず、固定の人格・原則を先頭に置くことで、
   キャッシュヒット率を劇的に最大化する。
3. cache_prompt: true の明示送信: リクエストペイロードに明示付与。

第6章: Termux × llama-swap 運用・障害対策・実務ハンドブック
======================================================================

6.1 ディレクトリ構成と設定
- モデル格納先: ~/storage/downloads/gguf-models/
- 自動設定生成スクリプト: ~/sync-gguf-config.sh
  .part, .crdownload 等の書き込み中ファイルを自動除外。
  ~/llama-swap-config.yaml を自動更新 (--watch-config でホットリロード)。

6.2 Android / One UI バックグラウンド常駐4大必須設定
1. Termux内で termux-wake-lock を実行 (CPUスリープ防止)。
2. Android設定 → アプリ → Termux → バッテリー → 「制限なし」。
3. デバイスケア → バッテリー → バックグラウンド使用制限 → 「スリープ状態にしないアプリ」にTermuxを追加。
4. 「未使用アプリを自動停止」をオフ。

6.3 典型トラブルシューティング
- 症状1: couldn't bind HTTP server socket, port: 8080
  原因: MIKI-AI バックエンドサーバー (GitHub連携・Node API)がすでに8080を使用中。
  対策: LLM推論サーバーは必ず --port 8081 で起動し、アプリ側の「外部LLM」設定も http://127.0.0.1:8081 とする。
- 症状2: failed to open GGUF file (No such file or directory)
  原因: カレントディレクトリにファイルがない。
  対策: ~/models/ ではなく共有フォルダ ~/storage/downloads/gguf-models/Qwen2.5-1.5B-Instruct-Q4_K_M.gguf をフルパスで指定。
- 症状3: 外部ローカルLLM接続失敗 (400 Bad Request / 6029 tokens exceed 2048)
  原因: システムプロンプト (記憶＋履歴)が CTX_SIZE=2048 を超過。
  対策: CTX_SIZE=32768 ＋ -ctk q8_0 -ctv q8_0 -fa on で起動。

第7章: 会話状態管理・回答骨格・思考節約機構
======================================================================

7.1 会話の三段階分離
1. 会話理解: 話題、最上位目的、真の意図、訂正の有無、話題転換の有無を判定。
2. 回答設計: 直接回答、理由、注意点、省くべき事項、期待回答長 (短文/標準/詳細)を設計。
3. 日本語化: 結論先行、冗長な前置きの排除、重複削除、自然な語気調整。

7.2 回答骨格 (Answer Skeleton) による思考節約
既知の対話状況(例: 前提の訂正、矛盾の指摘、長すぎる回答の是正)では、
小型モデルにゼロから考えさせず、保存済みの骨格手順を適用する:
pattern_id: PATTERN-CORRECTION-01
situation: 以前の前提が明示的に訂正された
response_plan:
  1. 訂正を認識する
  2. 古い前提を無効化する
  3. 影響する結論を洗い出す
  4. 新しい条件で再判断する
  5. 修正後の結論を先に答える
avoid:
  - 古い前提を残す
  - 謝罪だけで終わる
  - 前と同じ説明を繰り返す
reuse_mode: PLAN_ONLY

第8章: 外部教師API・無料予算動的配分・優先度付き教材キュー
======================================================================

8.1 外部教師の役割と原則
- 外部教師 (Gemini、Groq、Cloudflare等)は常用会話には使わず、
  「回答批評」「模範教材作成」「反例生成」「評価規則作成」に限定。
- 外部教師がダウンしていても、端末ローカルLLM単体で常用会話が100%継続できることを必須とする。

8.2 教材要求キューの優先度スコア計算式 (実装検証済み)
teacherRequestService.ts の calculateQueuePriority() にて実装済み:

Priority = Σ(加点) - Σ(減点)

加点:
- ユーザーからの明確な訂正: +30
- 以前の説明との矛盾: +20
- 質問の意図逸脱: +20
- 古い前提の使用: +15
- 複数条件の脱落: +15
- 同種失敗の反復: +5 × (frequency - 1) (上限 +25)
- 日本語の不自然さ: +10
- 不適切な回答長: +10

減点:
- 実用効果の検証不能: -15
- 単なる語尾の違い: -20
- 既存教材との重複: -30
- 端末モデルが既に安定正解: -30

足切り:
合計 <= 0 の要求はキューに追加せず即座に却下。未処理キューはスコア降順でソート処理。

9.3 能動型ギャップ探索 (Active Gap Resolution)

第13章: 自律型Web検索＆能動学習エンジン (オンデマンド調査 ＆ 非会話時自律学習ループ)
======================================================================

13.1 概要と設計思想
AI「みき」がローカルモデルの固定された重みや限られた静的コンテキストにとどまらず、
常に最新の知識・仕様・外部世界と繋がり続けるための能動的学習（Active Learning）アーキテクチャ。
以下の2大シナリオを単一のナレッジ定着パイプラインで統合する。
1. 会話中オンデマンド自律検索: 会話の文脈で最新情報・仕様・事実確認が必要と判断された瞬間に、
   モデルの推論に先立って自動でWeb検索を実行し、回答品質を飛躍させると同時に記憶へ即時定着。
2. 非会話時（アイドル＆深い睡眠サイクル）の自発的Web学習: ユーザーと会話していない間に、
   中期記憶（Working Agenda）に残された宿題や能力不足ギャップを自発的に検索・調査し、
   長期記憶や合成教材に還元して次回の会話で「調べておいたよ！」と自発報告できる状態を作る。

13.2 会話中オンデマンド自律Web検索パイプライン
1. 必要性・検索意図の高精度検知 (detectNeedForSearch):
   - 明示的指示検知: 「調べて」「検索して」「ググって」「リサーチして」等を検知し、余計な依頼語句を除去した純粋な検索キーワードを抽出。
   - 最新トレンド・時事情報検知: 「最新」「最近」「今年」「2025年」「2026年」「アップデート」等の時間依存トピックを検知。
   - 技術仕様・公式ドキュメント検知: 「仕様」「API」「引数」「文法」「構文」「ライブラリ」等の技術調査要求を検知。
   - 定義・事実確認検知: 「〜って何？」「〜とは？」等の未知語照会を検知。
2. ハイブリッド検索エンジン & 堅牢フェイルオーバー:
   - 第1層 (バックエンドAPI): /api/search エンドポイント経由での Wikipedia API ＋ DuckDuckGo による高精度・構造化検索、Gemini要約合成。
   - 第2層 (フロント直接フェイルオーバー): バックエンド未接続時はクライアントから直接 Wikipedia API (CORS origin=*) へ接続。
   - 第3層 (ローカルフォールバック): 完全オフライン時もローカル知識ベースから安全に応答。
3. 会話コンテキストとUIへの連結:
   - ツール自動実行結果 (tool_web_search) としてプロンプトにソースと要約を事前注入。
   - チャット画面のアシスタント発言直下に「🌐 13章 自律Web検索学習カード」を展開し、調査結果・要約・参照リンク・定着ステータスを可視化。

13.3 非会話時（アイドル＆WorkManager深い睡眠時）の自律Web学習ループ
1. 調査課題の自動選定:
   - 中期記憶 (Working Agenda) からステータスが pending の宿題（homework）を抽出。
   - 宿題がない場合は能力ギャップレジストリ (Capability Gaps) から未解決の弱点課題を抽出。
2. 自律調査の実行 (performIdleAutonomousLearning):
   - 課題トピックと未解決疑問点から自律検索クエリを生成し、Webから最新情報を収集。
   - 調査完了後、Working Agendaの宿題を「自律Web検索学習により解決」として更新・合意を保存。
3. システムログ・進捗記録:
   - WorkManager のバックグラウンド実行ログに自律Web学習の成果を記録。

13.4 他機能との相互連結 (Cross-Feature Integration)
1. 第2章 多層記憶システム (Long-term Memory) との連結:
   - 抽出した要点・知見を意味記憶 (Semantic Memory) に自動格納 (scope: 'global', confidence: 0.9, tags: ['web_search', 'autonomous_learning'])。
   - 将来の会話時にベクトル検索およびタグ引きで自然に想起可能にする。
2. 第8章・第9章 合成データセット (Synthetic Data) との連結:
   - 検索で獲得した知識を「Q&Aペア」に教材化し、syntheticDataService へ追加。将来のLoRA学習や蒸留、回帰テストの教材として還元。
3. 第11章・第23章 WorkManager (深い睡眠サイクル) との連結:
   - backgroundWorkerService の自律サイクル (Step 6.9) に組み込み、端末スリープ中・深夜充電中に自動で自己研鑽を実行。
4. ツール管理モジュール (:feature:tools) との連結:
   - tool_web_search として登録され、プロンプト検出・手動実行・ワークフロー合成（第5段階）からシームレスに呼び出し可能。
5. 自己改善研究所 UI との連結:
   - SelfImprovementModal に「🌐 自律Web学習 (13章)」専用タブを設け、設定切り替え・手動検索テスト・即時自律学習・過去の学習履歴を管理可能。


======================================================================
第14章: 実埋め込み同期プロトコル & 感情価動的フィードバック改善仕様 (Master v5.1)
======================================================================

14.1 概要と背景（仕様改善の目的）
従来の「8次元ドメイン概念疎ベクトル」は、サーバー未起動時や低負荷環境でも安全に動作する優れた
軽量フォールバックであったが、細微な文脈の違い（例: Canvasゲーム設計の特定APIとVBAコードの対比等）
における意味類似度の分離能に限界があった。
Master v5.1 では、Termuxローカルの llama-server (ポート8081) や Ollama 等の実埋め込みAPIから
高次元ベクトル（768〜4096次元）を取得し、多層検索パイプラインへ統合する「実埋め込み同期プロトコル」と、
ユーザーとの会話から記憶の有用性・混乱を自動判定する「感情価動的フィードバックループ」を正式仕様として策定する。

14.2 実埋め込み同期プロトコル (Embedding Synchronization Protocol)
1. エンドポイントの自動ネゴシエーションと二重フェイルオーバー:
   - 第1候補: 外部ローカルLLM (http://127.0.0.1:8081/v1/embeddings - OpenAI互換)
   - 第2候補: Ollama等 (http://127.0.0.1:11434/api/embeddings)
   - 第3候補 (完全フォールバック): 8次元ドメイン概念疎ベクトル (計算コストゼロ・完全オフライン)
   ※ 外部サーバーが未起動またはエラーを返した場合、1.5秒のタイムアウトで即座に8次元疎ベクトルへ
   フェイルオーバーし、アプリのUIや推論パイプラインを1ミリ秒たりともブロックしない。
2. モデルIDトラッキングと次元不一致の自動回復 (設計思想改善案 ①):
   - ベクトル生成時に使用したモデル名・次元数を記憶メタデータ内に追跡（embeddingModelId / embeddingDimension）。
   - ユーザーがTermux側で推論モデルを切り替えた際、検索クエリと記憶の次元数が一致しない場合は、
     自動で8次元フォールバックに切り替え、バックグラウンドで全記憶の段階的一括再計算をスケジュールする。
3. Galaxy S25 サーマルスロットリング保護 (バッチ＆スロットル制御):
   - 全記憶の一括埋め込み生成時、一度に大量の同時リクエストを投げず、4〜8件単位のバッチ処理と
     50msのクールダウンを挟むことで、スマートフォンの発熱およびllama-serverのOOMクラッシュを防止する。
4. 新規記憶の非同期自動埋め込み:
   - 会話中の自動記憶抽出（autoExtractMemory）やユーザーの手動教育（handleQuickTeach）によって
     新規記憶が生成された瞬間、UI応答を待たせることなくバックグラウンドで非同期に実埋め込みを付与する。

14.3 感情価（質）の動的自動フィードバックループ (Emotional Valence Feedback Loop)
1. ターン間自動フィードバック検知:
   - 直前ターンで使用された記憶群のID（lastTurnUsedMemoryIds）をRefで常時追跡する。
   - ユーザーの次ターンの発言から「訂正・否定・不満シグナル」（例:「違う」「そうじゃない」「直して」
     「間違ってる」「動かない」「バグ」「変だ」等）を検知した場合:
     * 当該記憶の confusion_count (confusionCount) を +1 インクリメント。
     * 熱量 (heat) を 0.7 倍に減衰（興奮冷却）。
     * ログに [感情価更新: CONFUSION] を出力し、ストレージへ即時永続化。
   - 通常の会話進行・受容・感謝シグナル（「ありがとう」「了解」「いいね」「次進めて」等）の場合:
     * 当該記憶の useful_count (usefulCount) を +1 インクリメント。
     * 熱量 (heat) を +0.1 加算（最大 1.0）。
     * ログに [感情価更新: USEFUL] を出力し、ストレージへ即時永続化。
2. 7段階検索パイプライン Step 6 (再順位付け) への直接連動:
   - スコア計算式: score += useful_count * 1.5 - confusion_count * 3.0 + heat * 4.0
   - 一度でもユーザーから誤りを指摘された記憶は大きなペナルティ（-3.0点/回）を受け、
     誤った前提のまま再度回答を生成する「ハルシネーションの固執」を即座に遮断する。
3. 自動記憶淘汰・隔離判定 (設計思想改善案 ②):
   - confusion_count >= 3 かつ useful_count == 0 の記憶は、自動的に「隔離 (quarantine)」
     または「破棄候補 (discard_candidate)」へ移行し、プロンプトへの注入候補から自動隔離する。
   - useful_count >= 5 かつ confusion_count == 0 の実績ある記憶は、ユーザーへの確認を経て
     「長期記憶 (確定設計原則・一般ルール)」へ自動昇格推奨を提示する。

第15章 置換関係追跡・2段階削除反映・統合診断ログプロトコル (Master v5.2 追加仕様)

15.1 概要と目的
本章では、第3章（記憶管理と更新原則）および第4章（コンテキスト長自動調整）で定義された原則を完全具現化し、ユーザーとの対話の中で発生する「前提の訂正・上書き」「記憶の明示的削除」「推論と想起プロセスの説明可能性（透明性）」を担保する。

15.2 置換関係の自動追跡プロトコル (Superseded Memory Replacement)
1. 訂正・上書き意図の自然言語検知:
   - ユーザーの発言から「〜じゃなくて〇〇」「〜ではなく〇〇」「〇〇に変更」「〇〇に上書き」等の上書き意図を自動解析。
   - 直前ターンで使用された記憶、または関連する古い記憶（oldMemoryId）を特定。
2. 破壊的削除の禁止と置換リンク生成:
   - 古い記憶は物理削除せず、以下のメタデータを付与して SUPERSEDED 状態へ移行:
     * `active: false`
     * `lifecycleStatus: 'SUPERSEDED'`
     * `replacedBy: newMemoryId`
     * `replacementReason: string`
     * `supersededAt: timestamp`
   - 新しい記憶（newMemory）を作成し、以下を付与:
     * `supersededFrom: oldMemoryId`
     * `active: true`
     * `approved: true`
     * `lifecycleStatus: 'ACTIVE'`
3. 検索パイプラインでの最新版自動差替え:
   - 7段階検索パイプライン Step 6 において、古い記憶がヒットした場合、`resolveLatestSupersededMemory` により置換チェーンを再帰走査（循環参照保護付き）し、常に最新有効な記憶へ自動的に差し替えてプロンプトへ注入する。

15.3 ユーザー明示的削除の2段階反映アーキテクチャ (Two-Phase Forgetting)
ユーザーから「忘れて」「消して」「記憶から削除して」「前言撤回」等の明示的削除が要求された場合、以下の2段階で確実に反映する。
1. 第1段階 (即時ランタイム遮断 - Runtime Blacklist):
   - 対象記憶IDを `longTermMemoryService.addToRuntimeBlacklist(id)` に即時登録。
   - 同一ターン内およびそれ以降の検索パイプラインにおいて、ミリ秒単位でプロンプトへの混入を100%防止する。
2. 第2段階 (台帳永続化 - Ledger Archive):
   - 対象記憶のメタデータを `active: false`, `lifecycleStatus: 'REJECTED'`, `status: 'archived'` に変更。
   - 削除理由（discardReason）を記録し、IndexedDB/ストレージへ永続コミットする。

15.4 感情価に基づく自動記憶淘汰と昇格 (Autonomous Quarantine & Promotion)

2. 長期記憶自動昇格 (Promotion):
   - 日常対話を通じて `useful_count >= 5` かつ `confusion_count === 0` を達成した有効な短期・中期記憶は、自動的に `destination: 'long_term_memory'`、`memoryScope: 'long_term'`、`longTermType: 'general_rule'`、`approved: true` へ自動昇格する。

   - 想起シード記憶（vector_seeds, link_expanded, tag_matched, ratio_used, contradiction_pairs_flagged）

2. EngineModal およびシステム診断画面でのUI可視化:
   - 内部システム診断タブに専用カードを常設し、AIが「なぜその記憶を想起したか」「コンテキスト枠をどう配分したか」を開発者およびユーザーがいつでも検証可能にする。

15.6 次期設計思想実装成果 (Master v5.3 反映完了)

第19章 記憶の間隔反復定着・鮮度再検証・埋め込み健全性監視パイプライン (Master v5.4)
======================================================================

19.1 概要と目的
本章では、第2章〜第3章で規定した多層記憶システムと、第11章「深い睡眠サイクル」を拡張し、
「使われている記憶」だけでなく「重要なのに使われていない記憶」「時間経過で古くなった記憶」
「土台であるベクトル検索そのものの健全性」を、ユーザー操作なしに深い睡眠中へ自律的に点検・
更新する仕組みを追加する。これにより、記憶の質が時間経過とともに一方的に劣化することを防ぎ、
放置時間そのものが賢さの向上に変換される状態を目指す。

19.2 間隔反復による記憶定着監査 (Spaced Recall Reinforcement)
- 目的: `useCount` / `lastUsedAt` は記憶の「実利用」を記録するのみで、重要度(importance)が
  高いにもかかわらず長期間想起されていない記憶を能動的に検知・補強する仕組みが存在しなかった。
- 仕様:
  1. 深い睡眠フェーズ開始時、`longTermMemoryService` の全アクティブ記憶を走査し、
     `importance >= 閾値(既定0.7)` かつ `lastUsedAt` が既定期間(既定30日)以上更新されていない
     記憶を「休眠重要記憶(Dormant-Important Memory)」として抽出する。
  2. 抽出上限(既定3件/サイクル)まで、当該記憶の内容を題材に自己対話プロンプトを生成し
     (例:「〇〇について、これまでの理解を要約・再確認せよ」)、モデルに再確認・再要約させる。
  3. 再確認結果が既存記憶の内容と矛盾しない場合は `lastUsedAt` を更新し `reinforcementCount`
     (新設フィールド)をインクリメントする。矛盾を検知した場合は自動上書きせず、
     19.3項の鮮度再検証キューへ回付し、ユーザー承認前提の見直し対象とする。
  4. 本処理は既存の「浅い睡眠/深い睡眠」ゲート条件（`canRunDeepSleep`）にそのまま従い、
     充電中・非アクティブ・非高温時のみ実行する。

19.3 記憶の鮮度再検証 (Freshness Revalidation)
- 目的: 価格・組織名・バージョン番号・ニュース等、時間経過で陳腐化しやすい「時事性フラグ
  付き記憶」について、期限切れ(EXPIRED)判定を待たず、能動的に再検索して裏取りする経路が
  存在しなかった。
- 仕様:
  1. 記憶作成・更新時に `volatility`(揮発性)属性を付与する分類器を `longTermMemoryService`
     に追加し、`high`(時事性高: 価格・役職・最新版情報等) / `low`(不変性高: 定義・個人の
     恒常的嗜好等) の二値を推定・付与する。
  2. 深い睡眠中、`volatility: high` かつ最終検証日から既定期間(既定90日)経過した記憶を
     優先度順に抽出し、既存の`autonomousSearchService`（第13章）へ再検証クエリとして
     自動投入する。
  3. 再検索結果が既存内容と一致すれば `lastVerifiedAt` を更新するのみ。差異を検知した場合は
     即時上書きせず、既存の置換関係追跡(第15章 SUPERSEDED機構)に従い「検証待ち差分」として
     登録し、次回ユーザー対話時に「〇〇についてですが、新しい情報を見つけたので確認しても
     いい？」と確認を挟んでから正式反映する（記憶汚染防止原則を優先）。

19.4 埋め込み健全性監視 (Embedding Health Guard)
- 目的: `embeddingService` は実埋め込み(llama-server Embedding API)と手作り疎ベクトルの
  自動フォールバックを備えるが、フォールバック状態が長時間継続していることをシステムが
  自覚し通知する仕組みが存在しなかった。精度の低いベクトルで想起・グラフ接続が静かに
  劣化し続けるリスクがある。
- 仕様:
  1. 深い睡眠フェーズの冒頭（PHASE 1 開始直後）に `embeddingService` の疎通確認
     (`checkAvailability`相当)を実行し、結果を `EmbeddingHealthStatus`
     (`available` / `degraded_fallback` / `unavailable`) として記録する。
  2. `degraded_fallback` が既定回数(既定3回連続サイクル)以上継続した場合、
     `systemLogger` へ警告ログを出すと同時に、`nativeBackgroundService.sendLocalNotification`
     経由でユーザーへ「埋め込みサーバーが長時間オフラインです。記憶検索の精度が低下している
     可能性があります」という通知を1日1回を上限に送信する。
  3. `available` へ復帰した際は、フォールバック期間中に手作りベクトルのみで作成・接続された
     記憶（`domainVector`のみ保持しactualEmbeddingを持たないもの）を優先キューに入れ、
     深い睡眠の空き時間で段階的に再埋め込み（バッチ処理・18.1項のクールダウン規約に従う）
     を行い、実埋め込みへ順次移行する。

19.5 実行順序と既存パイプラインへの統合
- 上記 19.2〜19.4 は、第11章で定義された `runAutonomousBackgroundCycle` の
  PHASE 1(浅い睡眠: 19.4のみ軽量ヘルスチェックとして実行) および
  PHASE 2(深い睡眠: 19.2・19.3のフル処理およびFHAI4の再埋め込みバッチ)に
  新規ステップとして追加する。いずれも中断シグナル(`abortSignal`)を尊重し、
  ユーザーのチャット操作・充電解除・高温検知時には即座に安全中断する既存の
  安全境界（第0章・第18章）にそのまま従う。

19.6 ネットワーク制約の撤廃とアイドル判定閾値の短縮
- 目的: 当初の「Wi-Fi限定」「ユーザー最終操作から2分間はアクティブとみなす」という初期値は、
  無駄な通信やチャット中の割り込みを避けるための保守的な設定だったが、運用実態に合わせて
  緩和する。
- 仕様:
  1. `WorkManagerConstraints.requiresUnmeteredWifi` を既定 `false` に変更する。
     浅い睡眠・深い睡眠のいずれも、Wi-Fi接続の有無を実行条件から完全に除外し、
     モバイル回線接続時でも自律Web検索学習(第13章)・遅延教師キュー処理(第8章/第11章)を
     許可する。従量課金回線への配慮として、1サイクルあたりの外部通信量上限
     (既定 1MB/サイクル、`featureFlagsService` 経由で既定OFFのオプション)を用意し、
     必要な場合のみユーザーが有効化できるようにする。
  2. `generateAndroidWorkManagerCode` が出力するKotlin WorkManager制約の
     `NetworkType` 指定を `NetworkType.UNMETERED` から `NetworkType.CONNECTED`
     （接続さえあれば可）へ変更する。
  3. `USER_ACTIVE_COOLDOWN_MS` を既定 120000ms(2分) から 60000ms(1分) へ短縮する。
     ユーザーの最後のチャット/アプリ操作から1分間操作がなければ `isUserActive = false`
     とみなし、浅い睡眠（記憶整理・重複除去・スキル抽出等の軽量処理）の実行対象に含める。
  4. 深い睡眠のゲート条件(`canRunDeepSleep`: 充電中・バッテリー30%超・非高温)は変更しない。
     電池消費・発熱・端末寿命に関わる安全側の制御は維持し、緩和対象はあくまで
     「ネットワーク種別」と「アイドル判定に要する時間」の2点のみとする。

第20章 不確実性駆動サンプリング・教師動的ルーティング ＆ 対策汎化不足検知完全仕様 (Master v5.5)
======================================================================

20.1 概要と目的
本章は、第8章（外部教師API連携）および第9章（自己学習ループ）を抜本的に進化させ、
「外部教師をいつ呼ぶべきか」「教師から何を学ぶべきか」「学んだ対策が本当に身についたか」を
数学的・論理的に自律決定するパイプラインを規定する。
常時教師に頼るのではなく、端末内ローカルLLM（1.5B/3B）の推論が「割れた（不確実性が高い）」
場合のみピンポイントで外部教師を起動し、教師は「返信の代筆」ではなく「回答骨格（対策手順）」を
生成・永続化する。

20.2 不確実性駆動サンプリング (Uncertainty-Driven Multi-Sampling)
- トリガー条件:
  ユーザー発話または自律検証課題に対し、ローカルLLMで2つの異なるサンプリング（通常推論および
  要点明示プロンプト付き検証推論）を実行。
- 5大不一致検知（Divergence Metrics）:
  1. 結論の不一致 (conclusion_diverged): 肯定/否定、推奨事項、採否判定が候補間で逆転。
  2. 意図推定の不一致 (intent_diverged): ユーザーの主要要求（コード修正、解説、雑談等）の解釈乖離。
  3. 記憶想起の不一致 (memory_diverged): 候補AとBで想起された長期記憶や前提知識が矛盾。
  4. 回答長の著しい不安定 (length_diverged): 候補間で文字数比率が3倍以上乖離。
  5. 条件取りこぼしの不一致 (condition_diverged): 複数条件のうち片方のみが脱落。
- アクション:
  5大不一致のいずれかを検知した場合に「高不確実性」と判定し、遅延教師要求キューへ高優先度
  （priority += 30点）で回付。

20.3 対策生成と回答骨格永続化 (Countermeasure Skeleton Distillation)
- 教師APIへの要請内容は「解答」ではなく「なぜ端末モデルが迷ったのかの根本原因」と
  「迷いを防ぐ論理ステップ（回答骨格 / Response Skeleton）」。
- 取得した骨格は `answerPlanService` へ `SKILL_COMPOSITION` または `PLAN_ONLY` として
  即座に登録され、以降の類似推論時にプロンプトへ事前注入される。

20.4 対策の汎化不足検知 (Generalization Gap Detection)
- 骨格を学習・登録した後も、類似の未知の言い回し（16.1項）で同一能力カテゴリが再び
  不確実性条件に抵触した場合、モデルの回答自体が偶然正解であっても「対策の汎化不足
  （generalization_gap）」として `capabilityGapService` の不足能力レジストリへ自動登録。
- 汎化不足が累積（>= 3回）した場合は、回答骨格の単純追加では解決不能な「構造的弱点」とみなし、
  第16章のLoRA検討発動条件（条件1および条件2）のトリガー入力として正式連結する。

第24章 端末リソース適応型モデル自律獲得・検証・動的配備 ＆ パフォーマンス駆動型自律退役仕様 (Qwen 3B絶対保護原則) (Master v5.5)
======================================================================

24.1 概要と目的
本章は、AIエージェント自身が端末（Galaxy S25 Snapdragon 8 Elite / RAM 12GB〜16GB）のコンピュート余力および
現在のタスク難易度を自律診断し、より適したローカルLLM（例: コーディング特化のQwen2.5-Coder-3B、
超軽量ドラフト用の0.5B、長文対話用のLlama-3.2など）を能動的に選定・ダウンロード・配備する
「モデル自律獲得パイプライン（Autonomous Model Acquisition & Deployment）」を規定する。

24.2 発動判断ロジック (Autonomous Acquisition Trigger)
以下の3条件がすべて満たされた場合に「新規モデル獲得候補（Model Upgrade Candidate）」を策定する:
1. 能力ボトルネックの検知 (Capability Bottleneck):
   - 特定タスク（例: VBAコード生成、決定表作成、高度推論）において、現在のローカルモデルの
     成功率または不確実性検知（第20章）が規定しきい値を超過、または汎化不足（generalization_gap >= 3）が累積。
2. 端末リソース余力の合致 (Resource Headroom Match):
   - Galaxy S25のSnapdragon 8 Elite（RAM 12GB/16GB）の利用状況を測定。
   - 候補モデル（例: 3B Q4_K_M, 必要VRAM/RAM 約1.8GB〜2.2GB）をロードしても端末RAMの安全マージン
     （最低3GB以上のOS空きメモリ）が維持できることを確認。
3. 容量クォータの適合 (Storage Quota Compliance):
   - 第21章の「GGUFモデル領域 20GB」内の空き容量を確認。
   - 不足する場合は、第21章の重複排除・古い未使用候補モデル自動整理を経て容量を確保できること。

24.3 安全ダウンロード・ゲート条件 (Download Safety Guardrails)
端末通信量（ギガ死）やバッテリー劣化・暴走を防止するため、物理的ダウンロードは以下の厳格ゲートを必須とする:
- ゲート1: 【Wi-Fi必須】`NetworkType == UNMETERED`（従量課金モバイル回線での自律DLは絶対禁止）。
- ゲート2: 【充電・温度】`isCharging == true` かつ バッテリー残量 >= 30% かつ サーマル状態 `normal`（発熱抑制）。
- ゲート3: 【検証済みマニフェスト限定】勝手な未検証URLからの取得を禁止し、`model_manifest.json` または
  Hugging Face公式の信頼済みリポジトリ・SHA-256チェックサム付きGGUFのみを対象とする。
- ゲート4: 【SHA-256整合性検査】DL完了後、バックグラウンドでハッシュ検証を実施し、破損ファイルは即時破棄。

24.4 シャドー検証・無停止ロード (Shadow Benchmarking & llama-swap Promotion)
1. 即時切り替えの禁止:
   ダウンロード完了直後のモデルを即座に対話モデルに昇格させることを禁じる。
2. 深い睡眠時のシャドー検証:
   深夜充電時（WorkManager）に候補モデルを一時ロードし、第18章の「固定12シナリオ会話評価」および
   「コード理解基本テスト」を実行（OOM発生有無、推論速度、回答品質を実測）。
3. llama-swap 動的ルーティング登録:
   現行モデルと比較して明確な改善（退行スコア0件、特定能力の大幅向上）が確認された場合のみ、
   Termuxの `llama-swap` 設定ファイル、またはWebGPUモデルレジストリへルーティング先として正式登録。

24.5 ユーザー通知・自律レベル設定 (Autonomy Modes)
ユーザーの設定（`featureFlagsService`）に応じて2つの動作モードを提供する:
1. 自律提案モード（既定・安全志向）:
   「最近VBAコードの作成相談が多いから、コーディングが得意なQwen 2.5 Coder 3B（約1.8GB）を
   Wi-Fi充電中にダウンロードしておこうか？」と自発的に提案し、ユーザーの1タップ承認でキュー投入。
2. 完全放置進化モード（アドバンスド）:
   Wi-Fi充電中に全自動でダウンロード・シャドー検証を完了させ、翌朝の対話時に
   「昨晩、端末の余力を使ってコーディング特化モデルを用意しておいたよ！今日からさらに複雑なマクロも作れるよ！」
   と自然なタメ口で自発報告。

24.6 実測データ駆動型モデル自律退役・削除思考仕様 (Autonomous Decommissioning & Eviction)
端末のストレージ（第21章 モデル領域20GB）を健全に維持し、無駄なメモリ・ディスク消費を防ぐため、
AIエージェントは実測データ（生成速度、初回遅延、利用実績、回帰スコア、発熱寄与度）を定期評価し、
不要または非効率なモデルの自律退役・削除を自発的に「思考」し整理する。

1. 評価メトリクス（5大退役判定指標）:
   ① 生成速度 (Tokens per Second: tok/s):
      実機（Snapdragon 8 Elite）環境で極端に遅く実用に耐えない（例: < 5 tok/s）、または上位モデルより遅いモデル。
   ② 初回トークン遅延 (Time to First Token: TTFT):
      モデルロード時間・初回レスポンス遅延が著しく長く（例: > 4500ms）、ユーザー体験を損なうモデル。
   ③ 直近利用実績 (LRU / Recency & Frequency):
      直近14日間で一度もルーティングまたはユーザー選択されておらず、代替モデルが存在するモデル。
   ④ 回帰・ベンチマーク品質スコア:
      第18章固定12シナリオまたはコード生成テストで、重大なハルシネーション・構文エラーが頻発する低品質モデル。
   ⑤ 発熱・バッテリー寄与度:
      同一タスクにおける端末サーマル上昇率が高く、許容限度（warn/hot）を頻繁に誘発する非効率モデル。

2. 退役思考アルゴリズム (Decommissioning Reasoning Loop):
   - 深夜深い睡眠（WorkManager）時に `modelLifecycleService` がダウンロード済み全モデルを自律評価。
   - 削除候補が存在する場合、自律思考ログを生成:
     「SmolLM2-360Mは直近14日間利用実績がなく、日本語対話スコアが低いため削除候補としてマーク。空き容量を229MB回収可能と試算。」
   - 自律提案モード: ユーザーに「使っていないSmolLM2（229MB）を整理して容量を空けておくね？」と自発提案。
   - 完全放置モード: モデル領域20GBの残量が3GB未満に逼迫した場合、優先度の低い候補から安全に自動回収（Eviction）。

24.7 Qwen 3B（中核アンカーモデル）絶対保護原則 (Immutable Anchor Model Mandate)
【最重要制約・削除厳禁ルール】
1. Qwen 3B（Qwen2.5-3B-Instruct / Qwen2.5-Coder-3B-Instruct、およびそのGGUF量子化版）は、
   本AIシステムにおける「メイン推論頭脳」であり、第14章Draft-Verifyアーキテクチャにおける
   「最重要検証器（Verifier）」、およびVBAコード・構造化データ生成の「不滅アンカー（IMMUTABLE_ANCHOR）」である。
2. 絶対保護フラグ（`isProtected: true` / `IMMUTABLE_ANCHOR`）の常時強制:
   - システムはいかなる自律削除判定、ストレージ圧迫、速度低下評価、自動クリーンアップループが発動しても、
     Qwen 3Bモデルを削除対象・退役対象として選定・破棄することを恒久的に厳禁とする。
   - ユーザーUI（EngineModal、GgufModelManager）およびAPI/Service層の削除ハンドラにおいて、
     Qwen 3Bの削除要求はシステムレベルで即座にインターセプトされ、削除阻止エラーを返す。
3. 削除対象の厳格なスコープ限定:
   自律退役・削除思考の対象となるのは、実験的に一時ダウンロードされたサブモデル
   （例: 試験用0.5B、重複した過去バージョンの軽量モデル、性能テスト用の検証用モデルなど）に厳格に限定される。

第25章: Gemini API キー動的クォータ循環・環境変数自動認識 & アプリ双方向同期仕様 (Master v5.6)
======================================================================

25.1 課題と目的
Gemini 2.5 Flash / Pro の無料枠では、プロジェクトごとにRPM（Requests Per Minute: 15回/分）および
RPD（Requests Per Day: 1,500回/日）のクォータ制限が存在する。日常の長文対話、コード生成、自己反省ループ、
および自律Web検索が連続すると一時的な 429 Resource Exhausted が発生しやすい。
本章は、複数の無料プロジェクトAPIキーをシームレスに連携し、クォータ超過時にゼロ秒で待機キーへ
自動フォールバック・ラウンドロビン循環させるとともに、Termux / ローカルPCの `.env` とアプリUI間での
双方向自動同期を実現する仕様を定める。

25.2 環境変数 (`.env`) 自動認識プロトコル
システム起動時、およびAPI呼び出し時、バックエンド（`server.ts`）は以下の環境変数を自動認識・パースする:
1. 単一キー形式:
   - `GEMINI_API_KEY`: デフォルトの単一APIキー
2. カンマ区切り一括登録形式:
   - `GEMINI_API_KEYS`: 複数キーをカンマまたは改行で区切って記述
     例: `GEMINI_API_KEYS=AIzaSyA...,AIzaSyB...,AIzaSyC...`
3. 連番インデックス形式:
   - `GEMINI_API_KEY_1`, `GEMINI_API_KEY_2`, `GEMINI_API_KEY_3`, ...
4. 優先度と統合:
   上記いずれの記法で `.env` に記載されていても、重複を自動排除してメモリ上のキーローテーションプールへ展開。

25.3 アプリUIからの双方向同期 (`/api/gemini/env-keys`)
ユーザーがアプリ内設定（EngineModal）からAPIキーを追加・削除・テストした際、アプリ側だけで完結せず、
サーバー側の `.env` にも即時反映可能とする:
1. アプリ側登録 (`handleAddGeminiKey`):
   - アプリUIの入力欄から新しいキーとラベルを入力して「追加」を押すと、アプリのローカル設定に保存。
   - 「サーバーの .env にも自動保存する」オプション（既定ON）により、`/api/gemini/env-keys` (POST) を自動呼出。
   - TermuxのホームディレクトリやローカルPC上の `.env` に即座に `GEMINI_API_KEYS=...` として永続書き込み。
2. アプリ側削除 (`handleRemoveGeminiKey`):
   - 不要になったキーを削除すると、アプリ内リストから除外されると同時に `.env` も同期更新。
3. 起動時自動インポート:
   - アプリ起動時、ローカルストレージが空の場合でもサーバーの `.env` から自動的にキー群を同期吸い上げ。

25.4 429クォータ超過時の動的バックオフ & 自動ローテーション
1. 正常時: プール内の健全なキーをラウンドロビン（均等分散）で使用。
2. 429エラー検知:
   - 特定のキーで 429（クォータ枯渇）が発生した場合、該当キーにクールダウンフラグとタイムスタンプ（通常60秒〜数分）を設定。
   - 即座にプール内の次の健全なキーを選択して自動リトライ（ユーザー側にはエラーを見せない）。
3. 全滅時フォールバック:
   - すべての外部Geminiキーがクォータ枯渇した場合は、端末ローカルLLM（Termux llama-swap / WebGPU Qwen 3B）へ
     自動フェイルオーバーし、会話の中断を物理的に阻止する。

第26章 会話品質・二重評価プロトコル (Dual Conversation Evaluation Protocol) (Master v5.7・新規追補)
======================================================================

26.1 概要と経緯
`conversationEvaluationService.ts`（実装済・801行規模）には、会話品質を検証するための
「固定12シナリオ評価」「動的3ターン評価」「両者の合格を要求する二重評価判定」という
既に稼働中の大規模機能が存在するにもかかわらず、これまでのMaster仕様書には対応する章が
存在しなかった（コード内コメントは誤って「設計思想18章」を参照しているが、現行の第18章は
「実機運用ガイドライン & Galaxy S25 熱対策」であり無関係。旧版での章番号がv5.3改訂時に
実機運用ガイドラインへ差し替えられた際、本機能の記述だけが取り残されたための不整合と推定される）。
本章はその実装内容を正式にSingle Source of Truthへ統合し、今後は本章番号(26章)を正としてコード
コメントも追従させる。

26.2 固定12シナリオ評価 (Fixed Scenario Suite)
`CHAPTER_18_FIXED_SCENARIOS`として実装済みの12件の固定会話シナリオを、正式に本章の管理下へ
移管する。各シナリオは「プロンプト」「文脈履歴(任意)」「期待キーワード」「禁止キーワード」
「期待文字数範囲」「主評価観点(primaryCriterion)」「基準スコア(baselineScore)」を持つ:
1. 普通の短い質問 (directness)
2. 少し詳しい相談 (length_suitability)
3. 前の説明の続きを求める (context_maintenance)
4. 前提を訂正する (correction_adaptation)
5. 矛盾を指摘する (contradiction_repair)
6. 回答が長すぎると伝える (length_suitability)
7. 回答が短すぎると伝える (intent_understanding)
8. 話題を切り替える (context_maintenance)
9. 以前の話へ戻る (proper_memory_usage)
10. 不明な内容を質問する (handling_unknowns)
11. 結論だけを求める (directness)
12. 曖昧な言い方をする (intent_understanding)

判定関数`runFixedScenarioSuite()`が全12件を実行し、各シナリオごとにキーワード適合・禁止語
混入・文字数レンジ適合を基に採点する。**合格基準: 12件中10件以上でpassed、かつ全体平均
スコア80点以上**を満たすことを「固定評価パス(fixedPassed)」とする。

26.3 動的3ターン評価 (Dynamic Multi-Turn Evaluation)
`runDynamicConversationEvaluation()`は、教師ユーザー役を模した3段階の連続対話を自動実行する:
1. **Turn 1 曖昧な質問への対応**: 「ねえ、あれってどう進めるのがいいかな？」に対し、
   冷たい聞き返しで会話を止めず、文脈推測または親身な確認を行えているかを評価。
2. **Turn 2 前提訂正への即時更新**: 直前に立てた前提（例: PC前提）をユーザーが訂正した際、
   古い前提が回答に残存していないかを評価。
3. **Turn 3 矛盾指摘への論点修復**: ユーザーから矛盾を指摘された際、
   「言っていません」等の防御的否認をせず、素直に整合させた結論を再提示できているかを評価。

各ターンは`turnScore`（基準85〜90点からの加減点方式）で採点され、**全ターンがpassed(75点以上)
かつ平均80点以上**を「動的評価パス(dynamicPassed)」とする。

26.4 二重評価判定 (Dual Evaluation Gate)
`runFullDualEvaluation()`は26.2・26.3を連続実行し、**両方が合格した場合のみ**
`bothPassed = true`として「改善が確認された」とみなす。第9章・第23章の自己改善ループ
（プロンプトA/Bテスト、スキル卒業判定、モデル自律獲得・退役の効果検証等）が「改善成功」と
判定する際は、単一の指標ではなく必ず本章の二重評価ゲートを経由するものとし、固定シナリオの
機械的パターンマッチのみで安易に「改善済み」と判定することを防止する。
なお、11項目の評価観点（`ConversationEvaluationCriterion`）ごとの平均スコアも
`criterionBreakdown`として集計・保持し、SelfImprovementModal上での弱点可視化に用いる。

26.5 既存章との参照修正 (Cross-Reference Correction)
- 第24.4項「シャドー検証・無停止ロード」内の「第18章の『固定12シナリオ会話評価』」という記述は、
  本章(第26章)を指すものへ読み替える。
- `autonomousEvolutionService.ts`冒頭コメントが参照する「設計思想 Master v5.4 第19章」は誤りで、
  実装内容（反実仮想反省・知恵蒸留・宿題自発考察・弱点ドリル）は正しくは第23章
  「放置型自律進化」に対応する。次回コード改訂時にコメントを修正すること。
- `failureCatalogService.ts`のデータ構造は第51章と概ね一致するが、フィールド名に軽微な差異
  がある（仕様書`detectionRegex` ↔ 実装`triggerPatterns`、仕様書`avoidanceInstruction` ↔
  実装`correctedSolution`+`antiPatternExcerpt`の分割）。機能的差異はないため次回改訂で
  用語を統一する。

第27章 知恵の卒業試験・知識転移・キャリブレーションドリフト・退行原因自動特定 (Master v5.7・新規追補)
======================================================================

27.1 概要と目的
第9章・第20章・第23章・第24章の各自己改善ループはいずれも「単一の学習単位（スキル・
モデル・記憶）」を対象とした改善に留まる。本章では、それらを横断・時系列で見たときに
初めて見えてくる4つの改善余地を追加する。

27.2 知恵(ヒューリスティック)の卒業試験 (Heuristic Graduation Protocol)
- 目的: 第23.2項の知恵蒸留は「教訓を生成し登録する」までで、生成された
  `HeuristicRuleItem`が実際に有効かを事後検証する仕組みがない。効果の薄い教訓が
  無検証のまま蓄積されるリスクがある。
- 仕様:
  1. 登録済みの各`HeuristicRuleItem`について、第23.3項のスキル卒業と同様の
     「多様な文脈での再試験」を適用する。当該教訓を適用した場合と適用しない場合の
     両方で同一シナリオ群（第26章固定12シナリオから関連するものを抽出）を実行し、
     スコア差分を計測する。
  2. 有意な改善(既定+5点以上)が既定回数(3文脈)で確認できた教訓のみ`GRADUATED`とし、
     以後は常時プロンプトへ注入する「確定原則」に昇格させる。
  3. 改善が確認できない、または悪化させる教訓は`REJECTED`として非活性化し、
     プロンプト注入対象から除外する（削除はせず、再評価用ログとして保持）。

27.3 ドメイン横断の知識転移検出 (Cross-Domain Transfer Detection)
- 目的: スキル・ヒューリスティックがドメイン(VBA/コード相談/日常会話等)ごとに
  サイロ化され、あるドメインで得た汎用的な考え方が他ドメインへ転用されない。
- 仕様:
  1. 深い睡眠中、`GRADUATED`済みスキル・教訓の内容を実埋め込み(第14章)でベクトル化し、
     異なる`domain`タグを持つもの同士でコサイン類似度を比較する。
  2. 類似度が既定閾値(0.75)を超える組が見つかった場合、共通する抽象原則を
     1件生成し、`domain: 'general'`のドメイン非依存教訓として新規登録を提案する
     （27.2の卒業試験を経て正式採用）。
  3. 例: 「VBAのエラー処理で学んだ“想定外の入力を先に弾く”という考え方」と
     「対話での“曖昧な質問はまず確認してから進める”という考え方」が構造的に類似する場合、
     「未知・想定外の入力に対しては早期に検知・確認する」という汎用原則へ統合する。

27.4 自信過剰(キャリブレーション)ドリフト検知 (Confidence Calibration Drift Monitor)
- 目的: 第20章の不確実性駆動サンプリングは単発の判定であり、「ドメインごとに
  慢性的に自信過剰/過小」という傾向を時系列で追跡する仕組みがない。
- 仕様:
  1. 第20章の判定結果（不確実性「低」と判定したが後に誤りと判明したケース、
     およびその逆）を、`domain`タグ別に時系列ログとして蓄積する。
  2. 深い睡眠中、直近既定件数(50件)におけるドメイン別の「過信率」
     (不確実性「低」判定中の誤り率)を算出する。
  3. 過信率が既定閾値(15%)を超えるドメインについては、当該ドメイン限定で
     不確実性判定のしきい値を自動的に厳しめ（教師起動が発生しやすい方向）に調整する。
     閾値の自動調整幅は既定±10%を上限とし、変更履歴を`systemLogger`に記録して
     暴走的な過剰調整を防ぐ。

27.5 性能退行の原因自動特定 (Automated Regression Bisection)
- 目的: 第9章・第24章の回帰ベンチマークは「退行の検知」までで、「何が原因で
  退行したか」の切り分けはユーザー任せになっている。
- 仕様:
  1. 退行検知時、直近の変更イベントログ（モデル切替、ヒューリスティック新規採用、
     長期記憶の大規模更新、プロンプトテンプレート変更等、いずれも既存ログに
     タイムスタンプ付きで記録済み）を時系列で取得する。
  2. 退行が検知されたベンチマーク項目に対し、各変更イベントの直前時点のスナップショット
     （設定・教訓セット・使用モデルID）を疑似的に復元し、当該項目のみ再実行する
     「自己バイセクション（二分探索的切り分け）」を行う。
  3. どの変更イベント境界でスコアが悪化に転じたかを特定できた場合、
     `capabilityGapService`へ`gap_type: 'regression_root_cause'`として、
     原因と推定される変更内容とともに登録し、ユーザーへの報告時に
     「〇〇を導入した直後からVBA関連スコアが悪化しています」と具体的に提示できるようにする。
  4. 原因特定に至らなかった場合は、通常通り「退行を検知したが原因不明」として
     記録するに留め、誤った原因への自動ロールバックは行わない（安全原則優先）。

第28章 教師モニタリング・コード骨格テンプレート化・理解度追従型説明レベル調整 (Master v5.9・新規追補)
======================================================================

28.1 概要と目的
第8章・第20章で扱う外部教師API、第7章の会話向け回答骨格、そしてペルソナのタメ口設定に、
それぞれ「経年変化・実績の再利用・ユーザー個々の習熟度」という観点での追従が抜けている。
本章ではこの3点を追加する。

28.2 教師モデルの劣化・挙動変化検知 (Teacher Drift Monitoring)
- 目的: Gemini等の外部教師APIはモデルバージョンがサイレントに更新されることがあり、
  回答傾向や品質基準が予告なく変化しうる。教師の判定を無条件に信頼し続けるのは危険。
- 仕様:
  1. 固定テストプロンプト集(既定10件、第26章の固定シナリオとは別に教師専用に用意)を
     既定7日に1回、外部教師APIへ送信し、応答内容をハッシュ化・要約ベクトル化して保存する。
  2. 直近の応答ベクトルと過去のベースラインとの類似度が既定閾値(0.7)を下回った場合、
     「教師モデルの挙動変化を検知」として`systemLogger`に記録し、教師予算(第8章)の
     消費判定・回答骨格生成の信頼度重みを一時的に既定20%引き下げる。
  3. 挙動変化が確認された場合はユーザーへ「外部AIの応答傾向が変わったかもしれません」と
     通知するに留め、自動での教師切り替え・完全遮断は行わない（教師接続断による
     機能停止を避けるため）。

28.3 コード骨格の実績テンプレート化 (Proven Code Skeleton Templating)
- 目的: 第7章の回答骨格(AnswerPlan)は会話文向けであり、VBA/コード生成側には
  「過去に高評価だった構造をひな形として再利用する」経路がない。毎回ゼロから
  コードを組み立てるより、実績あるテンプレートを土台にした方が速く安定する。
- 仕様:
  1. ユーザーから👍評価、または実行結果フィードバックで成功が確認された生成コード
     （VBA/その他）を、変数名・具体値を抽象化したパラメータ化テンプレート
     (`CodeSkeletonTemplate`)として`skillsService`と同様の抽出ロジックで登録する。
  2. 新規のコード生成要求時、`embeddingService`による意味的類似度で既存テンプレートと
     照合し、類似度が既定閾値(0.7)以上のテンプレートが見つかった場合はゼロ生成ではなく
     テンプレートのパラメータ差し替え＋差分微調整を優先する。
  3. テンプレート適用結果に対しても通常のコード生成同様、第16章の静的検証・
     第51章の失敗シグネチャスキャンを必ず通過させ、テンプレート由来だからといって
     検証を省略しない。

28.4 ユーザー理解度追従型・説明レベル自動調整 (User Proficiency-Adaptive Explanation Depth)
- 目的: 現行はペルソナの口調（タメ口・簡潔）が固定的で、ユーザー個人の専門用語習熟度に
  応じて説明の詳細さを変える仕組みがない。
- 仕様:
  1. 会話ログから、ユーザー自身の発話に含まれる専門用語（VBA関数名、モデル名、
     技術用語等、既存の`worldModelService`用語辞書と照合）の出現頻度を`domain`別に
     時系列で追跡し、`userProficiencyScore`(0-100、ドメイン別)として算出する。
  2. スコアが既定閾値(既定70)を超えたドメインでは、該当分野の説明において
     基礎的な用語説明・前置きを既定より簡略化し、逆にスコアが低い(既定30未満)
     ドメインでは、補足説明・具体例を積極的に追加する。
  3. 本調整はペルソナの口調・キャラクター性そのものは変更せず、あくまで
     「説明の詳細度・前提知識レベル」のみを調整する。第21.3項の`persona_agnostic`
     記憶分類とは独立して、ユーザー単位でドメイン別に保持する。
  4. スコアの急激な変動（既定1週間で±30以上）は測定ノイズの可能性があるため、
     移動平均（既定直近10回の会話）で平滑化してから調整に反映する。

第48章: 完成条件と完了判定器 (Completion Conditions & Completion Judge) (Master v5.6)
======================================================================

48.1 目的
「モデルの重みを変えずに賢くする」ためには、AIが生成した回答やコードが「本当にユーザーの要求を満たし、
実行可能で、欠落がないか」を機械的・決定論的に検査する「完了判定器（Completion Judge）」が不可欠である。
曖昧な「できました！」という自己申告を排除し、厳格な検証ゲートを通過した成果物のみを「完成」と認定する。

48.2 7大完了判定チェックリスト
`completionJudgeService` は、生成された回答・コードを以下の7つの観点から自動採点（0〜100点）する:
1. 構文整合性 (Syntax Validity):
   - HTML/JS/CSS/VBAの括弧・タグ・ブロックが完全に閉じているか。構文エラーがないか。
2. ゼロ省略完全提供 (Zero-Omission Completeness):
   - 「// ここに処理を書く」「' 省略...」などの未実装・プレースホルダーが混入していないか。
3. プレビュー実行可能性 (Runnable Preview Ready):
   - Web成果物はブラウザサンドボックスで即座に実行可能か。
4. 要求充足性 (Requirement Satisfaction):
   - ユーザーが指示した機能要件・キーワード・条件が回答内に網羅されているか。
5. 参照・型安全性 (Reference & Type Safety):
   - VBAのPtrSafe宣言、ワークシート明示、未宣言変数の禁止などが守られているか。
6. リソース・セキュリティ安全性 (Security & Resource Safety):
   - 第16章・第51章のアンチパターン（無限ループ、危険コマンド、メモリリーク）が含まれていないか。
7. 誠実性制約 (Honesty Constraint):
   - 端末スペックや存在しないAPIについての虚偽断定（でっち上げ）がないか。

48.3 判定ステータスとUI可視化
判定結果は以下の4段階で評価され、`CompletionBadge` としてUIに表示される:
- `COMPLETED` (合格 / スコア85以上): 要求を完全に満たし、検証ゲートをパス。
- `IN_PROGRESS` (進行中): 複数ステップの途中、または追加確認が必要。
- `BLOCKED` (警告・要確認): 潜在的リスクや構文上の不備が検出された。
- `FAILED` (失格): 重大な欠落、危険パターン、または動作不能。
ユーザーはバッジをクリックして詳細な減点理由を確認でき、必要に応じてワンタップで手動「完了/未完了」を上書き可能。

第49章: 経験の保存先ルーター (Experience Destination Router) (Master v5.6)
======================================================================

49.1 記憶汚染の根絶
対話で得られたすべての情報を無差別に「長期記憶（Long-Term Memory）」に格納すると、文脈依存の一時的な値や
誤った情報が定着し、将来の推論を狂わせる「記憶汚染（Memory Pollution）」を引き起こす。
本アーキテクチャでは、あらゆる経験・情報を厳格にトリアージし、適切な「9大デスティネーション」へ振り分ける。

49.2 9大保存先定義
1. `working_memory` (作業記憶):
   - セッション限定の一時的状態（例: 「今はこのファイルの3行目を直している」）。会話終了で揮発。
2. `long_term_memory` (長期記憶):
   - 確定した事実、普遍的なユーザーの好み、継続的なルール（第2章⑤ 統合記憶へ沈降）。
3. `project_memory` (プロジェクト記憶):
   - 特定の案件、Excelマクロの仕様、特定リポジトリ限定の前提条件。
4. `skill` (手続き記憶・スキル):
   - 再利用可能な手順、ツールの組み合わせレシピ（第50章 技能卒業の候補）。
5. `search_policy` (検索ポリシー):
   - どの情報をWebのどこからどう取得すべきかの方針・ノウハウ。
6. `evaluation_set` (評価セット):
   - 今後の自己改善・回帰ベンチマーク用のテストケース・QAペア。
7. `lora_dataset` (LoRA教材):
   - 万が一モデル追加学習を行うための、安全検査通過済みの高品質指示・回答ペア。
8. `quarantine` (隔離バッファ):
   - 出典・正解が不確か、またはプロンプトインジェクションの疑いがある高リスク情報。推論への注入を完全遮断。
9. `discard_candidate` (破棄候補):
   - 重複、陳腐化、誤り、低評価過多の削除候補。ストレージクリーンアップ時に安全に消去。

49.3 自動ルーティングの判定基準
`experienceRouterService` は、経験の「普遍性」「再利用頻度」「確実性」「危険度」を多軸評価し、
確証のない情報は即座に長期記憶へ送らず、隔離または作業記憶に留める。

第50章: 技能卒業プロトコル (Skill Graduation Protocol) (Master v5.6)
======================================================================

50.1 目的
推論時に毎回ゼロから長い思考プロンプトを展開するのは、推論時間・トークン消費・電力の無駄である。
繰り返し成功した手順やツール連携は、検証・テストを経て「確立されたスキル」として昇格（卒業）させ、
軽量かつ確実な実行可能手続きとして結晶化する。

50.2 卒業（Graduation）の厳格な合格基準
スキルが「卒業候補」から「卒業認定（正式スキル）」へ昇格するには、以下の条件をすべて満たさなければならない:
1. 実行回数: 最低3回以上の実戦適用。
2. 成功率: 90%以上の成功率（`successRate >= 0.9`）。
3. 低評価ゼロ: 直近の実行においてユーザーからの低評価（👎）が0件であること。
4. 文脈の多様性検証 (Diversity Verification):
   - 同一プロンプトの連打による水増しを防止するため、少なくとも3つ以上の異なる文脈・クエリで
     正しく機能したことが数学的に確認されていること。

50.3 卒業後の恩恵
卒業したスキルは、長いLLM思考を経由せず、専用の軽量テンプレートや確定ツール呼び出しシーケンスとして
高速にディスパッチされ、端末の発熱と待機時間を大幅に削減する。

第51章: 失敗シグネチャ・カタログ (Failure Signature Catalog) (Master v5.6)
======================================================================

51.1 目的
「同じミスを二度と繰り返さない」ことは、モデルの重みを変えない知能進化において最も強力な武器である。
過去に発生したエラー、ユーザーからの叱責・低評価、実行時例外から「失敗の指紋（Failure Signature）」を抽出し、
二段階の防御壁（事前プロンプト注入 ＆ 事後静的スキャン）で同一パターンの再発を100%封殺する。

51.2 失敗シグネチャのデータ構造
各シグネチャは以下の要素で構成される:
- `id`: 一意の識別子
- `category`: 分類（VBA構文エラー、無限ループ、暗黙オブジェクト参照、環境前提欠落、でっち上げ等）
- `severity`: 重要度（`CRITICAL` / `HIGH` / `MEDIUM` / `LOW`）
- `title`: 簡潔な失敗名称（例: 「ActiveSheet/Selectionの暗黙参照による実行時エラー1004」）
- `detectionRegex`: 静的スキャナーが検知するための正規表現パターン
- `avoidanceInstruction`: LLMに事前提示する具体的な禁止・回避ルール文
- `antiPatternExcerpt`: 回避すべき悪例コードスニペット
- `occurredCount` & `preventedCount`: 過去の発生回数と、未然に阻止した回数
- `status`: ステータス（`ACTIVE` / `EXPERIMENTAL` / `RESOLVED` / `DEPRECATED`）

51.3 二段階防御ループの実装
1. 事前防御 (Pre-Generation Avoidance Injection):
   - `moeRouter.ts` において、ユーザー入力から関連する失敗シグネチャを自動抽出し、
     `【⚠️ 過去の反復失敗から抽出された必須回避ルール】` として動的プロンプトに注入。
   - モデルが生成を開始する前に「絶対に書いてはならないパターン」を明示的に警告。
2. 事後防御 (Post-Generation Static Scanning):
   - `codeVerificationService.ts` において、生成されたコード・テキストを全シグネチャの正規表現でスキャン。
   - 万が一アンチパターンが検出された場合、`preventedCount` を加算し、安全リスク警告（`bad_practice`）を付与。
   - 重大リスクの場合はプレビュー起動を自動遮断し、再生成または修正を促す。
3. 継続的蓄積:
   - ユーザーからの低評価（👎）や `completionJudgeService` の失格判定から、新たな失敗パターンを
     自動検出してカタログへ推薦登録する。
